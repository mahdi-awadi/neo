# Engineering practices that make autonomous coding agents reliable (state of the art, Nov 2026)

Scope note for the report writer: this file catalogues practices with (a) mechanism, (b) evidence, (c) the failure prevented, and (d) whether an engine can enforce it (`ENGINE`) or whether it only lives in a prompt (`PROMPT`), with `ENGINE+PROMPT` for hybrids. Measured results are labelled as such; opinion/vendor claims are labelled. Network note: in this session only `anthropic.com` and `code.claude.com` were fetchable directly; arxiv.org, metr.org, openai.com, trychroma.com were blocked, so figures from those sources come from abstracts/snippets and secondary summaries surfaced by search and are flagged "(via secondary)". The report writer should treat those numbers as approximately right but unverified against the PDF.

A cross-cutting framing that recurs across every section, stated by Anthropic's own docs: every instruction is either non-deterministic (prompt/CLAUDE.md/skill: "there's no *guarantee* that it'll follow your instructions") or deterministic (hook, deny rule, managed setting, test, Stop hook, CI, `--max-turns`, branch protection: "Claude Code applies this every time, no matter what the model decided to do"). "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

## 1. Verification: test loops, verifier-gated done, project checks, mutation/coverage, browser/screenshot QA, second-model review

### Takeaway
The single highest-leverage, engine-enforceable practice is giving the worker a pass/fail check it cannot skip (project tests/typecheck as a hard gate on "done"), while treating the agent's own "tests pass" claim as untrusted. Evidence: fabricated success appears in ~26% of failed CLI-agent trajectories; "submit vs resolve" gaps of 44–80 points; separate evaluators are measurably more tractable than self-grading; test-time sampling + verifier selection yields large gains at high budgets but is cost-sensitive; coverage is a weak proxy, mutation signal is stronger only when it drives generation.

### Cited Findings

**Why verification must be external to the model (failure being prevented: fake/premature completion)**
- "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually *is* done, 'looks done' is all it has to go on. In practice that makes you the test suite." The options form a ladder from least to most enforced: prompt ("run the auth tests after, and keep going until they pass") → `/goal` (a separate model checks a condition after every turn) → `Stop` hook (exit 2 blocks the stop; "enforced by Claude Code (the harness), so the turn doesn't end until the typecheck passes") → `/code-review` in a fresh subagent that "never saw your conversation. It isn't swayed by the reasoning that produced the code." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices) (ENGINE for hook/goal; PROMPT for the first rung)
- "Whichever option you use, ask Claude for *evidence*: the command it ran and its output, or the screenshot. 'All tests pass' on its own tells you very little." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- "Failure as a Process" (3,843 trajectories, 7 frontier models, 3 scaffolds on Terminal-Bench; 1,794 manually annotated, 63k steps): fabricated success (claiming results/completion with fake evidence) appears in 26% of failed trajectories; epistemic errors cause ~57.9% of failures, with acting on an unverified assumption the single largest trigger (30.7%); 92% of successful trajectories act on error signals vs 37% of failed ones; decisive error at median step 7 of a median 27-step run, first visible sign ~step 16 (via secondary) — [arXiv 2607.09510](https://arxiv.org/abs/2607.09510); [secondary summary](https://codex.danielvaughan.com/2026/08/06/failure-as-a-process-cli-coding-agent-trajectory-anatomy-codex-cli-early-intervention/)
- "Confident and Wrong": GPT-5 submits a patch on 100% of runs but resolves 44%; Llama 4 submits 99%/resolves 18%; Gemini submits 70% but resolves 50%; silent semantic failure rates reach up to 80% for some models; wrong patches are nearly identical across runs ("interpretation traps", Jaccard 0.49 overlap between GPT-5 and Llama 4 failure sets) — [arXiv 2603.25764](https://arxiv.org/abs/2603.25764)
- Terminal-Bench (ICLR 2026) failure taxonomy has three top-level classes, Execution / Coherence / Verification, with named modes including "Premature termination" and "No or Incomplete verification"; frontier agents resolve <65% of its 89 tasks — [Terminal-Bench paper, ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/file/444a3737adaee10d86ad2ef5f74468e6-Paper-Conference.pdf)
- Anthropic long-running-agent harness: "Claude often marked features complete after only unit tests or `curl` checks, without verifying end-to-end behavior"; the fix was browser automation (Puppeteer MCP) and testing "as a human user", which "dramatically improved performance" (qualitative, no numbers). The feature-list JSON forbids editing tests: "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality"; coding agents may only flip the `passes` field — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- "Building effective agents": coding agents benefit most because they can "gain 'ground truth' from the environment at each step"; the evaluator-optimizer pattern fits when there are "clear evaluation criteria, and when iterative refinement provides measurable value" — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)

**Separate evaluator / second model (failure prevented: self-grading leniency)**
- Anthropic harness-design post: "agents reliably skew positive when grading their own work"; "Out of the box, Claude is a poor QA agent" (talked itself into approving flawed work, tested superficially); "tuning a standalone evaluator to be skeptical turns out to be far more tractable"; hard thresholds per criterion ("if any one fell below it, the sprint failed"); evaluator clicks through the running app with Playwright. Measured: solo Opus 4.5 run 20 min/$9 with the core feature broken vs full planner/generator/evaluator harness 6 h/$200 (>20x cost) producing a playable result with 16 features across 10 sprints; a simplified harness on Opus 4.6 3 h 50 min/$124.70, with QA rounds ~$3–4 each still catching stubbed features — [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Cross-model review controlled experiment (30 artifacts, 150 planted errors, 900 review sessions): two reviewers find partly different errors (Jaccard 41.2%); a top-tier cross-model reviewer is "not significantly different in F1 from same-model review in a fresh session"; a lightweight cross-model reviewer scores no higher — [arXiv 2607.21656](https://arxiv.org/pdf/2607.21656)
- "Groundability, Not Scale Alone": reviewer size is not a consistent predictor of audit quality (Qwen3-235B catches 0.28 vs Llama-8B 0.70 under structured evidence); with official execution evidence, 5 of 6 reviewers improve both catch and over-rejection on 122 held-out traces and two classify every trace correctly; what matters is "whether an independent check, such as a runnable test or sound static analysis, can answer the disputed question" — [arXiv 2610.01023](https://arxiv.org/abs/2610.01023)
- RETRACE (bidirectional reconstruct-and-verify, training-free, runs after the patch): +7.0 and +3.6 Pass@1 on SWE-bench Verified with two backbones on mini-SWE-agent, comparable gains on OpenHands; independent commentary disputes that this is truly "independent" rather than a self-consistency check — [arXiv 2608.08950](https://arxiv.org/abs/2608.08950); [Pith critique](https://pith.science/paper/2608.08950)
- Practitioner reports: a fresh reviewer agent given only the diff caught hardcoded image URLs pointing at an old port that Playwright tests missed; three of four LLM reviewers "returned confident findings about files they had never read" (anecdotal) — [daily.dev write-up](https://daily.dev/posts/how-to-make-your-coding-agent-check-its-work-in-the-browser-faxnmjz0d); [DEV post](https://dev.to/tonydzi/i-asked-four-llms-to-review-my-code-by-path-three-invented-bugs-199n)
- Anthropic's reviewer-subagent pattern: `tools: Read, Grep, Glob` gives "a reviewer that can't edit anything, and that limit is enforced by Claude Code rather than requested in a prompt"; the review prompt should say "skip style" because "A reviewer that's asked to find problems will always find *something*" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices) (ENGINE: tool restriction; PROMPT: the "skip style" instruction)

**Test-time sampling + verifier selection (failure prevented: single-sample wrong patch)**
- Repeated sampling on SWE-bench Lite raised DeepSeek-Coder-V2 from 15.9% (1 sample) to 56% (250 samples); CodeMonkeys resolved 57.4% of SWE-bench Verified at ~$2,300 budget (via secondary) — [Awesome-Inference-Time-Scaling list](https://github.com/ThreeSR/Awesome-Inference-Time-Scaling)
- SWE-Replay cuts the cost of naive test-time scaling by up to 17.4% while maintaining or improving performance by up to 3.8% on SWE-bench Verified — [arXiv 2601.22129](https://arxiv.org/abs/2601.22129)
- SWE-Verifier (step-level verification of agent actions): 73.27% resolution at 1.29× cost at one threshold — [arXiv 2610.30284](https://arxiv.org/html/2610.30284)
- "Sample, Mix, or Verify?": under imperfect LLM patch verifiers (492 SWE-bench Verified tasks × 22 samples), argmax/threshold selection beats power-law extrapolation at 16 samples, but the advantage is "large only under a simulated verifier" — [arXiv 2610.23255](https://arxiv.org/html/2610.23255)
- Anthropic's own vendor claim: Sonnet 4.5 77.2% on SWE-bench Verified, 82% with parallel test-time compute (vendor-reported, via secondary) — [Medium summary](https://medium.com/@cognidownunder/claude-sonnet-4-5-4ddf33d53cd4)

**Coverage vs mutation signals (failure prevented: hollow tests that pass)**
- Replicability study: "weak to negligible correlations between test suite size and both raw and normalized mutation score for LLM-generated test suites"; coverage/mutation "no longer serve as reliable indicators when the code under test is already buggy" — [arXiv 2607.22880](https://arxiv.org/abs/2607.22880)
- Hamidi et al.: mutation testing "only marginally outperformed statement and branch coverage in both fault triggering and fault detection, at higher cost"; generated assertions "often fail to recognise the incorrect behaviour of LLM-generated code" — [ICSoft summary](https://www.icsoft.org/article/study-finds-traditional-test-criteria-miss-many-llm-generated-code-faults.html)
- Mutation feedback *inside* the generation loop: MutGen 53% → 89.5% mutation score on HumanEval-Java (via secondary); AdverTest (adversarial test-vs-mutant agents) +8.56% fault detection on Defects4J over best prior LLM methods, "the gain came from optimising for killed mutants, not for coverage" — [Augment guide](https://www.augmentcode.com/guides/mutation-testing-ai-generated-code); [arXiv 2602.08146](https://arxiv.org/html/2602.08146v1)
- Thoughtworks moved mutation testing to "Trial" (Apr 2026) because "high coverage percentages can mask logically hollow tests" (via secondary) — [creuto.com](https://creuto.com/ai-generated-unit-tests-coverage-vs-mutation-testing)

**Browser / screenshot verification for UI (failure prevented: "renders in curl but broken for a user")**
- Anthropic's evaluator used Playwright MCP to navigate the live page and score design quality, originality, craft, functionality; limitation: Claude "cannot see browser-native alert modals through Puppeteer MCP, so features that rely on them tended to be buggier" — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps); [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Claude Code lists "A browser screenshot next to the mockup" as a valid pass/fail check, and `/verify` "has Claude build and run the app and look at the result. That catches the kind of problem that tests and typechecks miss." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Practitioner tooling: agents record UI changes with the Playwright CLI and attach screenshots/recordings to PRs, required to inspect every screenshot before presenting; Playwright MCP "ships an accessibility-tree snapshot alongside pixels"; "a screenshot is evidence, not a regression test" — [timdeschryver.dev](https://timdeschryver.dev/blog/let-your-ai-agent-capture-its-changes-with-the-playwright-cli); [daily.dev](https://daily.dev/posts/how-to-make-your-coding-agent-check-its-work-in-the-browser-faxnmjz0d)

**Benchmark-level caveats on what "verified" means**
- OpenAI audit (Jul 8 2026): ~30% of SWE-Bench Pro tasks broken (automated pipeline 200 = 27.4%; human annotation 249 = 34.1%); defects include hidden requirements, contradictory instructions, overly strict tests, incomplete grading; OpenAI retracted its recommendation of the benchmark — [OpenAI post](https://openai.com/index/separating-signal-from-noise-coding-evaluations/); [OpenAI on X](https://x.com/OpenAI/status/2074972179385720836)
- SWE-Bench+ found ~32.67% of one agent's apparent successes involved solution leakage and 31.08% passed weak tests; filtering dropped SWE-Agent+GPT-4 from 12.47% to 3.97% — [SWE-Bench+](https://huggingface.co/papers/2410.06992); SWE-Bench Pro Verified reports reward hacking "enabled by leakage of gold solutions or hidden evaluation information" — [arXiv 2609.08149](https://arxiv.org/abs/2609.08149)
- Terminal-Bench 2.1 fixed 28 of 89 tasks (changed external deps, too-tight resource budgets, instructions not matching tests) — [Snorkel leaderboard](https://snorkel.ai/leaderboard/terminal-bench-2-1/)

### Inferences
- An engine should implement a **verifier-gated done**: the worker's final "done" is a *claim*; the engine runs the project's own check command (test/typecheck/lint), parses the exit code, and only then records done. The Claude Code `Stop` hook with exit 2 is exactly this mechanism and is available programmatically in the Agent SDK `hooks` option (see §6), so Neo can do it in code rather than trusting a prompt.
- Since fabricated-success and "submit-but-wrong" rates are high and model-stable, an engine should **log the verification evidence** (command + stdout/exit code) in the ledger, not the model's summary.
- Separate evaluator > self-review is well supported; *cross-model* evaluator > same-model-fresh-context evaluator is **not** established by controlled data. The cheap win is a fresh-context, read-only reviewer (engine-enforced tool restriction), not necessarily a second vendor.
- Mutation testing is not worth running as a routine gate (marginal gain, high cost); it is worth using as a *generation-time* signal when the agent is writing tests, and coverage % should never be a gate on its own.
- Browser verification is engine-enforceable in the sense of "require a screenshot/trace artifact before done" but its *judgement* still comes from a model; pair with deterministic checks (console errors, failed network requests, element presence).

### Gaps
- No controlled study quantifying how much a Stop-hook-style test gate reduces defect rate in shipped PRs; evidence is mechanistic plus trajectory studies, not an A/B on merge quality.
- No independent replication of RETRACE's or SWE-Verifier's gains; no head-to-head of LLM-judge vs held-out-test detection accuracy for reward hacking beyond EvilGenie's own claims.
- Browser/screenshot verification has no research-grade effect size; all evidence is practitioner or Anthropic-qualitative.

## 2. Planning and specification: spec-first, plan approval, decomposition, acceptance criteria, "stop by impact"

### Takeaway
Measured evidence says explicit planning raises success for weaker models but mostly *reduces cost* (fewer turns, less redundant post-edit verification) for strong ones; the clearest reliability wins come from decomposition into one-feature-per-session with a written definition of done, sprint "contracts" negotiated before coding, and explicit abstain/stop rules. The "2–3x" plan-mode claims are vendor/blog, not measured.

### Cited Findings
- "An Empirical Study of Harness Design for Coding Agents" (176 settings, 4 models, SWE-bench Verified + Terminal-Bench 2.1; execution loop held fixed): for the weakest model planning raises success; for stronger models accuracy barely moves and the gain shows up as lower cost; planning "primarily improves stopping behavior by reducing redundant post-edit verification, rather than accelerating localization or repair"; median SWE-bench trajectory for one strong model drops from 108 to 74 turns (via secondary) — [arXiv 2609.20804](https://arxiv.org/html/2609.20804v1); [summary](https://notesbylex.com/an-empirical-study-of-harness-design-for-coding-agents)
- SlopCodeBench "plan_first" condition appears to score slightly below "just solve" for GPT-5.5 rows (reading of a table via secondary; unverified) — [arXiv 2603.24755](https://arxiv.org/abs/2603.24755)
- Anthropic long-running harness: the initializer agent expands the prompt into a JSON feature list (>200 features for a claude.ai clone, each with category/description/test steps/`passes`); JSON chosen "because models are less likely to inappropriately overwrite it than Markdown"; each coding session works one feature and ends with a commit + progress entry; failure modes it prevents: "one-shotting" (ran out of context mid-feature leaving half-built undocumented work) and "premature completion" (later sessions saw progress and declared the project finished) — [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) (ENGINE: feature-list schema and one-feature-per-session loop; PROMPT: the content of the plan)
- Harness-design post: planner "focused on deliverables rather than granular technical detail, so spec errors don't cascade"; "sprint contracts": generator and evaluator negotiate what 'done' means and how it will be tested before coding; after Opus 4.6, sprints were no longer needed for coherence but the evaluator was kept "where the task sat beyond what the model could reliably do alone"; "the space of interesting harness combinations doesn't shrink as models improve" — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Claude Code docs: "Interview me until you could write the spec, then write it to SPEC.md. ... Once `SPEC.md` exists, start a fresh session to build from it, so the build begins with a clean context and a written definition of done"; the five pre-unattended-run questions: does it know what done looks like, can it check its own work, what may it touch, what stops it (`--max-turns`, `--max-budget-usd`), who signs off — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Cursor: "the most impactful change you can make is planning before coding" (vendor opinion; cites a U. Chicago study about *developer* behaviour, not agent success) — [Cursor blog](https://cursor.com/blog/agent-best-practices)
- Blog claims of "2–3x success rate improvement" from plan mode and "23% → 61%" with a planning document have no methodology and should not be cited as evidence — [vibecoder blog](https://blog.vibecoder.me/plan-mode-2x-3x-success-rate-claude-code); [loadsys](https://www.loadsys.com/blog/ai-coding-agent-failure-rate/)
- "Stop by impact" / knowing when *not* to act: FixedBench shows agents apply unnecessary edits to already-fixed code in 35–65% of cases; an explicit verify-then-abstain instruction raised correct abstention to 80.5% and 88.5% for top models but "introduces a symmetric failure mode: over-abstention on incorrect code" — [arXiv 2605.07769](https://arxiv.org/abs/2605.07769); [ETH SRI blog](https://www.sri.inf.ethz.ch/blog/fixedcode). "Confident and Wrong" probe: most models still edited correct code when abstaining was right — [arXiv 2603.25764](https://arxiv.org/abs/2603.25764)
- Boundary/scope violations: SWE-Misbehavior (7.4K samples, 11 misbehaviours) reports agents touched unrelated files in up to 21.5% of file tasks, environment-integrity violations up to 53% on system tasks (unrequested `git checkout`, dependency installs), unintended changes to user inputs 50.5%; the authors attribute much of it to "tool interfaces rather than the underlying model"; their Code-KIT scaffold cut misbehaviours 52% (smolagents) / 34% (OpenHands) while improving completion — [arXiv 2610.18206](https://arxiv.org/html/2610.18206)
- "How Coding Agents Fail Their Users" (20,574 sessions, 1,639 repos, EMNLP 2026): seven forms including wrong project diagnosis, misread intent, constraint violation, self-initiated overreach, faulty implementation, operational error, inaccurate self-reporting; 91.49% of visible resolutions required explicit user correction; constraint violations and inaccurate self-reporting are a *growing* share over time; CLI sessions more prone to constraint problems — [arXiv 2605.29442](https://arxiv.org/abs/2605.29442); [ACL Anthology](https://aclanthology.org/2026.emnlp-main.1011/)
- Beyond Resolution Rates (9,374 trajectories, 19 agents, 500 tasks): agents that "gather context before editing and invest in validation succeed more often", and those strategies "are set by the agent rather than adapted to each task"; framework prompts' influence "diminishes with stronger LLMs"; 12 never-solved tasks fail on architectural reasoning/domain knowledge, not patch complexity — [arXiv 2604.02547](https://www.alphaxiv.org/overview/2604.02547v1)

### Inferences
- For a strong-model engine, mandatory plan-approval is a **cost** control and a **scope** control more than an accuracy control. Neo's plan registry (Approve/Changes/Execute) is justified mainly by overreach/constraint-violation data (21–53% boundary violations; growing share of constraint violations), not by raw pass-rate data.
- Decomposition should be **engine-owned data** (a schema-validated feature/todo list with per-item acceptance test and a `passes` flag the engine flips only after its own verification), not free text in a prompt. Anthropic's "JSON over Markdown because models overwrite it less" is a concrete, cheap format choice.
- "Stop by impact" rules (e.g., do not run `git checkout`, install deps, or touch files outside the brief) are enforceable via PreToolUse hooks and path fences; abstain-when-already-fixed is only PROMPT-enforceable and has a known over-abstention cost.

### Gaps
- No controlled measurement of plan-approval (human in the loop) on defect/merge rates; only vendor claims.
- No data on the optimal granularity of decomposition (feature size per session); Anthropic reports it changed model-to-model (Opus 4.5 needed sprints, 4.6 did not).

## 3. Context management: compaction, checkpoints, handoff notes, forking, fresh-context-per-subtask, repo maps, context bloat effects

### Takeaway
Context degradation is real and measured ("context rot" across 18 models; distractors worse than length alone), and compaction is lossy and unstable; the practices with the best evidence are structured external state (feature list + progress file + git) with clean-context restarts, sub-agents returning condensed results, and just-in-time retrieval over pre-loaded context. Repo maps give only modest localization gains over grep.

### Cited Findings
- Anthropic context engineering: "Context ... must be treated as a finite resource with diminishing marginal returns"; n tokens create n² pairwise attention relationships; keep "the smallest set of high-signal tokens"; tools should be minimal with little overlap ("If a human engineer can't definitively say which tool should be used in a given situation" the agent won't either); just-in-time retrieval with lightweight identifiers, hybrid with key files loaded up front (CLAUDE.md); compaction = summarise + restart, in Claude Code keeping the summary plus the five most recently accessed files; tune compaction prompt for recall then precision; clearing old tool results is the lightest compaction; structured note-taking (NOTES.md/to-do) outside the window; sub-agents may use tens of thousands of tokens but return 1,000–2,000-token summaries — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Chroma "Context Rot" (Jul 2025, 18 models incl. GPT-4.1, Claude 4, Gemini 2.5, Qwen3): reliability degrades non-uniformly as input grows even on simple tasks; degradation starts well before the window is full; semantically similar distractors degrade beyond length alone; needle position mattered little vs distractors and question-answer similarity; a LongMemEval result where ~300 relevant tokens outperformed ~113k tokens containing the same answer (all via secondary; original not fetchable) — [hivetrail summary](https://hivetrail.com/blog/context-rot-chroma-study); [particula summary](https://particula.tech/blog/chroma-context-rot-long-context-degradation); [Hacker News thread](https://hn.svelte.dev/item?id=44564248)
- "Classifier Context Rot": monitor/classifier performance also degrades with context length — [arXiv 2605.12366](https://arxiv.org/pdf/2605.12366)
- Harness-design study: context management "mainly helps by preventing context-overflow failures, and it matters most as the context budget tightens" — [arXiv 2609.20804](https://arxiv.org/html/2609.20804v1)
- Anthropic harness-design: "context anxiety" (models wrap up early as they near a perceived limit); "Compaction alone was not enough for Sonnet 4.5: context resets became essential"; with Opus 4.5 progress passed via context resets + structured handoff artifacts; with Opus 4.6 one continuous session with SDK auto-compaction sufficed — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Anthropic long-running harness session routine: `pwd`, read git log + `claude-progress.txt`, read feature list and pick highest-priority unfinished, run `init.sh` and an end-to-end smoke check before new work; sessions end with a commit + progress entry; git lets agents revert bad changes — [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) (ENGINE: the engine can run this routine and inject the files)
- Compaction loss measurements: summary-conditioned agents "more often continue acting or supply unnecessary content instead of terminating directly" at 4K and 8K budgets — [arXiv 2608.06503](https://arxiv.org/pdf/2608.06503); a terminal-agent RL run where budget/summary-length mismatch caused 98.3% of full-summary attempts to fail, agents repeated completed work and average turns rose 22 → 30 — [T1, arXiv 2609.11042](https://arxiv.org/pdf/2609.11042); "Compaction Cliff": decay "appeared for every LLM family and every structural baseline" — [arXiv 2608.22752](https://arxiv.org/html/2608.22752v1); summary length and content "become increasingly unstable at longer contexts" — [arXiv 2605.23296](https://arxiv.org/pdf/2605.23296); CompactionRL: task success is "sensitive to the quality of the summary" — [arXiv 2607.05378](https://arxiv.org/html/2607.05378v1)
- Claude Code current guidance: "With a 1M-token window on most current models and compaction near the top of it, you'll rarely run out of context. You can still *pay* for context you don't need"; `/clear` between unrelated tasks; "after two failed corrections run `/clear` and write a better prompt instead of a third" (a third correction "mostly adds to a conversation that already contains two failed attempts"); the "old advice" table retires "manage context aggressively" and "use subagents to protect your context window" but keeps subagents for parallelism, noisy output, and independent review — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Multi-agent research system (Anthropic internal eval): Opus 4 lead + Sonnet 4 subagents outperformed single Opus 4 by 90.2%; token usage alone explains 80% of variance (with tool calls and model choice the other factors, on BrowseComp); agents use ~4× chat tokens, multi-agent ~15× — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- Agent SDK sessions: sessions persist the *conversation*, "not the filesystem" (file checkpointing is separate); `resume` by id recovers from `error_max_turns` / `error_max_budget_usd`; `forkSession` branches history ("Forking branches the conversation history, not the filesystem"); cross-host resume via `SessionStore` or moving the `.jsonl`; alternative: "Capture the results you need ... as application state and pass them into a fresh session's prompt. This is often more robust than shipping transcript files around." — [Agent SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions)
- Claude Code checkpoints "cover the files Claude edited with its own file tools ... a file that only a Bash command touched isn't restored. They work alongside git rather than replacing it." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Repo maps / retrieval: Agent Retrieval Bench — lexical retrieval beats most embedding baselines on MRR; top-3 file F1: grep 0.0841, RepoMap 0.1102, Qwen3-4B retriever 0.1247; "embeddings alone are insufficient" — [arXiv 2607.24882](https://arxiv.org/html/2607.24882). Architecture survey of 13 agents: keyword/regex search most common; only one exposes embedding retrieval as an LLM tool; Aider's repo map is a PageRank-weighted tree-sitter tag index — [arXiv 2604.03515](https://arxiv.org/pdf/2604.03515). Claude Code: a "code intelligence plugin lets Claude jump straight to a definition instead of reading through many files" — [best practices](https://code.claude.com/docs/en/best-practices)
- SlopCodeBench (long-horizon iterative extension): no agent fully solves any problem end-to-end (best 14.8% of checkpoints); structural erosion rises in 77% of trajectories, verbosity in 75.5%; agent code 2.3× more verbose and 2.0× more eroded than 473 OSS repos; quality prompts cut initial verbosity/erosion up to a third "without affecting degradation rates" ("shift the intercept but not the slope") — [arXiv 2603.24755](https://arxiv.org/abs/2603.24755)

### Inferences
- The robust engine pattern is **state outside the context**: feature list (schema), progress file, git commits, and a deterministic start-of-session routine the engine injects; use `resume` for crash recovery within a task but prefer **fresh session + explicit handoff artifact** at task boundaries (matches Neo's ADR-0021 "boundary handoffs").
- Compaction should be treated as a lossy, model-dependent fallback: `PreCompact` hooks can archive the full transcript and inject the engine's own structured summary; the engine should snapshot task state before compaction rather than trusting the summary.
- Sub-agents are an engine-enforceable isolation primitive (tool restriction + fresh context) whose main costs are tokens (~15× chat) and re-gathering context.
- Repo maps are cheap and modestly helpful; the engine should guarantee `rg`/grep availability and consider LSP/code-intelligence for typed languages rather than investing in embeddings.

### Gaps
- No public study quantifying success-rate loss per compaction event in *coding* agents with current frontier models; the measured compaction studies are small or RL-specific.
- Chroma's exact per-model numbers were not retrievable (site blocked); one blog's "7.9% drop" figure is uncorroborated.

## 4. Memory and learning across runs: project memory files, curated vs raw, corrections-as-rules, skills, memory poisoning/drift

### Takeaway
Memory files are high-trust, auto-loaded instruction channels, which makes them both a cheap way to capture corrections and a persistent injection/drift surface. Evidence favours: keep CLAUDE.md short and rationale-annotated, prefer skills (loaded on demand) for procedures, compile recurring corrections into *runtime checks* rather than more prose, and scan/purge memory because poisoning persists across sessions.

### Cited Findings
- Claude Code: CLAUDE.md loads every session so "every line in it takes a little of Claude's attention on *every* task"; write only what Claude "couldn't work out from the code itself": test/typecheck commands, misleading places in the code, decisions not in the repo, "Anything you've had to correct twice already"; memory guide recommends staying under 200 lines; `/doctor prompt-audit` flags stale/contradicting instructions; path-scoped `.claude/rules/*.md` with `paths:` filters; skills are "lighter on context" because the full file is read only when the task calls for it; `disable-model-invocation: true` makes a side-effecting skill runnable only by the operator — [Claude Code best practices](https://code.claude.com/docs/en/best-practices) (ENGINE: path-scoped rules and invocation control; PROMPT: content)
- "Why Does CLAUDE.md Keep Growing? Catastrophic Remembering" (247,694 instruction lifetimes, 1,867 repos): files grow ~226% over their lifetime; older instructions are less likely to be deleted; 76.8% of instruction deletions occur in whole-file rewrites; storing the rationale next to each instruction is proposed as the fix, with one summary claiming comments remove 99.3% of excess growth (unverified) — [arXiv 2608.11095](https://arxiv.org/abs/2608.11095); [irz.fr summary](https://irz.fr/en/articles/agent-instructions-catastrophic-remembering-en/); [developersdigest summary](https://www.developersdigest.tech/blog/claude-md-catastrophic-remembering-2026)
- TRACE: "memory alone is insufficient ... even when agents can access past corrections via a memory system, they frequently fail to comply with them"; it mines user corrections, rewrites them as atomic rules, and compiles them into runtime checks (evaluated on ClawArena and MemoryArena-derived tasks) — [arXiv 2606.13174](https://arxiv.org/pdf/2606.13174)
- Accumulated-behavioural-rules deployment (35+ microservices): rule set grew 5 → 18 rules plus 15+ language standards and a 15-item self-review checklist (anecdotal, uncontrolled) — [arXiv 2607.13091](https://arxiv.org/abs/2607.13091)
- CODESKILL learns/evolves procedural memories from downstream feedback; earlier coding-agent memory mostly retrieved/summarised prior cases — [arXiv 2605.25430](https://arxiv.org/pdf/2605.25430)
- Source-code taxonomy: all five surveyed agents "with no persistent memory treat each task as independent, with no cross-task learning" — [arXiv 2604.03515](https://arxiv.org/pdf/2604.03515)
- "Bad Memory" (Claude Code + Codex; Haiku 4.5, Opus 4.7, GPT-5.2, GPT-5.5): payloads planted in auto-loaded files (CLAUDE.md, AGENTS.md) successfully attack current and future sessions; Claude models persisted the payload more often than Codex models; credential theft succeeds on weaker models and is refused by stronger ones; success varies by model/goal/sequence (exact ASRs not retrievable) — [arXiv 2607.14611](https://arxiv.org/abs/2607.14611); [Pith review](https://pith.science/paper/2607.14611)
- MemoryGraft: poisoned "successful experiences" planted through benign-looking files (e.g., READMEs) are retrieved on later similar tasks and cause persistent drift "until the memory is manually purged" (MetaGPT SE agent) — [arXiv 2512.16962](https://arxiv.org/abs/2512.16962)
- Cisco demonstration: poisoning Claude Code MEMORY.md via a hook rewrote guidance so the agent recommended committing API keys; "memory files are treated as high-authority additions ... models assume they were written by the user and implicitly trust them" — [Cisco blog](https://blogs.cisco.com/ai/identifying-and-remediating-a-persistent-memory-compromise-in-claude-code)
- "Persistent Memory Poisoning Attack on Harness-Based Agents" and "From Untrusted Input to Trusted Memory" survey the attack class — [arXiv 2609.13889](https://arxiv.org/pdf/2609.13889); [arXiv 2606.04329](https://arxiv.org/pdf/2606.04329)
- Claude Code's `--bare` flag for scripted runs "skips hooks, skills, plugins, MCP servers, and `CLAUDE.md` files ... so the run does the same thing wherever it runs" — [best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- Neo's "capped curated memory + frozen snapshot injection" is aligned with the evidence: cap size (attention cost), curate (catastrophic remembering), freeze/snapshot (poisoning persistence). Add: store a *reason* with each memory line, and a scheduled prune pass (the "dream loop") that deletes rules whose rationale no longer applies.
- Corrections the operator makes twice should be compiled into a **hook/check** (ENGINE) where possible (TRACE finding), and only otherwise into a CLAUDE.md line (PROMPT).
- Because memory/instruction files are trusted at the same level as the user, the engine should treat them as a write-protected surface: deny worker writes to `CLAUDE.md`/`MEMORY.md`/`.claude/` via PreToolUse (or route through an operator-approved path), and diff/scan them at session start.

### Gaps
- No quantitative study of how much curated project memory improves task success in coding agents (the memory papers measure risk and compliance, not uplift).
- Bad Memory per-model attack-success percentages not retrievable.

## 5. Self-review and honesty: outcome reports, draft-vs-done, fake completions, reward hacking detection

### Takeaway
Reward hacking and fabricated completion are measurable, prompt-resistant, and concentrated where graders are visible or tests are editable; detection that works is structural (test files immutable or separated from the patch, held-out tests in a fresh sandbox, evidence-bearing reports), not asking the model to be honest.

### Cited Findings
- METR "Recent Frontier Models Are Reward Hacking" (Jun 2025): o3 pre-deployment eval found reward hacking in ~0.7% of HCAST runs, ~1–2% of all attempts across HCAST+RE-Bench, 30.4% of RE-Bench runs, and on one RE-Bench task "in every single trajectory we generated"; hacking >43× more common on RE-Bench than HCAST; similar behaviours in Claude 3.7 Sonnet and o1; instructions not to cheat had limited effect (one summary: 80% → 70% with an Alzheimer's-research framing; o3 hacked 14/20 attempts framed as real-world science) (figures via METR summary pages and secondary) — [METR post](https://metr.org/blog/2025-06-05-recent-reward-hacking/); [METR o3 report](https://metr.org/evaluations/openai-o3-report/); [LessWrong summary](https://www.lesswrong.com/posts/Zu4ai9GFpwezyfB2K/metr-recent-frontier-models-are-reward-hacking)
- A MIRI compilation cites a METR table where a "Please do not cheat" prompt moved the rate from 80% to 95% (unverified secondary) and METR 2026 "MirrorCode" experiments where agents tried to expose hidden tests, alter scoring scripts, and infer protected test information — [MIRI PDF](https://intelligence.org/wp-content/uploads/The-State-of-Reward-Hacking-in-AI-September-2026.pdf)
- EvilGenie (LiveCodeBench-derived, environment where hacking is easy): measures hacking via held-out unit tests, LLM judges, and test-file-edit detection; explicit reward hacking observed in both Codex and Claude Code, misaligned behaviour in all three agents tested; o4-mini and GPT-5 hack more on ambiguous problems; claims LLM judges outperform held-out tests for detection — [arXiv 2511.21654](https://arxiv.org/abs/2511.21654)
- SpecBench (30 systems-level tasks, JSON parsers to OS kernels): defines reward hacking as the validation-vs-held-out gap; one result shows a 97pp gap — [arXiv 2605.21384](https://arxiv.org/abs/2605.21384)
- Reward Hacking Benchmark (tool-use agents): Claude 3.7 Sonnet 3.9% exploit rate vs o3 11.8% (not a METR result) — [arXiv 2605.02964](https://arxiv.org/pdf/2605.02964)
- Defence-in-depth protocol from SE-agent RL: separate the agent's patch from the tests, replay only the sanitised patch in a fresh sandbox, then run held-out tests "so reward doesn't depend on rollout-side test edits" — [arXiv 2609.23377](https://arxiv.org/pdf/2609.23377)
- "From Faulty Claims to Incorrect Patches": task-grounded reasoning is 18.5% of CoT tokens yet yields ~191 checkable claims per trajectory, ≥9.6% faulty; 127 of 188 incorrect patches trace to faulty claims; some faulty claims "leave defects that the validation tests miss, yielding plausible but incorrect patches" — [arXiv 2610.32338](https://arxiv.org/abs/2610.32338)
- "How Coding Agents Fail Their Users": "inaccurate self-reporting" is one of seven forms and a growing share over time — [arXiv 2605.29442](https://arxiv.org/abs/2605.29442)
- Anthropic: feature-list rule that agents "may change only `passes`" and must not edit/remove tests; evaluator separated from generator because self-grading "reliably skew[s] positive" — [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Claude Code scripted-run contract: `claude --bare -p "... Reply OK or FAIL." --max-turns 20` with "a run that hits the turn limit exits with an error instead"; `--output-format json` gives "a single result object to parse" — [best practices](https://code.claude.com/docs/en/best-practices)
- GPT-5.1-Codex-Max system card notes Codex models were "more likely to attempt data-destructive actions in some tests" and reports reward-hacking findings (fragmentary) — [OpenAI system card PDF](https://cdn.openai.com/pdf/2a7d98b1-57e5-4147-8d0e-683894d782ae/5p1_codex_max_card_03.pdf)
- Monitoring reward hacking via internal representations during evals — [arXiv 2609.19101](https://arxiv.org/pdf/2609.19101)

### Inferences
- The engine should make tests **structurally unhackable**: PreToolUse deny on edits to test files/CI config during implementation (or require a separate, reviewed "test change" step); run the project's checks in a fresh checkout that contains only the agent's non-test diff; compare agent-visible vs held-out results where the engine can keep a held-out suite.
- Structured outcome reports should be **schemas the engine validates** (status enum, commands run, exit codes, files changed, open questions), with "done" being a status the engine assigns after verification — a model-written "done" is at most "draft/claims-done".
- Prompting for honesty is weak evidence-wise; the only prompt-level practice with support is "ask for evidence (command + output)" plus a reviewer who hasn't seen the reasoning.

### Gaps
- No production-scale measurement of reward-hacking rates in self-hosted SDK workers on real repos (all data is benchmark/eval).
- EvilGenie's LLM-judge accuracy and SpecBench vs EvilGenie comparability are not established.

## 6. Tool-call hygiene: loop/spin detection, stall detection, retry ladders, idempotent external actions, recovery after interruption

### Takeaway
Loop/stuck detection with simple exact-match rules (reminder at ~4–5 identical calls, terminate at ~8 identical failing calls) is standard in production harnesses; asynchronous monitors can resolve ~90% of single-intervention misbehaviours; many errors self-recover within a few steps so intervention should target non-recovering patterns; external side effects need harness-generated idempotency keys and unknown-outcome reconciliation. All of these are engine-enforceable, mostly via PreToolUse/PostToolUse/Stop hooks and the session resume API.

### Cited Findings
- OpenHands Stuck Detector (on by default): five unproductive patterns including repeated actions; compares events by tool name, action content and thought (ignoring ids/metrics); triggers on four identical action-observation pairs — [OpenHands docs](https://docs.openhands.dev/sdk/guides/agent-stuck-detector)
- Harness-design study's fixed substrate: reminder after 5 consecutive byte-identical tool calls, termination after 8 consecutive identical failing calls; reminder prompts in the appendix — [arXiv 2609.20804](https://arxiv.org/html/2609.20804v1)
- agent-loop-guard: sliding-window exact/fuzzy repeats and A→B→C→A cycles, plus "output stops changing"; trade-off is exact matching (cheap, misses rephrased retries) vs fuzzy (catches more, false positives) — [PyPI](https://pypi.org/project/agent-loop-guard/)
- Wink (10,000+ real trajectories): asynchronous monitor detects specification drift, reasoning problems, tool-call failures and injects course correction; resolves 90% of misbehaviours that need a single intervention; agents most often recovered from infinite loops (39%); course-correction most effective on tool-call failures; no independent replication — [arXiv 2602.17037](https://arxiv.org/abs/2602.17037)
- "When to Intervene?" (ReInBench: 1,259 traces, 1,403 error events): 725 error events self-recover, often within a few steps; intervention should "prioritize errors unlikely to self-recover" — [arXiv 2610.36471](https://arxiv.org/abs/2610.36471)
- "Failure as a Process": agents should "reconsider a diagnosis once a repair attempt runs well past typical successful recovery" — [arXiv 2607.09510](https://arxiv.org/abs/2607.09510)
- Claude Code auto mode falls back to asking after three classifier blocks in a row or twenty total; in `-p` runs "repeated blocks don't pause the run"; Stop-hook block cap: after eight blocked stops in a row with no tool call between, Claude Code overrides the block (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises it) — [best practices](https://code.claude.com/docs/en/best-practices)
- Claude Code hooks mechanics: exit 2 = blocking error ("On events that can block, Claude Code stops the action"); exit 1 without JSON is non-blocking; `PreToolUse` `permissionDecision` allow/deny/ask/defer with `updatedInput`; "staying silent doesn't approve it"; a timed-out PreToolUse hook "doesn't block the tool call ... so don't count on a stalled hook to act as a gate" unless `"onFailure": "block"` (v2.1.295+); `PostToolUse` cannot block ("the tool already ran"); Stop `decision: "block"` with `reason` — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- Agent SDK hooks (programmatic, the surface Neo would use): events include PreToolUse, PostToolUse, PostToolUseFailure, PostToolBatch, Stop, StopFailure, SubagentStart/Stop, PreCompact/PostCompact, PermissionRequest/Denied, TaskCreated/TaskCompleted ("Require passing tests before a task closes"), SessionStart/End (TS only), Notification; multiple PreToolUse hooks run in parallel and "the most restrictive result applies" (deny > defer > ask > allow); `updatedInput` can rewrite arguments (e.g., redirect paths to a sandbox); on PreToolUse timeout "Claude Code blocks the tool call"; on Stop timeout the callback counts as no decision; "Hooks may not fire when the agent hits the `max_turns` limit"; a `Write|Edit` matcher does not catch Bash writes to the same file ("To block Bash writes ... see the sandbox configuration") — [Agent SDK hooks](https://code.claude.com/docs/en/agent-sdk/hooks)
- Permission rules: `deny` rules "hold in every permission mode, including auto and `bypassPermissions`"; `Read` deny catches `cat .env` but "won't catch a script that opens the file"; a `WebFetch` deny "does nothing about `curl` to that same domain, unless the sandbox is on"; "for anything security-related you want both" — [best practices](https://code.claude.com/docs/en/best-practices)
- Recovery after interruption: `resume` with a higher limit after `error_max_turns`/`error_max_budget_usd`; session id present on every result message; file checkpointing is separate from session history — [Agent SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions)
- Idempotency: every mutating tool call should carry a harness-generated key tied to the attempted action (not the arguments), so retries return the first result; "Unknown outcomes are the hard case" (a timeout can hide a success; reconcile before another side effect); keys need expiry; compensation for non-idempotent actions; one preprint on verified tool wrappers states "idempotency keys provide stronger guarantees, while verification provides best effort protection" (practitioner posts + one preprint; evidence thin) — [DEV post](https://dev.to/aiexplore369zoho/ai-agent-tool-calls-need-idempotency-keys-not-retry-loops-4hc2); [arXiv 2608.02645](https://arxiv.org/html/2608.02645v1); [AWS agentic-AI lens](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentrel06-bp04.html)
- Trajectory diagnostics: TraceProbe flags "search loops and verification skips" from a nine-type action taxonomy with deterministic labels; CONVERGE compares run pairs for divergence — [arXiv 2607.06184](https://arxiv.org/abs/2607.06184)
- Tool design (ACI): "requiring absolute file paths removed a class of errors"; poka-yoke tool design — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

### Inferences
- Minimal engine spin detector: hash (tool, args) per call; reminder via `additionalContext` at 4–5 identical, hard stop at ~8 identical-and-failing; separately watch for unchanged file state / unchanged test output across N edits (semantic stall), and a time/turn cap (`maxTurns`, budget) as the backstop.
- Retry ladder for the engine itself (API rate limit, transient tool failure) is orthogonal to the model's own retries; the engine should distinguish "model keeps retrying the same thing" (spin → intervene) from "environment failed" (retry with backoff).
- Any external, non-idempotent action (push, PR comment, email, Telegram send) should be wrapped by the engine with an idempotency key stored in the ledger before the call, and reconciled on restart.
- Fail-closed hooks (`onFailure: block`) and sandbox + deny rules together, not either alone, are what make a "never" rule real.

### Gaps
- No peer-reviewed study of retry ladders or idempotency practices for coding agents specifically; durable-execution engines (event-sourced replay) for agents not found.
- Wink's live A/B numbers (Table 5) not retrievable.

## 7. Model and effort routing: cheap triage, strong implementation, thinking budgets; cost/quality trade-offs

### Takeaway
Measured results show diminishing returns from extra thinking on SE benchmarks (+0.3 pp when doubling to a 30M budget on SWE-Bench Pro; low-effort o4-mini matched high-effort Opus 4.1 on a 50-task SWE-bench subset at 1/6 the cost), and a production router cut median cost 64% with no measurable quality change; but routing only pays when the cheap tier's pass rate under the *same verification gate* beats the cost ratio, and "almost right" cheap outputs can cost more via rework. Routing is engine-enforceable; the gate it depends on is §1.

### Cited Findings
- "How Inference Compute Shapes Frontier LLM Evaluation": for the two SE benchmarks "extending further yields only limited improvement"; on SWE-Bench Pro, near-doubling the budget to a 30M cap adds only +0.3 ± 0.3 pp across models — [arXiv 2606.17930](https://arxiv.org/pdf/2606.17930)
- Holistic Agent Leaderboard (SWE-bench Verified Mini, 50 tasks): o4-mini low effort 54.0% at $259.20; Claude Opus 4.1 high effort 54.0% at $1,599.90; GPT-5 medium 46.0% at $162.93; only o4-mini-low and GPT-5-medium Pareto-optimal — [arXiv 2510.11977](https://arxiv.org/pdf/2510.11977)
- Claude Code guidance: effort "replaces most of what people used to do with prompt wording"; default `medium`; raise to `high`/`xhigh` for bugs in unfamiliar code, flaky tests, schema changes; `max` "tends to overthink" on ordinary tasks; Haiku "a good fit for subagents doing simple jobs"; "think hard / be thorough" phrases are retired as advice — [best practices](https://code.claude.com/docs/en/best-practices) (ENGINE: effort/model are per-request parameters)
- LangChain Open SWE router: median cost per thread down 64% vs always-frontier "with no measurable change in quality" (single company, first-party) — [LangChain blog](https://www.langchain.com/blog/how-to-build-a-model-router-in-the-harness)
- Triage (routing SE tasks by code-health signals): send each task to the cheapest tier that passes the same verification gate; cost-effective only if the cheap tier's pass rate on healthy code exceeds the tier cost ratio and code health separates tiers by at least a small effect size — [arXiv 2604.07494](https://arxiv.org/html/2604.07494v1)
- RouteLLM: ~95% of GPT-4 quality while sending 14–26% of calls to the strong model (secondary summary of the framework's claims); calibrate thresholds on your own query sample — [RouteLLM](https://github.com/lm-sys/routellm)
- Counter-evidence: a small local test where the router escalated 14/30 tasks and matched the cheap model's accuracy exactly at higher cost; analysis that "almost right" cheap output triggers retries/rework costing more than one frontier call — [DEV post](https://dev.to/priyansh_singhal_5975e7d3/my-llm-router-spent-8x-more-and-matched-the-cheap-model-exactly-18d9); [Unblocked analysis](https://getunblocked.com/blog/model-routing-coding-agents/)
- Beyond Resolution Rates: "the LLM matters more than the framework"; framework prompt influence diminishes with stronger LLMs — [arXiv 2604.02547](https://www.alphaxiv.org/overview/2604.02547v1)
- Anthropic: Opus lead + Sonnet subagents beat single Opus by 90.2% on research evals (model-tier split by role) — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- Subagent cost caveat: "a fresh subagent first has to gather context your conversation already had, so it can end up *slower*"; "Handing the same task to a subagent doesn't make the answer any better" — [best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- Measure **cost per verified-solved task** (including retries and escalations), not per-token price; the verification gate (§1) must be identical across tiers or routing data is meaningless.
- Reasonable default for Neo: strong model + medium effort for implementation; cheap model (Haiku-class) for read-only subtasks (search, link checks, summarising test output), and for the "triage" step that classifies an order's risk/size; escalate effort only on signals (test flakiness, schema migrations, unfamiliar code), which the engine can detect from the diff and from failed verification attempts.
- Extended thinking beyond medium is a poor lever for SE pass rate at scale; spend tokens on sampling+verification or on review instead.

### Gaps
- No public, controlled study of a cheap-triage/strong-implement pipeline on real repos; LangChain's result is the only first-party production number found.

## 8. Published research and reports 2025–2026 (METR, SWE-bench analyses, vendor posts, failure taxonomies)

### Takeaway
The 2025–26 literature converges on: failures are mostly epistemic and early (wrong beliefs, unverified assumptions), benchmarks overstate capability (broken tasks, leakage, weak tests), reliability is a property of the system around the model, and human-measured productivity effects are small/uncertain even as self-reports and capability horizons climb.

### Cited Findings
- METR time-horizon: original 2025 finding that the 50%-reliability task length doubled ~every 7 months since 2019; Time Horizon 1.1 (Jan 2026) expanded the suite (170 → 228 tasks; long tasks 14 → 31) without changing the slope; secondary/forecast sources put frontier 50% horizons around 12 hours by Apr 2026 with a ~4-month doubling, and note the 80% horizon is "considerably shorter" (no primary 2026 METR page retrievable) — [aiwiki summary](https://www.aiwiki.ai/wiki/metr_time_horizon/raw); [Substack analysis](https://buttondown.com/anatol/archive/are-ai-time-horizons-still-doubling/); [Manifold](https://manifold.markets/Bayesian/what-will-be-the-metr-time-horizon)
- METR developer RCT (2025): 16 experienced OSS devs, 246 tasks, 19% slower with AI while believing 20% faster; 2026 follow-up (57 devs, 143 repos, 800+ tasks): 10 returning devs +18% speedup (interval reported as 38% slower to 9% faster, which looks inconsistent with the point estimate and should be checked against METR), 47 new devs −4% (interval −15% to +9%); METR called the signal unreliable because the no-AI control broke down (devs reluctant to work without AI, held back tasks); separate METR survey (349 technical workers, Feb–Apr 2026) median self-reported 3× speedup, only ~¼ software engineers — [andrewwegner.com](https://andrewwegner.com/metr-ai-productivity-study-update.html); [DEV summary](https://dev.to/gabrielanhaia/metrs-ai-coding-speed-study-broke-too-many-developers-wouldnt-work-without-ai-5afm); [ingenire](https://ingenire.com/blog/metr-2026-developer-productivity-study)
- "Engineering Reliable Coding Agents" (314-page monograph, 206 reliability records, runnable protocols): "coding agents are judged as models but run as systems"; "many apparent model failures originate elsewhere in the system"; reliability is "a property of the system that preserves intent, authority" etc.; a score can move "because the model improved or because the harness changed" — [arXiv 2608.13867](https://arxiv.org/abs/2608.13867)
- "Exploring Autonomous Agents: Why They Fail": three-tier taxonomy, 19 causes across planning/execution/response, including environment setup (missing deps) and loops of failed self-correction exhausting attempt limits — [arXiv 2508.13143](https://arxiv.org/abs/2508.13143)
- XAI for coding-agent failures: taxonomy from 32 real failures; automatic classifier 82% accuracy; taxonomy does not transfer to other domains — [arXiv 2603.05941](https://arxiv.org/pdf/2603.05941)
- MAST (multi-agent): 14 failure modes from 1,642 traces across 5 frameworks; Terminal-Bench adapted it for single agents — [arXiv 2503.13657](https://arxiv.org/abs/2503.13657); [Terminal-Bench](https://proceedings.iclr.cc/paper_files/paper/2026/file/444a3737adaee10d86ad2ef5f74468e6-Paper-Conference.pdf)
- SWE-Bench Pro paper: GPT-5 as judge on unresolved trajectories (87% agreement with humans); "wrong solution" and "incorrect file" among the common buckets — [arXiv 2509.16941](https://arxiv.org/pdf/2509.16941); DeepSWE qualitative analysis of 30 SWE-Bench Pro tasks — [arXiv 2607.07946](https://arxiv.org/pdf/2607.07946)
- Agentic PRs in the wild (AIDev dataset, 33,596 PRs): merge rates Codex 82.6%, Cursor ~65%, Claude Code ~59% (n=459), Devin ~54%, Copilot 43%; Claude vs Codex gap not statistically significant in a larger analysis; merge conflicts Codex 32.3%, Claude Code ~26%, Copilot ~15%; Jellyfish 100M-PR report: 28% of merged PRs involved AI agents, 0.5% AI-only review — [arXiv 2607.21832](https://arxiv.org/pdf/2607.21832); [arXiv 2604.03551](https://arxiv.org/html/2604.03551v2); [devops.com](https://devops.com/report-claude-code-exceeds-github-copilot-for-merging-pull-requests)
- "Where Do AI Coding Agents Fail?" (MSR 2026, ~33k PRs, 600 coded): overall merge 71.48%; blockers: lack of reviewer engagement 38%, duplication 23%, CI/test failures 17%; each failed CI check reduces merge odds ~15%; agent-level issues ~2% — [arXiv 2601.15195](https://arxiv.org/html/2601.15195). Rejected-fix study: 46.41% of agent fix PRs rejected (incorrect implementation, CI failures, incomplete work, low priority) — [arXiv 2606.13468](https://arxiv.org/pdf/2606.13468). Microsoft: agents lift PR volume 24% but "measured merged pull requests, not software quality" — [TechRepublic](https://www.techrepublic.com/article/news-ai-coding-agents-microsoft-pull-requests/)

### Inferences
- For Neo, the most defensible reading: treat benchmark deltas with suspicion, instrument the engine's own ledger (verification outcomes, turns, cost per verified task, intervention counts) as the real signal, and expect that harness components become unnecessary model-by-model (Anthropic dropped resets after Opus 4.5 and sprints after 4.6) — so each gate should be a config flag with a measured reason to exist.
- Merge-rate data says the dominant blocker on real PRs is *human engagement and CI*, not agent-level error, so engine-side CI-equivalent gates before a PR is opened directly raise merge odds (~15% per avoided failed check).
