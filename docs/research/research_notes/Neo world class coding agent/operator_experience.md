## 1. Attention economics: silence rules, priority channels, digests, interruption budgets

### Takeaway
Everything that transfers from on-call practice says the same thing: a message that reaches the operator must be (a) actionable by a human, (b) urgent enough to justify the interruption, and (c) otherwise batched into a digest or logged silently. The evidence for the cost of interruptions is solid (resumption lag, stress), and the evidence that "most alerts are not actionable" is consistent across surveys. Products shipping in 2026 (Claude Tag routines, Claude Code Remote Control push) have converged on "post only on change / only when a person must act", with user-chosen toggles for "when Claude decides" vs "when action required".

### Cited Findings
- **Google SRE "Monitoring Distributed Systems" (Ch. 6) sorts every monitoring output into three tiers: page (act now), ticket (act eventually), log (no action; diagnostics only); paging should key off user-visible symptoms that are urgent and actionable.** [secondary summary of the SRE book — primary unreachable] — [SoundCloud "Alerting on SLOs like Pros"](https://developers.soundcloud.com/blog/alerting-on-slos); [Rabenstein SREcon16 slides](https://www.usenix.net/sites/default/files/conference/protected-files/srecon16europe_slides_rabenstein.pdf); [SRE book notes](https://bitmaybewise.substack.com/p/sre-book-notes-monitoring-distributed)
- The page-worthiness test paraphrased from the book: does the rule detect an otherwise-undetected condition that is urgent, actionable and actively/imminently user-visible? [secondary] — [KodeKloud notes](https://notes.kodekloud.com/docs/Fundamentals-of-SRE/Incident-Management/Designing-Effective-Alerts/page)
- **NeuBird AI survey of 1,039 SRE/ops professionals (Feb 2026): 77% of on-call teams receive ≥10 alerts/day; 57% report that fewer than 30% of those alerts are actionable; ~40% of orgs report >25% of on-call engineers showing burnout symptoms.** [vendor survey, not peer-reviewed] — [NeuBird](https://neubird.ai/glossary/alert-fatigue) via [BusinessWire](https://www.businesswire.com/news/home/20260406439955/en)
- PagerDuty "State of IT Work-Life Balance" (800+ IT pros): 94% said alert interruptions affect family life, 94.5% said they hurt productivity; 51.3% are interrupted >10 times/week. - VictorOps 2015 State of On-Call (600+ respondents): alert fatigue is the #1 pain point; 70% said it was a problem in their org. [vendor survey] — [via PagerDuty/ITWorldCanada search results](https://itworldcanada.com/?p=379536)

### Inferences
- Map the SRE three-tier model directly onto Neo's channel: **page** = a decision or a failure only Neo can resolve (push, Telegram message with buttons); **ticket** = results Neo can use but need not act on now (batched into a digest / status board, delivered at Neo's chosen times); **log** = everything else (trace spine, `/trace`, web console only). The "page" tier should be allowed to interrupt; the other two should never notify.
- The "speak only when a person must act or can use a result" rule is well supported by the Horvitz expected-value framing and by the on-call survey data showing that most alerts are not actionable; add a per-day interruption budget (e.g. N pages/day, after which further pages are downgraded to digest unless tagged critical) — this is an inference from the SLO-paging idea, not a documented product feature.
- Batching improves *throughput* (Mark 2016, Claude Tag "batch your reviews") but should not be sold as a stress reducer; the stress lever is reducing *total* time spent on the channel, i.e. shorter messages and fewer of them.
- The two-toggle model in Remote Control ("when Claude decides" / "when action required") is a good minimal notification policy; add a "presence" suppression (don't push while the operator is active in the web console).
- Every scheduled/loop output should have an explicit "nothing changed → say nothing" branch, like Claude Tag's "Skip 🟢 unless something changed".

### Gaps
- No peer-reviewed study specifically on operator attention when supervising *multiple coding agents*; evidence is transferred from on-call alerting and office interruption research.
- Could not open the SRE book primary text or Horvitz's CHI'99 PDF to quote exact wording.
- No published numbers on an "interruption budget" for agent operators; the budget idea is an inference from SLO-based paging.

## 2. Decisions: asking a human one well-formed question at a time, queues, reminders, expiry, answering from any channel

### Takeaway
Product docs and HITL guidance converge on: present the *decision*, not the transcript (what will happen, to whom, why the agent thinks it's right, the options with trade-offs); make the default on timeout fail-safe (deny/expire, never auto-proceed); give pending items a visible queue and an owner; and keep the operator's declared "decisions that come back to me" list explicit. Products differ on expiry: Claude Code keeps permission prompts open indefinitely but closes other dialogs after 5 minutes; Dispatch-spawned sessions expire app approvals after 30 minutes; Permit.io defaults to 5-minute auto-reject.

### Cited Findings
- **Claude Tag "Say which decisions come back to you": "Tell Claude which decisions it can make on its own and which ones it must bring to you before acting. If you don't, Claude judges each case itself. It may make a change you wanted to see first, or stop to ask so often that it spends most of the task waiting for your replies."** Example brief: "Handle test failures and lint yourself. Come back to me before changing any public interface, and for anything you're not sure is in scope." [vendor doc] — [Good habits](https://claude.com/docs/claude-tag/users/good-habits)
- **Claude Tag end-condition table — who closes a task: "An objective check passes → Claude, on its own ('Done when CI is green')"; "You approve a prepared result → You, one click"; "You choose between options → You, one word ('Research approaches A and B and recommend one')"; "No verifiable condition exists → No one; reframe it as a question."** "Starting a thread costs one sentence. Closing it costs your attention." [vendor doc] — [Good habits](https://claude.com/docs/claude-tag/users/good-habits)
- HITL design guidance (Claude skill, practitioner): show "the decision itself, not the full transcript, including what will happen, to whom, and why the agent thinks it's right"; use "a safe-by-default timeout that expires rather than auto-proceeding". [practitioner] — [human-in-the-loop-design SKILL.md](https://claudskills.com/skills/human-in-the-loop-design/SKILL.md)
- "You need a default that fires when nobody answers, and the default has to be deny." [practitioner] — [dev.to, Anhaia](https://dev.to/gabrielanhaia/human-in-the-loop-approval-gates-where-to-pause-an-autonomous-agent-2kh2)
- Permit.io MCP gateway: "default timeout: 5 minutes — if no admin responds, the request is automatically rejected", with a countdown and an extend option near expiry. [vendor doc] — [Permit.io HITL](https://docs.permit.io/permit-mcp-gateway/human-in-the-loop)
- AWS Well-Architected Agentic AI Lens flags "approval workflows without timeout policies or escalation paths, so agent execution stalls indefinitely when reviewers are unavailable" as an anti-pattern. [vendor doc] — [AWS AGENTSEC04-BP02](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec04-bp02.html)
- "The approval queue nobody drains": decide the terminal state for an expired item per action type up front; hand expired items to a normal human work queue; "a queue with no owner or alert becomes a black hole". [practitioner] — [tianpan.co](https://tianpan.co/blog/2026/05/17/approval-queue-nobody-drains)
- Mastra: "in a chat interface, the approval should feel like a message from the agent. In a dashboard, it might be a modal or an approval queue... if approvals can stack up, you need a way to list and manage them." [vendor blog] — [Mastra](https://mastra.ai/blog/human-in-the-loop-when-to-use-agent-approval)
- **Claude Code Remote Control: "Claude Code keeps permission prompts and `AskUserQuestion` questions open until you answer them." Other forwarded dialogs wait five minutes then "close the dialog and continue with the dialog's no-action default" (`dialogExpiry` setting).** [vendor doc] — [Remote Control](https://code.claude.com/docs/en/remote-control)
- Claude Code Desktop Dispatch: "App approvals in these sessions expire after 30 minutes and re-prompt. Approvals in regular Code sessions last for the full session." Push notifications "cover completion and approval requests". [vendor doc] — [Desktop docs](https://code.claude.com/docs/en/desktop)
- **Claude Code channels: a channel server that declares the permission-relay capability can forward permission prompts so you approve/deny remotely; "Anyone who can reply through the channel can approve or deny tool use in your session, so only allowlist senders you trust with that authority." In `-p` (non-interactive) mode, "tools that need terminal input, such as multiple-choice questions and plan mode approval, are disabled so the session never stalls waiting for input."** [vendor doc] — [Channels](https://code.claude.com/docs/en/channels)
- Claude Code permission prompts distinguish scoped grants in the prompt itself: "Yes, and keep allowing..." (recorded, won't ask again) vs "Yes, but ask again next time" (nothing saved); some prompts offer "for this session" scope. [vendor doc] — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Devin batch sessions: "Devin analyzes your request and proposes the sessions for your approval before launching them." [vendor doc, secondary — docs.devin.ai unreachable] — [Devin advanced capabilities](https://docs.devin.ai/work-with-devin/advanced-capabilities)
- Claude Code `AskUserQuestion` and MCP tools marked `requiresUserInteraction` are never auto-approved by any permission mode, including `bypassPermissions`. [vendor doc] — [Permission modes](https://code.claude.com/docs/en/permission-modes)

### Inferences
- A Neo decision card should carry: project + task id, one-sentence context, 2–4 options each with a trade-off line, the worker's recommendation, the *default that applies on timeout* (spelled out), and the expiry. Inline buttons for the options; free-text reply as the escape hatch.
- "First answer wins" across channels (Telegram vs web console) is not documented by any product I found, but Claude Code Remote Control's "conversation stays in sync across all connected devices... send messages from your terminal, browser, and phone interchangeably" is the nearest precedent; implement by binding every decision to an id and accepting the first resolution from any channel, then editing the other surfaces to show "answered via Telegram".
- Expiry defaults should differ by action class (as tianpan argues): read-only/in-folder → short expiry then proceed with the worker's recommendation only if pre-approved; anything irreversible/out-of-folder → deny on expiry (Neo already does this per ADR-0012). Decisions that merely pick a direction (plan A/B) can stay open indefinitely like Claude Code's permission prompts, with reminders.
- Keep a single "needs me now" queue (one item per message, oldest-first, with a count badge) rather than scattering questions across project threads — the HITL sources agree that stacked approvals need a list view.

### Gaps
- No empirical study comparing one-question-at-a-time vs batched questions for agent operators.
- Could not confirm Devin's or Codex's exact Slack approval/expiry behaviour from primary docs.

## 3. Trust and autonomy levels: graduated autonomy, scoped grants, earned trust, kill switches, undo; automation bias

### Takeaway
The human-factors literature is unambiguous that automation bias and complacency occur in experts as well as novices, cannot be trained away, and worsen with constant-reliability automation under multitask load — so a fleet operator should expect to under-check reliable workers and should design the system (not the prompt) to force verification where it matters. Products implement graduated autonomy as explicit modes (Claude Code: default → acceptEdits → plan → auto → dontAsk → bypass) plus a hard floor of actions no mode auto-approves; and they all state that prompt-level constraints "steer but don't restrict" — only external controls (branch protection, hooks, permission rules) are enforcement. Earned trust is framed as something the operator *widens* after seeing output hold up, not something the system auto-applies.

### Cited Findings
- **Parasuraman & Manzey (Human Factors, 2010, "Complacency and Bias in Human Use of Automation: An Attentional Integration"): complacency appears under multiple-task load when manual tasks compete with the automated one for attention; it "is found in both naive and expert participants and cannot be overcome with simple practice"; automation bias produces omission and commission errors with imperfect aids, "occurs in both naive and expert participants and cannot be prevented by training or instructions".** [research] — [TRID abstract](https://trid.trb.org/View/1085175); [TU Berlin repository](https://depositonce.tu-berlin.de/handle/11303/8923)
- Parasuraman (1993): detection of automation failures was substantially worse for constant-reliability than variable-reliability automation after ~20 minutes; when monitoring was the only task, detection was efficient regardless of reliability. [research, via NASA NTRS listing] — [NTRS](https://ntrs.nasa.gov/citations/19930055574)
- **Lee & See (2004): trust should be *calibrated* to the automation's true capability; designers should aim for "appropriate" rather than "greater" trust; over-trust → misuse, under-trust → disuse; system feedback plays a particularly powerful role in calibration.** [research, via systematic reviews] — [Systematic review on appropriate trust (arXiv 2311.06305)](https://arxiv.org/pdf/2311.06305); [Frontiers 2021](https://www.frontiersin.org/journals/robotics-and-ai/articles/10.3389/frobt.2021.652776/pdf)
- Goddard, Roudsari & Wyatt (JAMIA 2012) systematic review of automation bias in clinical decision support (74 studies): mediated by cognitive style, experience, trust and confidence; mitigation "by altering advice characteristics to aid clinicians' awareness of advice correctness and support their own informed judgement" — but the mitigation evidence base is thin. [research] — [JAMIA](https://academic.oup.com/jamia/article/19/1/121/732254); [PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC3240751)
- 2025 literature on LLM coding assistants: a 131-professional interview study lists "overreliance on LLMs, reduced critical thinking" as top concerns; an observational study of 14 developers found "Instant Gratification" and "Suggester Preference" biases most frequently affect LLM-related actions (19.3% and 12.6%); a 2026 thesis found LLM tools reduced coding time but *increased verification time*, with developers "actively managing" the risk. [research, small samples] — [arXiv 2510.09058](https://arxiv.org/pdf/2510.09058); [arXiv 2601.08045](https://www.arxiv.org/pdf/2601.08045); [LUT thesis](https://lutpub.lut.fi/handle/10024/172524)
- **Claude Code permission modes (graduated autonomy): `default` (reads only), `acceptEdits` (reads + file edits + mkdir/touch/mv/cp), `plan` (reads + classifier-approved commands), `auto` ("everything, with background safety checks"), `dontAsk` (pre-approved tools only; anything that would prompt is denied — "locked-down CI and scripts"), `bypassPermissions` ("isolated containers and VMs only"). Deny rules apply in every mode including bypass; allow rules have no effect in bypass.** [vendor doc] — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- **Actions *no* mode auto-approves: explicit ask rules, connector tools set to `ask`, `AskUserQuestion`/`requiresUserInteraction` tools, recognised `rm`/`rmdir` critical-path removals, cross-session messaging safeguards, reads/writes outside working directories when the block settings are on. Writes to protected paths (`.git`, `.claude`, `.bashrc`, `.mcp.json`) are never auto-approved outside bypass.** [vendor doc] — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- **Auto mode: "A separate classifier model reviews actions before they run, blocking anything that escalates beyond your request, targets unrecognized infrastructure, or appears driven by hostile content Claude read." Blocked by default: `curl | bash`, sending sensitive data externally, production deploys/migrations, force push, `git reset --hard`, `git clean -fd`, `terraform destroy`, merging unapproved PRs, irreversible deletion of pre-existing files. Allowed by default: in-directory file ops, installing from lockfiles, reading `.env` and sending creds to their matching API, read-only HTTP, pushing to non-deploy branches. Stated boundaries ("don't push") are enforced by the classifier; stated approvals clear a block only when the specific action is named. Circuit breaker: "if the classifier blocks an action 3 times in a row or 20 times total, auto mode pauses and Claude Code resumes prompting." On entering auto mode, blanket allow rules (`Bash(*)`, `Bash(python*)`, package-manager run, `Agent`) are dropped and restored on exit.** [vendor doc] — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Anthropic reportedly made Auto Mode the default for Claude Code on Pro/Max/Team from 2026-08-14. [secondary, unverified] — [Foundra](https://www.foundra.ai/key-reads/the-solo-founder-agent-stack-what-s-actually-working-in-2026)
- **Claude Tag on earned trust: "Calibrate over time. Check everything it produces in a new channel at first, and widen what it closes on its own as its output holds up under review." And: "Once you've seen and verified Claude's output over several tasks, you can let it make more decisions without checking in."** [vendor doc] — [Good habits](https://claude.com/docs/claude-tag/users/good-habits)
- **Claude Tag on enforcement vs steering (two warnings): "Constraints in a task steer Claude but don't restrict Claude from performing a specific action. Anything you type to Claude goes into its working context, where it can be forgotten or overridden. If there are actions Claude must not take, enforce them outside the conversation, with controls like repository permissions, branch protection rules, and required checks." And "A decision that must come back to you needs an enforced control too, such as branch protection for merges." "A CLAUDE.md is guidance; a required status check is a gate."** [vendor doc] — [Good habits](https://claude.com/docs/claude-tag/users/good-habits)
- Claude Code memory docs make the same point: CLAUDE.md and auto memory are "context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." [vendor doc] — [Memory](https://code.claude.com/docs/en/memory)
- **Undo: Claude Code checkpoints snapshot files before every prompt (100 most recent per session); `/rewind` offers "Restore code and conversation / Restore conversation / Restore code / Summarize"; limits: Bash-only file changes are not tracked, subagent edits usually are not restored, external changes not tracked; "Not a replacement for version control."** [vendor doc] — [Checkpointing](https://code.claude.com/docs/en/checkpointing)
- Kill switch from phone: Remote Control shows running subagents/workflows on the device; "Stop one of them from the device, and Claude Code stops that task on your machine." Claude Tag: "To interrupt Claude in a channel thread, select Stop on the indicator." Devin Slack keywords: `sleep` (wake by any message), `mute`, `archive`, `EXIT`. [vendor doc; Devin via secondary] — [Remote Control](https://code.claude.com/docs/en/remote-control); [Claude Tag getting started](https://claude.com/docs/claude-tag/users/getting-started); [Devin Slack docs](https://docs.devin.ai/integrations/slack)
- GitHub Copilot coding agent: "draft pull requests created by the agent require human review before merging"; Copilot code review has an admin toggle "Allow Copilot to approve pull requests", off by default; an approval assessment "does not count as an approving review". [vendor doc + secondary] — [GitHub configure code review](https://docs.github.com/en/copilot/how-tos/copilot-on-github/set-up-copilot/configure-code-review); [c-sharpcorner](https://www.c-sharpcorner.com/article/can-github-copilot-approve-a-pull-request)
- Solo-founder field guide (agent-007 repo, Oct 2026): "AI reports success confidently" — verify results yourself; keep "pricing, refunds, legal matters and anything public in your name" as human decisions ("edit and sign"); "put a spending cap on every usage-billed service"; keep all accounts in your own name. [practitioner] — [SOLO-FOUNDER-GUIDE.md](https://raw.githubusercontent.com/bill10/agent-007/main/docs/SOLO-FOUNDER-GUIDE.md)

Codex code review "flags high-priority issues" and can start follow-up cloud tasks to fix them. [vendor doc, secondary — developers.openai.com unreachable] — [OpenAI Codex GA](https://openai.com/index/codex-now-generally-available); [Codex Slack](https://developers.openai.com/codex/integrations/slack)

### Inferences
- Because complacency is *attentional* and worsens with reliable automation under multitask load, a one-person fleet is the worst case: Neo will be multitasking across projects and the workers will be reliable most of the time. Design for it: (1) never let "trusted" collapse the evidence card — keep what-changed / what-ran / risk lines even for auto-approved work; (2) occasionally require an explicit confirmation on a *sample* of routine work (variable-reliability effect) rather than making every grant permanent; (3) show the worker's self-assessed confidence and the verification that actually ran, since Goddard's mitigation lever is "awareness of advice correctness".
- Graduated autonomy should be a per-project, per-action-class ladder (observe → propose → act-with-report → act-silently), with grants scoped "once / this task / this project / always" as Claude Code's prompt options already model. Earned trust should be *offered* ("this has been approved 12 times without change — make it standing?") and never auto-applied — consistent with Claude Tag's "widen what it closes on its own" and Lee & See's calibration framing.
- Keep a hard floor of never-auto-approved actions (irreversible deletes, force push, deploys, merges, out-of-fence writes, spending) in code, as Claude Code does; make the auto-mode circuit breaker pattern (N blocks → drop to prompting) part of the governor.
- Undo must be two-layered: session checkpoints for quick rewind, git for anything a Bash command or subagent touched.

### Gaps
- No controlled experiment measuring automation bias in developers supervising *autonomous coding agents* (as opposed to inline suggestions); the LLM-era studies are small (n=14) or self-report.
- Could not verify the claim that Auto Mode became default on 2026-08-14 from Anthropic's own pages.

## 4. Reporting: honest status, evidence cards, one-sentence results, edit-in-place vs new messages, "what needs me now" first

### Takeaway
The shipped pattern (Claude Tag, Linear) is: acknowledge immediately, keep one checklist message updated in place while working, post one result with attached proof, and let the operator "read the proof, not the transcript". The review-side data is sobering: AI-authored PRs wait far longer for first review and are merged far less often, a large share get no human review at all, and reviewers report fatigue from oversized diffs — so reports must be sized for a phone and link out to evidence rather than inline it.

### Cited Findings
- **Claude Tag: "A working indicator appears at the bottom of the thread when Claude picks the task up... a multi-step task also gets a checklist it updates as it works. A quiet thread under the indicator means Claude is working, not stuck." Example: "Done: Pulled p99 latency from Datadog / Done: Diffed deploy 4f2c1 against main / Done: Reproduced the slow query locally / In progress: Opening a pull request with the fix…"** [vendor doc] — [Claude Tag overview](https://claude.com/docs/claude-tag/overview); [Getting started](https://claude.com/docs/claude-tag/users/getting-started)
- **"For tasks Claude closes itself, ask it to attach proof, such as the source link, the chart, the test output, or the diff. You read the proof, not the transcript."** "Read Claude's work before you use it, in proportion to what's at stake. A summary you can skim; something going to a customer or changing a system gets a careful read." [vendor doc] — [Good habits](https://claude.com/docs/claude-tag/users/good-habits); [Getting started](https://claude.com/docs/claude-tag/users/getting-started)
- Claude Tag recurring output: "Name the output format in the job so recurring posts stay scannable"; "Say how long each item should be, give it the status legend to use, and tell it what to leave out"; "use the format from your 9am post going forward." [vendor doc] — [Routines](https://claude.com/docs/claude-tag/users/proactivity); [Good habits](https://claude.com/docs/claude-tag/users/good-habits)
- Linear AIG: agents report progress by emitting activities of type thought, action, clarification prompt, final response, or error; Linear infers session state from the last activity; an "Agent Session" view shows every step; issues are "assigned to humans and delegated to agents, since an agent cannot be held accountable". [vendor doc, secondary] — [Linear AIG](https://linear.app/developers/aig); [Linear agent best practices](https://linear.app/developers/agent-best-practices)
- Claude Code Desktop: OS notification "when any Code session finishes while you're viewing a different session"; Claude projects have a "see what needs you in overview" view. [vendor doc] — [Desktop docs](https://code.claude.com/docs/en/desktop)
- **LinearB 2026 Software Engineering Benchmarks (8.1M PRs, 4,813 teams): acceptance (merged within 30 days) 84.4% for manual PRs vs 32.7% for AI PRs; agentic PR pickup time 1,055 min vs 201 min unassisted (~5.3×; other write-ups say 4.6×); heavy-AI teams merged 98% more PRs while review time climbed 91%; developers "feel 20% faster but are 19% slower" end-to-end.** [vendor research; figures vary across write-ups] — [LinearB benchmarks](https://linearb.io/library/engineering-benchmarks-and-research); [LinearB AI productivity gap](https://linearb.io/resources/ai-engineering-productivity-gap); [byteiota summary](https://byteiota.com/ai-prs-wait-4-6x-longer-linearb-2026-benchmarks/)

[research, secondary — paper not opened] — [via pengupress summary](https://pengupress.duckdns.org/articles/ai-code-review-agents-scale/)
- Qodo State of AI Code Quality (500 US devs, Aug 2026): 25.8% name review/validation as the main delivery constraint; 19% say PRs are "much larger and harder to parse, leading to review fatigue". [vendor survey] — [Qodo](https://www.qodo.ai/?p=22526)
- Graphite: GT MCP "allows AI agents to automatically create stacked PRs, breaking down large AI-generated changes into smaller, reviewable stacked pull requests"; Graphite admits AI "sometimes struggles with very large or monolithic diffs"; GitHub reportedly in private preview for native stacked PRs in 2026. [vendor marketing + secondary] — [Graphite gt-mcp](https://graphite.com/docs/gt-mcp); [dev.to comparison](https://dev.to/pyor/github-pr-review-alternatives-in-2026-an-honest-comparison-4m0h)
- Solo-founder guide: "Skim each pull request's summary and screenshots. You don't need to read the code"; "before every release, click through the product as a customer would"; keep a one-page "it works when…" checklist. [practitioner] — [SOLO-FOUNDER-GUIDE.md](https://raw.githubusercontent.com/bill10/agent-007/main/docs/SOLO-FOUNDER-GUIDE.md)
- Telegram text message limit is 4096 characters (captions 1024); inline keyboards up to 100 buttons, 8 per row, markup ≤10 KB; only an inline keyboard can be attached to an edited message. [secondary — core.telegram.org unreachable] — [Telegram limits (tginfo)](https://limits.tginfo.me); [TundraSoft wiki](https://github.com/TundraSoft/tundra-connect/wiki/Telegram-API)

### Inferences
- Neo's evidence card per task should be a fixed, scannable shape: **status word first** (DRAFT / BLOCKED / DONE / NEEDS YOU), one-sentence result, then three short lines — *what changed* (files/PR link), *what ran* (tests/commands with pass/fail), *risks/unknowns* — and buttons (Approve / Changes / Open). Keep under ~1,000 chars so it reads on a phone without expanding; link the diff and trace for depth.
- Progress should be one message edited in place (checklist) while running, and a *new* message only at terminal states (done / blocked / needs decision) so the notification count equals the number of things that matter. Telegram's edit-with-inline-keyboard constraint fits this.
- "Honest status" = the worker never says "done" unless the definition-of-done (tests/CI/proof) was verified by the engine; otherwise it is DRAFT. This is the Claude Tag "objective check → Claude closes; otherwise you close" rule enforced in code.
- Given AI PRs' low acceptance and long pickup times, have workers produce small stacked changes and a PR summary + screenshots aimed at a 2-minute skim; batch PR reviews into one sitting.

### Gaps
- No controlled data on optimal message length or edit-in-place vs new-message for operator comprehension; this is inferred from Telegram constraints and product conventions.
- EASE 2026 and LinearB primary PDFs not opened; numbers are from the vendors' pages and secondary summaries, which disagree on the exact multiplier.

## 5. Steering: plan approval, mid-run steering, pause/redirect, cross-project handoff, efficient PR review

### Takeaway
Products provide a small, consistent steering vocabulary: plan mode before build, "reply in the thread to steer" without re-invoking, Stop/sleep/wake/mute/restart/fork commands, and a self-stopping maintenance loop that will not start new initiatives. Cross-project handoff is not a documented feature anywhere I found; the nearest is per-folder session grouping (Dispatch) and per-channel-per-project conventions (Claude Tag).

### Cited Findings

- Claude Tag: "Once Claude is in a thread, you don't need to @-mention it again; it reads every reply in that thread"; "anyone can reply to steer the work"; a message edit "never starts a new task on its own, so to be sure a correction is picked up, say it in a new reply." [vendor doc] — [Getting started](https://claude.com/docs/claude-tag/users/getting-started); [Good habits](https://claude.com/docs/claude-tag/users/good-habits); [Routines](https://claude.com/docs/claude-tag/users/proactivity)

- Devin Slack thread keywords: `sleep` (any message wakes), `mute` (stops reading thread), `archive`, `EXIT`; `!fast`/`!ultra` mode switches; playbook macros. [vendor doc] — [Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)
- Gas Town (Yegge, Jan 2026): 20–30 parallel Claude Code instances across defined roles coordinated by a "Mayor"; work state kept in git-backed "beads" so restarts don't lose context; commentators conclude "agent sessions are ephemeral, but work definitions must be durable" and that design/architecture, not execution, becomes the bottleneck; critics (incl. Yegge himself warning against serious use) call the concept count overwhelming. [practitioner + secondary] — [SE Daily](https://softwareengineeringdaily.com/2026/02/12/gas-town-beads-and-the-rise-of-agentic-development-with-steve-yegge/); [Maggie Appleton](https://maggieappleton.com/gastown); [dev.to lessons](https://dev.to/kiwibreaksme/what-i-learned-from-steve-yegges-gas-town-and-a-small-tool-for-solo-developers-2me2)

[practitioner/vendor guides] — [Augment guide](https://www.augmentcode.com/guides/how-to-run-a-multi-agent-coding-workspace); [Shruggie](https://shruggie.tech/blog/multi-agent-coding-workflows); [MindStudio worktrees](https://www.mindstudio.ai/blog/parallel-ai-coding-agents-git-worktrees)

### Inferences
- Neo's steering vocabulary over chat should be tiny and consistent across projects: Approve / Changes / Execute on plans (already in the plan registry, ADR-0019); `/now <text>` to inject mid-run; `/pause`, `/resume`, `/stop` (kill, keep worktree), `/restart` (fresh context, same brief), `/fork` (branch the task). Reply-to on a task's message should route to that task without a prefix, mirroring Claude Tag's "reply in the thread to steer".
- Cross-project handoff: treat it as "close here as BLOCKED-ON-<project>, open a todo in the other project's queue with a link to the trace" — durable work definition, ephemeral session (the Gas Town lesson).
- Keep the parallel count small per repo (≤3–4 active workers per reviewer) and isolate by worktree; remove worktrees when done (operator rule already in CLAUDE.md).

- No documented product feature for moving a task between projects/agents; this is inferred.
- Could not open Yegge's primary Gas Town post.

## 7. Memory and corrections from the operator: "never do X", "always Y", showing/forgetting memory

### Takeaway
Shipped products split memory into (a) human-written standing rules (CLAUDE.md / rules files / channel instructions), (b) agent-written learnings (Claude Code auto memory with a `feedback` type for corrections), and (c) an audit surface (`/memory`, "what do you remember about this channel?", `/doctor prompt-audit`). All of them warn that memory is advisory; a "never do X" that must hold needs a hook/permission rule. Size limits are explicit (200 lines / 25 KB index; CLAUDE.md target <200 lines; Cursor rules <500 lines).

### Cited Findings
- **Claude Code auto memory: Claude saves notes with a `type` field; `feedback` = "corrections you give Claude and approaches you confirm". Stored per repo at `~/.claude/projects/<project>/memory/` with a `MEMORY.md` index (one line per memory) plus topic files; "the first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation"; Claude Code reminds/forces Claude to shorten the index when near/over the limit. Files are plain markdown "you can edit or delete at any time"; `/memory` lists memory files and toggles auto memory; "Saved 2 memories" / "Recalled 2 memories" surface in the UI. Disable with `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`.** [vendor doc] — [Memory](https://code.claude.com/docs/en/memory)
- Claude Code CLAUDE.md guidance: "Keep it to facts Claude should hold in every session: build commands, conventions, project layout, 'always do X' rules"; "target under 200 lines... Longer files consume more context and reduce adherence"; "if two instructions contradict each other, Claude may pick one arbitrarily"; `/doctor prompt-audit` finds outdated/conflicting instructions and proposes edits "nothing in your files changes until you ask". Path-scoped `.claude/rules/*.md` load only when matching files are touched. [vendor doc] — [Memory](https://code.claude.com/docs/en/memory)
- "Both are loaded at the start of every conversation. Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." [vendor doc] — [Memory](https://code.claude.com/docs/en/memory)
- **Claude Tag channel memory: "@Claude remember for this channel: keep replies short, and always include a link to the source." Verify with "what do you remember about this channel?" A table maps each kind of correction to where it should live: channel memory (anyone, this channel) → CLAUDE.md (repo write, any session in that repo) → Channel instructions on the Configure page ("outrank memory") → Managed instructions (private correction from a managing channel) → a skill in the org marketplace → Workspace/Slack instructions. "The first three are yours to write."** [vendor doc] — [Good habits](https://claude.com/docs/claude-tag/users/good-habits); [Getting started](https://claude.com/docs/claude-tag/users/getting-started)
- Claude Tag "Steer explicitly": "Claude adapts to instructions, but it won't guess that you want it to... 'remember for this channel: always format reports as a table, and ask before posting anything longer than a screen.'" [vendor doc] — [Good habits](https://claude.com/docs/claude-tag/users/good-habits)
- Cursor rules are advisory ("models still may choose to ignore them or only partially follow them"); Cursor advises adding a rule when the agent repeats a mistake; keep rules under 500 lines; Memories documentation now redirects to Rules. [vendor doc + practitioner forum] — [Cursor forum](https://forum.cursor.com/t/cursor-rules-are-they-still-supported-by-cursor/117766/17); [MemoryLake](https://www.memorylake.ai/blogs/carry-cursor-context-across-sessions); [Cursor memories](https://docs.cursor.com/context/memories)
- Devin: Playbooks for recurring tasks, Knowledge for org-wide context; "instructions can be refined over time as you run a playbook"; enterprise admins can CRUD playbooks and attach automation macros. [vendor doc, secondary] — [Devin playbooks](https://docs.devin.ai/product-guides/using-playbooks.md); [Cognition June '24 update](https://www.cognition.ai/blog/june-24-product-update)
- Claude Code can migrate rules from `.cursor/rules/`, `.cursorrules`, `AGENTS.md`, `.devin/rules/`, `.windsurf/rules/`, `.clinerules` on `/init`. [vendor doc] — [Memory](https://code.claude.com/docs/en/memory)

### Inferences
- Expose operator corrections as a first-class chat verb (`/never <x>`, `/always <y>`, or a "Remember this" button on a correction) that writes to the project's curated memory with `type: feedback`, echoes back what was stored, and is listable/forgettable (`/memory list`, `/forget <id>`). This matches Neo's memory Phase 2 (capped curated memory) and the Claude Code index-size discipline.
- Keep two tiers visibly separate in the console: *rules* (operator-authored, loaded always, small) vs *learnings* (worker-authored, capped, reviewable). Offer a periodic "audit memory" sweep (like `/doctor prompt-audit`) as a loop.
- Any "never" that is a safety invariant must be mirrored into the governor (deny rule) — memory is for preferences, code is for prohibitions.

### Gaps
- Could not open Devin's Knowledge docs to confirm how corrections are captured there.
- No study on how often agent-written memories drift or conflict over months.

- Claude Code scheduled tasks are session-scoped and expire after 7 days; durable schedules need cloud/desktop tasks or GitHub Actions. [vendor doc] — [Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)

### Inferences
- Addressing model for Neo over Telegram: default target = pinned/focused project; `project: order` or reply-to-a-task-message for one-shot addressing (already built: one-shot session focus); a `/status` board sorted **needs-me → running → blocked → done today**, and a project overview that shows per project: active workers, open decisions, last result, next scheduled loop.
- Daily rhythm that the evidence supports: (1) morning brief = decisions queue + "waiting on you" + overnight results, no recap of green items; (2) during the day, only pages interrupt; (3) one or two batched review sittings for PRs/drafts; (4) evening digest optional; (5) weekly 30-minute review that prunes loops/todos not serving the current goal and audits memory/rules.
- Treat the "needs me" queue as the single source of truth across all projects (one list, project-tagged), because the serial bottleneck is the operator, not any project.

### Gaps
- Few rigorous, long-horizon field reports from solo operators of multi-project agent fleets (most content is vendor or SEO); the "4–7 agents" statistic is unverified.
- No product documents a cross-project "what needs me now" board for a *personal* fleet; Claude Code projects' overview is the closest.

## Cross-cutting design principles (synthesis for the report writer)

1. **Three tiers, enforced in code:** page (decision/failure only Neo can resolve) → digest (results Neo can use) → log (everything else). Only pages notify. Source basis: SRE tiers, NeuBird/PagerDuty actionability data, Remote Control's two push toggles, Claude Tag "post only on change".
2. **Every task has a definition of done and a closer.** Objective check → engine closes; approval → Neo one click; choice → Neo one word; none → it's a question, not a task (Claude Tag table).
3. **Decision cards, not transcripts:** context, options with trade-offs, recommendation, timeout default, expiry; fail-safe (deny) on expiry for irreversible actions; permission-style prompts can stay open with reminders (Claude Code keeps them open; other dialogs expire at 5 min).
4. **Graduated autonomy with a hard floor:** modes per project/action class; never-auto-approved list in code; circuit breaker (N blocks → back to prompting); grants scoped once/task/project/always; earned trust *offered*, never auto-applied (Lee & See calibration; Claude Tag "widen as output holds up").
5. **Design against complacency:** keep evidence lines even on trusted work; sample-verify routine approvals; show what verification actually ran (Parasuraman & Manzey; Goddard).
6. **Steering vocabulary is tiny and uniform:** Approve/Changes/Execute; reply-to-steer; /now, /pause, /stop, /restart, /fork; durable work definitions survive session death (Gas Town).
7. **Phone-first reporting:** status word first, one sentence, three evidence lines, links; edit-in-place while running, new message only at terminal states; ≤~1,000 chars; small stacked PRs with skimmable summaries (LinearB/Qodo review data).
8. **Memory as two visible tiers:** operator rules (small, always loaded, auditable) vs worker learnings (capped, typed `feedback`, forgettable); prohibitions live in the governor, not in memory (Claude Code & Claude Tag warnings).
9. **Multi-project rhythm:** one topic per project, one thread per task, a single cross-project "needs me" queue, morning "waiting on you" brief, batched review sittings, weekly 30-minute prune (Claude Tag habits; Solo Founder guide).
