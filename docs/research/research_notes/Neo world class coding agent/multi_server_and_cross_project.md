# Multi-server / multi-environment operation and cross-project coordination for a self-hosted coding-agent engine

Scope note for the report writer: Neo today runs headless Claude Agent SDK workers in project folders under `/home` on one server, projects deploy with Docker, production often lives on other hosts, and the operator steers over Telegram. The engine already records a deployed version per project (`src/engine/producers/probe.ts`: GET `deployedVersionUrl`, read the sha at `deployedVersionPath`, count commits on the deploy branch after it, written to `deploy:<project>`) and already runs its governor as a PreToolUse-style gate (ADR-0006, `src/engine/governor.ts`). The findings below are selected for mechanisms a single operator can run and the engine can enforce deterministically.

Research constraints: in this session the following hosts were unreachable (network allowlist), so their content is cited only via search-result snippets or GitHub-hosted source mirrors, and is marked as such: sre.google, docs.devin.ai, docs.github.com (used the `github/docs` repo mirror instead), developers.openai.com, fluxcd.io (used the `fluxcd/website` repo mirror), backstage.io (used the `backstage/backstage` repo mirror), tailscale.com, docs.pact.io (used the `pact-foundation/docs.pact.io` repo mirror), dora.dev, dortort.com, dzone.com, agentpatterns.ai, augmentcode.com, oneuptime.com, dev.to, arxiv.org.

## A1. Execution topology: one engine with remote-exec vs. a runner per host

### Takeaway
Every current agent product that executes "somewhere other than the developer's machine" converges on the same shape: a long-lived runner process on the target host that **polls outbound** for work and streams events back, with no inbound ports (Claude Code self-hosted runners, Remote Control, GitHub self-hosted runners, Salt minions). For a single operator with a few hosts, the realistic choice is between (a) keeping the engine on one box and reaching other hosts over SSH/Docker-context for a *narrow* set of deploy/inspect commands, and (b) running a thin Neo "runner" per host that polls the engine; the Claude Code runner design is the best-documented template for (b).

### Cited Findings
- Claude Code **Remote Control** keeps execution local: "Claude keeps running locally the entire time, so your code execution and filesystem access stay on your machine"; the web/mobile UI "are a window into that local session, so your computer has to stay on and the `claude` process has to keep running." — [Claude Code docs: Remote Control](https://code.claude.com/docs/en/remote-control)
- Remote Control's network model: "Your local Claude Code session makes outbound HTTPS requests only and never opens inbound ports on your machine. When you start Remote Control, it registers with the Anthropic API and polls for work." Credentials are "multiple short-lived credentials, each scoped to a single purpose and expiring independently." — [Remote Control](https://code.claude.com/docs/en/remote-control)
- Remote Control server mode supports a spawn mode per folder: `--spawn same-dir` (sessions share the cwd "so they can conflict if editing the same files") or `--spawn worktree` ("each on-demand session gets its own git worktree"); session names default to `<hostname>-<adjective>-<noun>`; "One remote session per interactive process" outside server mode; "If you run `claude` from a terminal on a remote machine, start it inside `tmux`". It refuses API-key auth and long-lived `setup-token` tokens ("Remote Control requires a full-scope login token"). — [Remote Control](https://code.claude.com/docs/en/remote-control)
- Claude Code **cloud sessions** run on Anthropic VMs by default, or "on your organization's self-hosted environment when routed there"; `claude --cloud "task"` creates a session that clones "your current directory's GitHub remote at your current branch, not your local checkout"; `claude -p "msg" --cloud <session-id>` queues a message into a running session from any machine. `--cloud works with a single repository at a time.` — [Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Claude Code **self-hosted environments** (public beta, Team/Enterprise only) are explicitly modelled on CI runners: "Runner: a program running on hosts inside your network. Runners execute the sessions; the idea is the same as a self-hosted CI runner." A runner "polls for sessions", "clones the repository the developer chose, and starts a Claude Code process on your host"; "every connection is outbound from your network, with none inbound"; "Anthropic never connects into your network." Lease/heartbeat: "each poll refreshes the lease and doubles as the heartbeat. If the runner stops polling, its lease lapses after about 60 seconds." A runner "serves one owner at a time and locks to that owner when it claims its first session, so checked-out code never mixes between owners." — [Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)
- Self-hosted runner extension points a Neo runner could copy: a wrapper script (`--exec-path`) for "provisioning short-lived credentials scoped to the session creator, exporting environment-specific secrets ... or applying resource limits around the child process"; lifecycle hooks (`--hooks-dir`) such as `checkout` ("clone from a read-through mirror ... or apply per-session git auth"), `post-session`, `spawn-runner`; a per-session `CLAUDE_CONFIG_DIR` snapshot so "Writes here are isolated to this session"; a session JWT whose `act` claim identifies the creator, with the advice "use `jq -re` rather than `jq -r` when the extracted claim gates an auth decision, so an absent claim exits non-zero". — [Customize sessions in self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments-configuration)
- Claude Code also offers a **lighter per-host option** than self-hosting: "To run Claude Code on your own always-on machine and drive it from other devices, use Remote Control, which is also available on Pro, Max, and Ultra plans." — [Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)
- Claude Code **Projects** (beta, Pro/Max/Ultra) add a coordinator layer: "A project is one ongoing conversation where Claude coordinates a stream of related work ... it starts a thread for each task"; each thread "is a separate session with its own context window that does one piece of work and reports back"; the coordinator "sees what threads report back, not every step they take"; a thread can be routed to "your computer ... through Remote Control" when it needs local resources. — [Projects](https://code.claude.com/docs/en/claude-projects)
- Docker's own remote-host story for compose: set `DOCKER_HOST=ssh://user@remotehost` or create a Docker context and run `docker --context remote compose up -d`; "Make sure we have set the key-based authentication for SSH-ing to the remote host." (search snippet; Docker blog) — [Docker blog: deploy on remote Docker hosts with docker-compose](https://www.docker.com/blog/how-to-deploy-on-remote-docker-hosts-with-docker-compose/)
- Config-management push vs. pull (search snippets, blog comparisons, not official docs): Ansible is "push-based and agentless ... over SSH or WinRM, with no daemon on target machines"; Salt "supports both push (master sends commands) and pull (minions check in periodically)" and has "a masterless mode (`salt-call --local`)" and "an SSH-based agentless mode (`salt-ssh`)". Sources disagree on whether Salt is push or pull. — [lucaberton.com: Ansible vs SaltStack 2026](https://lucaberton.com/blog/ansible-vs-saltstack-2026/); [computingforgeeks: Ansible vs Chef/Puppet/Salt](https://computingforgeeks.com/ansible-vs-chef-puppet-salt/)
- Codex cloud tasks "run in isolated, OpenAI-managed containers"; "the agent phase runs offline by default unless you enable internet access"; secrets "are removed before the agent phase starts." (search snippet; developers.openai.com not fetchable) — [OpenAI Codex docs: sandbox](https://developers.openai.com/codex/sandbox)
- Devin's hosted model: per-repo "blueprints" build on an org blueprint; "Repos are cloned and set up in the order shown in Settings, and a snapshot is saved after a health check"; a `post-build` step is "the place to check that the whole stack boots together". (search snippet; docs.devin.ai not fetchable) — [Devin docs: environment blueprints](https://docs.devin.ai/onboard-devin/environment/blueprints)

### Inferences
- The industry-standard shape for "agent on host X" is **pull, not push**: a runner on X polls a control plane over outbound HTTPS and holds a lease with a heartbeat. For Neo this maps cleanly onto the existing engine: a `neo-runner` on each extra host polls `POST /agent/ingress`-style endpoints (already bearer-gated by `AGENT_INGRESS_SECRET`), claims a unit, runs `query()` locally with that host's `cwd`, and streams events back into the ledger. Nothing new has to accept inbound connections on prod hosts.
- SSH/Docker-context from the engine box is the right tool for the **narrow deploy surface** (pull image, `compose up`, health probe, read logs), not for running an agent on prod. Keep the agent's filesystem on the dev server; let only a small allowlisted command set cross the SSH boundary (see A3).
- Remote Control's `--spawn worktree` and the runner's "one owner, isolated per-session config dir" are the two isolation primitives worth copying: per-session worktree for parallel work on one repo, and a per-session config snapshot so a worker cannot mutate host-wide settings.
- Claude Code Projects is effectively the hosted version of what Neo's dispatcher already does (coordinator sees reports, not steps; thread per task; thread per repo for one goal). Its explicit limitation, "sees what threads report back, not every step", is a validation of ADR-0007's report-to-dispatcher design.

### Gaps
- No primary source compared Nomad/Kubernetes jobs or GitHub self-hosted runners against SSH for *agent* execution specifically; the comparison above is drawn from the runner designs of Claude Code and Devin.
- The Codex cloud and Devin docs could not be fetched; their details are from search snippets only.
- Self-hosted Claude Code environments are Team/Enterprise-only, so a single Max operator cannot use them directly; they are cited as a design template, not an available product path.

## A2. Environment model: dev → staging → prod, GitOps, config/secrets, and how an agent learns where it is

### Takeaway
The durable patterns are: environments are *directories or repos* in git with a reconciler per environment (Flux/Argo); dev auto-reconciles while staging/prod promotion is a PR with review; secrets live encrypted per environment with separate keys (SOPS+age) so a dev key cannot decrypt prod; and the running process discovers its environment from an explicit variable that **fails closed** (unset or unknown = not production-capable, never "assume prod").

### Cited Findings
- Flux repository-structure guide (official, via repo mirror): in a **monorepo** "All Kubernetes manifests live in one repository, with per-environment overlays and a `clusters/` directory per cluster"; apps and infrastructure are separated "so reconciliation order can be controlled"; promotion: "Staging: new app releases can be delivered automatically using image updates to Git. Production: app version bumps can require manual approval, with Flux pushing changes to a new branch for a pull request." Infrastructure changes "merge to staging first. After the cluster reconciles and passes conformance tests, they are promoted to production through PR reviews and end-to-end testing." Con of monorepo: "Git doesn't restrict access to individual files, so everyone can read production config." — [fluxcd/website: repository structure](https://raw.githubusercontent.com/fluxcd/website/main/content/en/flux/guides/repository-structure.md)
- Flux **repo-per-environment**: "production has its own repository ... Access can be limited to a subset of team members"; con: "Promotion between environments is more time-consuming, especially for infrastructure changes" which "can't be fully automated with Flux image updates." — [fluxcd/website: repository structure](https://raw.githubusercontent.com/fluxcd/website/main/content/en/flux/guides/repository-structure.md)
- Flux **repo-per-app**: "Application source code and deployment manifests share a repository. A config repository points to the app repo rather than copying its manifests"; the config repo "defines a `GitRepository` (tracking a branch or semver range) and a `Kustomization` that selects the environment's directory and patches", or a `HelmRelease` per environment. — [fluxcd/website: repository structure](https://raw.githubusercontent.com/fluxcd/website/main/content/en/flux/guides/repository-structure.md)
- Practitioner Flux tutorials (search snippets, one author's series; not fetched) describe three promotion styles: branch-based (`develop` → `staging` → `main`, "promoting a change means merging from one branch to another"), directory-based (one branch, per-environment overlay directories, "a promotion script copies the image version between directories"), and image-based (`ImagePolicy` per environment, "dev tracking any semver version and prod limited to stable releases"). Safety advice: "Keep prod pruning off (`prune: false`)", "Auto-reconcile dev, but gate staging and prod behind manual approval." — [oneuptime: GitOps promotion pipeline](https://oneuptime.com/blog/post/2026-02-09-gitops-promotion-pipeline-dev-staging-prod/view); [oneuptime: directories for environment promotion with Flux](https://oneuptime.com/blog/post/2026-03-06-use-git-directories-environment-promotion-flux-cd/markdown)
- **GitHub Environments** as the environment model for CI/CD (official docs via `github/docs` mirror): deployment protection rules include required reviewers ("Up to six users or teams ... one approval is enough"; optional block on self-review "so the person who starts a deployment can't approve it"), a wait timer ("1 to 43,200 minutes"), deployment branches/tags ("Protected branches only" or name patterns matched against `GITHUB_REF`), and custom protection rules "built on GitHub Apps so third-party systems (such as observability, change management, or code quality tools) can gate deployments". Environment secrets are "available only to jobs that reference the environment. If the environment requires approval, jobs can't access its secrets until a reviewer approves." Admin bypass is on by default and "can be disabled per environment." Plan limit: required reviewers, wait timers and custom rules are "limited to public repositories" on Free/Pro/Team. — [github/docs: deployments and environments](https://raw.githubusercontent.com/github/docs/main/content/actions/reference/workflows-and-actions/deployments-and-environments.md)
- **SOPS + age per environment** (search snippets; blogs and one project's ADR): "a separate encrypted file per environment, such as `secrets.dev.enc.yaml` and `secrets.prod.enc.yaml`", with rules in `.sops.yaml` at the repo root defining "which age public keys may decrypt which file"; "Don't share keys between production and non-production" so "each environment can only decrypt its own secrets"; `encrypted_regex` keeps metadata readable in diffs; rotation is `sops updatekeys` but "the old encrypted blobs remain decryptable in git history." — [protea ADR-D28: secrets management](https://protea.readthedocs.io/en/latest/adr/D28-secrets-management.html); [oneuptime: multi-environment secrets with SOPS and Flux](https://oneuptime.com/blog/post/2026-03-05-multi-environment-secrets-sops-flux/view)
- SOPS README (official) confirms age as a backend alongside AWS/GCP/Azure KMS and PGP and describes SOPS as "an editor of encrypted files that supports YAML, JSON, ENV, INI and BINARY formats." — [getsops/sops README](https://raw.githubusercontent.com/getsops/sops/main/README.rst)
- Claude Code cloud environments show how a hosted agent product models "environment" = network allowlist + env vars + setup script + secrets the agent cannot read: "Each environment sets one network access level ... **Trusted** allows package registries and other allowlisted domains; **Custom** takes your own domain list"; "A network secret is an API key or token you store on a cloud environment so Claude can call that API from any session in the environment without seeing the key. Anthropic's agent proxy adds the key to requests for the hosts you list, after each request leaves the session's VM"; "Anyone who uses the environment can read the values [of environment variables] ... use a network secret instead." — [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)
- How an agent learns which environment it is in, fail-closed guidance (search snippets): twelve-factor treats "no env vars" as "a vanilla development deploy"; an `envconfig` package "treating the environment as development by default" but able to "fail immediately when a non-development environment is misconfigured"; a config guide recommends "required variables fail startup if missing (not silently default)" and "validate all configuration at startup"; an agent-rules file recommends the app "fails fast if required env vars are missing or malformed" and "discourages per-environment branches keyed on APP_ENV in business logic"; Node docs warn "some libraries default NODE_ENV to a development setting". — [12factor config (mirror)](https://git.kennethreitz.org/kennethreitz/12factor/src/commit/313f5785643d7f9d3c7d6ec3de764d6962cd6bf7/content/config.md); [npm envconfig](https://www.npmjs.com/package/envconfig); [aiwg config-in-environment rule](https://cdn.jsdelivr.net/npm/aiwg@2026.7.12/agentic/code/frameworks/sdlc-complete/rules/config-in-environment.md); [Node.js: development vs production](https://nodejs.org/learn/getting-started/nodejs-the-difference-between-development-and-production)
- Claude Code hooks give an engine a per-session way to inject environment facts: `SessionStart` hooks "can use `CLAUDE_ENV_FILE`, a file path where environment variables can be saved for later bash commands", and `hookSpecificOutput.additionalContext` is "inserted as a system reminder at the start of the conversation"; on resume "SessionStart runs again with `source` set to `"resume"`, so it can refresh stale context." — [Claude Code hooks](https://code.claude.com/docs/en/hooks)

### Inferences
- For Neo's Docker-per-project world the Flux "repo-per-app + directory per environment" layout is the lightest fit: each project repo carries `deploy/{dev,staging,prod}/compose.override.yml` (or image tag files); promotion is a commit that bumps a pinned image digest in the next directory. The engine can then *diff directories* to answer "what is in staging that is not in prod" deterministically, extending the existing `deploy:<project>` probe.
- "Everything starts as dev" should be enforced two ways: (1) in the engine's per-session environment injection (a `NEO_ENV` value the worker cannot change, set from the project registry; absent = `dev`), and (2) in project code per the engineering baseline, where `NEO_ENV`/`APP_ENV` unset means dev *features* but an unknown value is a startup error. Both are deterministic and cheap.
- Secrets: a per-environment SOPS file keyed to a per-environment age key, with the **prod private key only on the prod host and never on the dev/engine server**, makes it structurally impossible for a worker on the dev server to read prod secrets, matching the "network secret the session cannot see" idea from Claude's cloud environments without any proxy.
- GitHub environment protection rules are the ready-made "approval gate for deploy" if a project deploys via Actions, but required reviewers are public-repo-only on Free/Pro/Team; for private repos a single operator must implement the gate in Neo (A3) or in the CI runner itself.

### Gaps
- Argo CD docs were not consulted (fluxcd mirror was); the promotion patterns are generic enough that Argo's are equivalent, but no Argo citation is given.
- Official SOPS docs on `creation_rules`/`path_regex`/`exec-env` could not be fetched (getsops.io not tried; README lacked them); the per-environment key practice is cited from community posts only.
- No source was found that describes an *agent* discovering its environment at runtime beyond generic twelve-factor/app guidance; the engine-injection pattern is an inference.

## A3. Production safety for agents: read-only default, approval gates, break-glass, and what the products actually allow

### Takeaway
Across Google SRE, vendor guides and the agent products themselves, the consensus mechanism is: agents start **read-only on production**, every mutating action is a named, scoped tool (not a shell), production writes require explicit human approval in a channel the human controls, and enforcement lives in code (hooks/policies) rather than in the prompt. None of the mainstream coding agents ships a "deploy to your infra" capability; they either refuse it (Devin: templates only, approval per deploy) or leave it to credentials you choose to hand over.

### Cited Findings
- Google SRE whitepaper "AI in SRE: How Google is Engineering the Future of Reliable Operations" (search snippets only; sre.google unreachable): "progressive authorization" is a pillar; "Agents are released to lower levels of autonomy (human approved) and scale up based on the SRE Autonomy Levels"; rationale: "the blast radius of a failure can be far larger and propagate far more quickly than with human operators"; it names "autonomous mitigation agents (AI Operator), execution guardrails (Actus), and evaluation pipelines grounded in incident history (IRM Analyzer)". — [sre.google: AI in SRE](https://sre.google/resources/practices-and-processes/ai-engineering-reliable-operations/)
- Google Cloud blog companion (fetched; May 28, 2026, Malesevic & Heiser): "SRE AI agents must have a strong identity (agents have roles and permissions assigned)"; "we favor transparency over black-box automation"; "having consistent controls to prevent unwanted mutations of production state"; "SRE AI agents need to provide a high level of reliability SLOs and have well-defined backup options (automated or manual)"; "Processes and operations that are already successfully automated, or that can be easily automated with classic non-AI based systems, do not need to be replaced"; "An agentic approach does not necessarily imply removing people from the process, specifically for higher-risk services"; "we developed a way to track autonomous levels" (levels not defined in the post). — [Google Cloud blog: how Google SRE is using agentic AI](https://cloud.google.com/blog/products/devops-sre/how-google-sre-is-using-agentic-ai-to-improve-operations)
- DZone "7 Essential Guardrails for Building AI SRE Agents" (search snippet; not fetched): "read-only access by default and human approval for production changes such as deploys, IAM edits, and alert suppression"; "scoped tools instead of shell access, validation hooks for proposed remediation, prompt injection protection, and complete audit trails." — [DZone: AI SRE agent guardrails](https://dzone.com/articles/ai-sre-agents-guardrails)
- Augment Code 2026 AI-SRE guide (search snippet): build "agent identity, blast radius limits, rollback infrastructure, policy-as-code, audit logging, and cost guardrails before letting an agent act in production." — [Augment Code: AI SRE guide](https://www.augmentcode.com/guides/ai-sre-ai-powered-site-reliability-engineering)
- **Claude Code hooks as the enforcement point**: PreToolUse "Runs after Claude creates tool parameters and before processing the tool call"; a command hook can print `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"..."}}`; decisions are `allow`, `deny`, `ask`, `defer`; "Exit 0 with no output means no decision"; "Exit 2 blocks the call. A JSON allow in the same run doesn't override the block"; "A timed-out hook doesn't block the call on PreToolUse, unless `onFailure: "block"` is set." Managed-settings hooks are additive and cannot be removed by user/project hooks; `allowManagedHooksOnly` blocks all other hook sources. 33 hook events are documented, including `PermissionRequest`, `PermissionDenied`, `WorktreeCreate`, `ConfigChange`. — [Claude Code hooks](https://code.claude.com/docs/en/hooks)
- Practitioner enforcement example (search snippet; Towards AI post): a PreToolUse hook that "greps the Bash command and rejects any call to the production deploy script"; "the model received the hook's message, stopped, and asked a human to run the deploy"; a chained command "with the script buried inside was still caught by the grep". Claude Academy: "exit code 2 blocks the action, and the stderr message gets fed back to Claude"; a Chinese-language guide warns "exit 1 does not block; it is treated as a non-blocking error." — [Towards AI: CLAUDE.md can't enforce anything](https://pub.towardsai.net/claude-md-cant-enforce-anything-here-s-the-hook-i-use-instead-424be05a68f0); [Claude Academy: hooks](https://academy.claude.com/courses/claude-code-101/hooks); [learnblockchain.cn: Claude Code hooks](https://learnblockchain.cn/article/26598)
- Vendor hardening advice for ops use (search snippets): "`--dangerously-skip-permissions` exists. Don't use it on a host that can SSH into prod"; "use separate kubeconfig and AWS profile files per environment, and add production hostnames and cluster contexts to your deny rules in `~/.claude/settings.json`"; run "in a devcontainer or isolated shell that only mounts staging credentials"; rule of thumb "always review the plan, always test in staging, never auto-apply to production." — [DeployHQ Claude Code cheatsheet](https://www.deployhq.com/cheatsheets/claude-code); [computingforgeeks: Claude Code for DevOps engineers](https://computingforgeeks.com/claude-code-devops-engineers/)
- Claude Code auto-fix warning shows the "comment can deploy" hazard: "If your repository uses comment-triggered automation such as Atlantis, Terraform Cloud, or custom GitHub Actions that run on `issue_comment` events, be aware that Claude can reply on your behalf, which can trigger those workflows ... consider disabling auto-fix for repositories where a PR comment can deploy infrastructure or run privileged operations." — [Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- **Devin** (search snippets; docs.devin.ai unreachable): built-in deployment covers only "static frontends, served from devinapps.com, and FastAPI backends, deployed to Fly.io. Every deploy needs your explicit approval"; "Deploying is not how Devin ships code to your infrastructure ... choose your own deployment method and give Devin the credentials and instructions it needs via Secrets and Skills"; "Enterprise organizations have deployment disabled for all sessions"; for existing apps "backend apps will not in 99% of cases." — [Devin docs: deployment capabilities](https://docs.devin.ai/product-guides/deployment-capabilities)
- **Codex** (search snippets; developers.openai.com unreachable): CLI "default workspace-write sandbox option will have the network disabled by default, unless enabled in config, using `[sandbox_workspace_write]` with `network_access = true`"; a `network_proxy` feature "can restrict enabled traffic to a domain policy"; "enabling network access carries prompt-injection risk"; the proxy "does not filter MCP connections, web search, or cloud tasks." The openai/codex repo's `docs/config.md` currently documents `allow_managed_hooks_only` in `requirements.toml` to "ignore user, project, and session hook configs." — [OpenAI Codex docs: sandbox](https://developers.openai.com/codex/sandbox); [openai/codex docs/config.md](https://raw.githubusercontent.com/openai/codex/main/docs/config.md)
- **Claude Code cloud sessions** keep credentials out of the sandbox: "git credentials and signing keys stay outside the sandbox, and a proxy authenticates on the session's behalf with scoped credentials"; "When running with network access disabled, Claude Code can still communicate with the Anthropic API, which may allow data to exit the VM." — [Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- **Tailscale SSH** (search snippets; tailscale.com unreachable): check mode "requires a user to re-authenticate with your SSO (or to have recently re-authenticated) before being able to establish a Tailscale SSH connection", set with `"action": "check"` and `checkPeriod` (default 12 hours; a 2024 bug treated `"0s"` as unset, fixed 2024-04-23). One third-party guide wrongly describes check mode as a dry-run; Tailscale's own description is authoritative. — [Tailscale blog: Tailscale SSH](https://tailscale.com/blog/tailscale-ssh); [Tailscale advisory TS-2024-003](https://vulnerability.circl.lu/vuln/ts-2024-003)
- **Short-lived SSH identity** (search snippets): Teleport Machine ID's `tbot` "writes short-lived certificates to disk" and "short-lived certificates automatically expire, there is no need to revoke them"; Teleport frames "proving an identity of an AI agent, human user, or service" as the same problem. — [Teleport Machine ID: SSH](https://goteleport.com/docs/machine-id/access-guides/ssh/); [Teleport architecture: authentication](https://goteleport.com/docs/architecture/authentication)
- Claude Code's own "actions no mode auto-approves" exist even under `--dangerously-skip-permissions`: "Even then, the actions no mode auto-approves still apply." — [Channels](https://code.claude.com/docs/en/channels)

### Inferences
- Neo already has the right enforcement point (governor as PreToolUse hook, default-ESCALATE, ADR-0006/0012). The production extension is a **host/environment-aware governor**: any Bash containing a prod hostname, a prod Docker context, `ssh prod*`, `DOCKER_HOST=ssh://`, `kubectl --context prod`, or a path under `deploy/prod/` is denied for autonomous paths and escalated to the Decisions channel otherwise. Exit-2/`deny` semantics mean the worker sees *why* and routes the deploy back to the operator, which is exactly the reported behaviour in the field.
- "Never debug by editing prod" can be made structural rather than policy: the agent's filesystem is only ever the dev server's project folder; prod hosts are reachable only through a tiny engine-owned toolset (`deploy.pull`, `deploy.up`, `deploy.rollback`, `prod.logs`, `prod.health`) exposed as MCP tools whose implementations the engine controls. Workers never get an interactive shell on prod, so there is nothing to edit.
- Break-glass = the operator, not the agent: the operator can run the same engine tools with a `--force`/`break-glass` flag that is logged with cause in the ledger (ADR-0015), and the agent can *propose* that action but never execute it. Tailscale `check` mode on prod hosts gives the equivalent human re-auth gate at the network layer if SSH is used.
- Credentials: put a per-host **deploy key** (SSH certificate with short TTL if Teleport/step-ca is adopted; otherwise a dedicated `neo-deploy` user with a forced-command `authorized_keys` entry) on the engine host, never inside a worker's environment. The worker calls an engine tool; the engine uses the key. This mirrors Claude's cloud "credentials stay outside the sandbox" design without any proxy.

### Gaps

## A4. Deploy loops: CI/CD as the only path, agent-triggered deploy with approval, post-deploy verification, auto-rollback, Docker specifics

### Takeaway
The verifiable loop is: agent produces a PR → CI builds an immutable image → a human-approved promotion commit (or environment approval) deploys → the engine watches health + error-rate over two consecutive windows → automatic rollback to the previous digest on breach, with every verdict appended to an audit log. DORA 2025 data says AI raises throughput but *lowers* stability unless small batches, strong version control and fast feedback are in place, which is the empirical argument for keeping the deploy loop small and automated.

### Cited Findings
- DORA 2025 (Google Cloud announcement, fetched): "AI amplifies what already exists"; "AI adoption now has a positive relationship with software delivery throughput ... AI adoption still has a negative relationship with software delivery stability"; "Increased change volume from AI can expose weaknesses downstream. Strong automated testing, mature version control, and fast feedback loops help prevent that instability"; "90% of survey respondents use AI at work"; "30% report little or no trust in AI-generated code"; "high-quality platforms correlate with an organization's ability to realize AI's value." The seven capabilities of the DORA AI Capabilities Model appear only as an image on that page; the fetch tool's list (clear AI stance, healthy data ecosystems, AI-accessible internal data, strong version control, small batches, user-centric focus, quality internal platforms) is **unverified** against the report text. — [Google Cloud: announcing the 2025 DORA report](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report); [DORA 2025 report](https://dora.dev/dora-report-2025/)
- Canary auto-rollback thresholds (search snippets): one workflow defines "Breach = error rate > 2× baseline OR p99 latency > 1.5× baseline, sustained across the previous and current 5-minute window" and says "every verdict should go to an append-only audit log"; a DEV post argues a bare 2× trigger "misfires on small canaries" and to "Fire only when two windows in a row breach"; a GitHub discussion proposes burn-rate SLO gating because "the burn-rate model uses a time-windowed error budget" rather than an instantaneous threshold. — [Augment Code: canary SLO auto-rollback workflow](https://www.augmentcode.com/workflows/devops/canary-slo-auto-rollback); [DEV: rolling a canary back on an error-rate spike](https://dev.to/multigrid/rolling-a-canary-back-automatically-on-an-error-rate-spike-1jf5); [GitHub discussion: burn-rate gating](https://github.com/petry-projects/.github-private/discussions/1158)
- Runbook pattern (search snippet; Lambda example): "If it fires within 30 minutes of a deployment, the Lambda alias automatically rolls back to the previous version", then manual verification "that error rate is recovering, root-cause analysis before any redeploy, and a fix in a new change rather than redeploying the same commit." — [a5c-cell RUNBOOK-007 deployment rollback](https://github.com/j3brns/a5c-cell/blob/main/docs/operations/RUNBOOK-007-deployment-rollback.md)
- GitHub environment gates as the "agent proposes, human approves" mechanism: a job referencing a protected environment pauses until a required reviewer approves, and "jobs can't access its secrets until a reviewer approves"; the wait timer and branch/tag restrictions are additional gates. — [github/docs: deployments and environments](https://raw.githubusercontent.com/github/docs/main/content/actions/reference/workflows-and-actions/deployments-and-environments.md)
- Claude Code's PR auto-fix shows the agent-side half of a deploy loop: "Claude subscribes to GitHub activity on the PR, and when a check fails or a reviewer leaves a comment, Claude investigates and pushes a fix if one is clear"; "GitHub does not emit a webhook when the base branch advances and creates a merge conflict, so auto-fix can't react to conflicts on its own." — [Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Claude Code **Channels** are the push-side primitive for "CI tells the agent": "a webhook from CI, your error tracker, a deploy pipeline, or other external service arrives where Claude already has your files open"; channel plugins "maintain a sender allowlist"; "Anyone who can reply through the channel can approve or deny tool use in your session, so only allowlist senders you trust with that authority." Telegram is a first-party channel plugin (`/plugin install telegram@claude-plugins-official`). — [Channels](https://code.claude.com/docs/en/channels)
- Session-scoped scheduled tasks (`/loop`) are the poll-side primitive: "poll a deployment, babysit a PR"; "Recurring tasks automatically expire 7 days after creation"; "Tasks only fire while Claude Code is running and idle"; "No catch-up for missed fires." Cloud scheduled tasks run "in the cloud on a schedule, via API call, or on GitHub events." — [Run prompts on a schedule](https://code.claude.com/docs/en/scheduled-tasks)
- Docker remote deploy mechanics: `DOCKER_HOST="ssh://user@remotehost" docker-compose up -d`, or a persistent context `docker --context remote compose up -d`; a CI pipeline "can create a context from a deploy host variable, load an SSH key, and run `docker --context remote compose up -d`", adding `ssh-keyscan` for known_hosts. Watchtower targets a remote daemon only via `--host`/`DOCKER_HOST` TCP (`tcp://10.0.1.2:2375`) with optional TLS; the unencrypted 2375 port "gives full control of the Docker daemon". — [Docker blog: remote Docker hosts with compose](https://www.docker.com/blog/how-to-deploy-on-remote-docker-hosts-with-docker-compose/); [Watchtower on Docker Hub](https://hub.docker.com/r/v2tec/watchtower)
- Pact's deployment matrix is the contract-side "can I deploy" gate (official docs via repo mirror): `pact-broker can-i-deploy --pacticipant Foo --version 23 --to-environment production` checks "successful verifications between that version and the versions of integrated apps already in the target environment"; exit 0 = yes, 1 = no; `record-deployment --pacticipant Bar --version 56 --environment production` tells the broker what is where; "recommends recording deployments to pre-production environments as well." — [pact-foundation/docs.pact.io: can-i-deploy](https://raw.githubusercontent.com/pact-foundation/docs.pact.io/master/website/docs/pact_broker/can_i_deploy.md)

### Inferences
- Neo's existing `deploy:<project>` probe (deployed sha + "N commits not deployed") is one half of the loop; the missing half is a **deterministic deploy state machine** per project: `proposed → approved(by operator msg id) → deploying(host, digest) → verifying(window 1/2) → live | rolled-back`, each transition a ledger row with cause (ADR-0015). The agent can only create `proposed`; only an operator Telegram reply moves it to `approved`; everything after is engine code.
- Docker-specific: deploy by **immutable image digest**, not tag; keep the previous digest in the ledger so rollback is `compose up` with the previous digest, no rebuild. Post-deploy verification = the existing health probe (`probe:<project>`) sampled every 30 s for two 5-minute windows, with breach = health failing or error-rate > 2× pre-deploy baseline in both windows (per the canary sources). This needs no new infrastructure.
- "CI/CD as the only path to prod" for a single operator with Docker: build the image in CI (or on the dev server), push to a registry, and let the prod host *pull*; the only command that crosses to prod is `compose pull && compose up -d` via a forced-command SSH key or Docker context. Watchtower-style auto-pull is cheaper but removes the approval gate, so it fits dev/staging only.
- If an engine-triggered rollback fires, the loop should hand the *diagnosis* back to a worker on the dev server (logs pulled over the same narrow tool) rather than letting anything run on prod, matching the runbook's "fix in a new change rather than redeploying the same commit".

### Gaps
- No source quantified failure rates of agent-triggered deploys or the reliability of two-window canary rules; thresholds above are practitioner heuristics.
- The DORA seven-capability list could not be verified from the report text (dora.dev blocked); treat the list as likely but unconfirmed.
- Google SRE book chapters on release engineering/change management were not fetched (sre.google blocked).

## A5. Multi-host visibility: inventory, health, deployed versions, logs, SSH identity for an agent

### Takeaway
Hosted agent platforms track exactly three things per executing host: liveness (poll/heartbeat with a lease), who/what is running there (owner lock, session id), and a trusted identity for the process (short-lived scoped token). For a single operator the equivalent is a small host registry in the engine, a heartbeat per runner, the existing per-project deployed-version probe extended per environment, and SSH identities that are short-lived or forced-command.

### Cited Findings
- Claude Code self-hosted runner liveness model: polling "doubles as the heartbeat"; "If the runner stops polling, its lease lapses after about 60 seconds. The server can then take a few minutes ... to requeue the session"; each poll has a 10-second timeout and failures back off "up to 20 seconds"; a signal-less host kill "is indistinguishable from a crash: the control plane records a lost worker rather than a clean release"; `--retire-at` lets a runner "stop taking new work" and release sessions before a known kill time. The reference page lists "every CLI flag, environment variable, metric, and the health endpoint." — [Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)
- Runner identity: sessions authenticate with "an Anthropic-issued, session-scoped OAuth token" with "a lifetime of about 30 minutes" that "the runner re-mints before expiry"; a session JWT carries an `act` claim (creator) and `CLAUDE_RUNNER_CLIENT_PLATFORM` records the creating surface (`web_claude_ai`, `scheduled_trigger`, ...) "once at session creation, so the wrapper and every lifecycle hook see the same value." Separate page "Verify session identity: validate the session token from your own services before granting access." — [Customize sessions in self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments-configuration); [Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)
- Cross-session listing shows how a product exposes fleet state to an agent: `/list-agents` shows "Your Remote Control sessions on other machines ... labeled `Remote Control`" and "shows `offline` as the status of a session whose Remote Control connection has dropped"; session names default to the hostname prefix. — [Message your other Claude Code sessions](https://code.claude.com/docs/en/cross-session-messaging); [Remote Control](https://code.claude.com/docs/en/remote-control)
- Pact Broker's environment model is a minimal "what version is deployed where" registry: `record-deployment --pacticipant X --version N --environment production`, and `can-i-deploy --to-environment` reads it. — [pact-foundation/docs.pact.io: can-i-deploy](https://raw.githubusercontent.com/pact-foundation/docs.pact.io/master/website/docs/pact_broker/can_i_deploy.md)
- Backstage models deployed/runtime things as `Resource` entities with `spec.type`, `spec.owner`, `spec.dependsOn`, and components carry `spec.lifecycle` (`experimental`, `production`, `deprecated`). — [backstage/backstage: descriptor format](https://raw.githubusercontent.com/backstage/backstage/master/docs/features/software-catalog/descriptor-format.md)
- Renovate's dependency dashboard is a per-repo issue listing PRs "pending, open, closed (unmerged) or in error", and `dependencyDashboardApproval: true` makes Renovate "wait for manual approval from within the Dependency Dashboard" before creating branches; a third-party tool scrapes many repos to track "the Renovate onboarding status of the repositories, over time" (fleet-level view). — [renovate-pr-visualization](https://github.com/MShekow/renovate-pr-visualization/)
- SSH identity for automation (search snippets): Teleport Machine ID issues short-lived SSH certs that "automatically expire, there is no need to revoke them"; Tailscale SSH does identity-based auth with ACL `ssh` rules (`action: accept|check`, `checkPeriod`); Docker contexts over SSH require "key-based authentication". — [Teleport Machine ID SSH](https://goteleport.com/docs/machine-id/access-guides/ssh/); [Tailscale blog: Tailscale SSH](https://tailscale.com/blog/tailscale-ssh); [Docker blog](https://www.docker.com/blog/how-to-deploy-on-remote-docker-hosts-with-docker-compose/)

### Inferences
- A **host registry** in `config.json` (`hosts: { prod-1: { ssh: "neo-deploy@...", dockerContext: "prod-1", env: "prod", projects: [...] } }`) plus a `host:<name>` ledger row (last heartbeat/probe, agent version, docker version) is enough fleet inventory for a few servers; it reuses the existing probe/scan producers and attention items (ADR-0018) for "host unreachable" and "N commits not deployed to prod".
- Extend `deploy:<project>` to `deploy:<project>:<env>` by letting each environment declare its own `deployedVersionUrl`; the dashboard then shows dev/staging/prod drift per project deterministically.
- Log aggregation for a few hosts does not need a stack: an engine tool `prod.logs(project, since)` that runs `docker compose logs --since` over the forced-command SSH key and stores the tail in the ledger is enough for a worker to diagnose from logs alone (the CLAUDE.md "log enough that an agent can diagnose any failure from logs alone" rule).
- SSH identity: one `neo-deploy` user per prod host, `authorized_keys` with `command="/usr/local/bin/neo-deploy-shim"` and `restrict`, where the shim accepts only `pull|up|rollback|logs|health <project>`. Short-lived certs (Teleport/step-ca) are the upgrade path if hosts multiply; Tailscale SSH `check` is the cheap human-re-auth gate for the operator's own break-glass access.

### Gaps
- No source describes log aggregation specifically for agent diagnosis across hosts; the "tool that tails over SSH" is an inference.
- Tailscale's official SSH KB page could not be fetched; `accept`/`check` semantics are from Tailscale's blog and advisory via snippets.

## B1. Dependency awareness: catalogs, a machine-readable project registry, contracts, contract tests

### Takeaway
Backstage's descriptor format is the de-facto schema for a machine-readable service registry (Component/API/Resource/System with `dependsOn`, `providesApis`, `consumesApis`, `lifecycle`, `owner`), and Pact's broker/matrix is the de-facto mechanism for *verifying* that a dependency change is safe to deploy. For Neo, a `catalog-info.yaml`-shaped file per project plus a Pact-style "which version is in which environment" table gives the engine deterministic answers to "who depends on this" and "can this ship".

### Cited Findings
- Backstage descriptor format (official, via repo mirror): kinds are **Component** ("a software unit, usually tied to source code and a deployable or linkable artifact"), **API** ("in formats such as OpenAPI, AsyncAPI, GraphQL, or gRPC"), **Resource** ("databases, topics, buckets, or CDNs"), **System**, **Domain**, **Location**. Component spec: `type` (required; `service`, `website`, `library`), `lifecycle` (required; `experimental`, `production`, `deprecated`), `owner` (required), `system`, `subcomponentOf`, `providesApis`/`consumesApis` (refs default to kind `API`), `dependsOn`/`dependencyOf` (refs to Component or Resource). API kind requires a `definition`. Reference forms: `group:default/dev.infra`, `<namespace>/<name>`, or a bare name using the field's default kind. Annotation `backstage.io/managed-by-location` records where the descriptor came from. — [backstage/backstage: descriptor format](https://raw.githubusercontent.com/backstage/backstage/master/docs/features/software-catalog/descriptor-format.md)
- Caveat on dangling references (search snippet): "there's no guarantee those referenced entities actually exist in your catalog, so a dangling `dependsOn` target is a real risk." — [Graham Brooks: exploring your Backstage catalog without Backstage](https://www.grahambrooks.com/post/exploring-your-backstage-catalog-without-backstage/)
- Thoughtworks Radar technique: "automatically generate Backstage entity descriptors" rather than hand-maintaining them. — [Thoughtworks Radar](https://thoughtworks.com/radar/techniques/automatically-generate-backstage-entity-descriptors)
- Pact matrix and `can-i-deploy` (official via mirror): the matrix is "a grid of consumer and provider versions that have been tested against each other"; `can-i-deploy` exits 0/1; `--to-environment` compares against "recorded deployments"; without it, the check uses "the overall latest versions of the other applications." — [pact-foundation/docs.pact.io: can-i-deploy](https://raw.githubusercontent.com/pact-foundation/docs.pact.io/master/website/docs/pact_broker/can_i_deploy.md)
- Pipeline pitfall (search snippet): "the consumer build can fail if the check runs before the provider has published its verification results", mitigated by retries or a separate contract-test job "run before deploying the provider to production." — [dev.to/kreuzwerker: Pact Broker and Jenkins](https://dev.to/kreuzwerker/integrating-contract-tests-into-build-pipelines-with-pact-broker-and-jenkins-132k)
- Monorepo vs polyrepo for agents (search snippet; dortort.com unreachable): "AI coding agents currently lack standardized tooling for orchestrating changes across multiple repositories as a single logical transaction." — [Dortort: monorepo vs multi-repo, why AI agents tip the scale](https://dortort.com/posts/monorepo-vs-multi-repo-why-ai-agents-tip-the-scale/)
- GitHub staff on cross-repo agent work (fetched): "clear interfaces and versioning" and "contract-first design, a parent issue with scoped sub-issues that include shared contracts" are the recommended prerequisites; "an integration environment (e.g., docker-compose or staging) or mocks" for verification. — [GitHub community discussion #186469](https://github.com/orgs/community/discussions/186469)
- Devin scopes knowledge per repo: "Knowledge is also scoped per repo, so Devin only sees the knowledge entries for the one it's working on", with three pinning modes "no repo, a specific repo, or all repos." (search snippet) — [Devin docs: environment blueprints](https://docs.devin.ai/onboard-devin/environment/blueprints); [fast.io: Devin Knowledge guide](https://www.fast.io/resources/devin-knowledge-guide.md)
- Claude Code Projects attach repos explicitly and advise "Add the repositories most tasks need rather than every one the work might touch"; threads get "the `CLAUDE.md` in each of the project's repositories, but not the repositories' skills, `.claude/settings.json`, or `.mcp.json`." — [Projects](https://code.claude.com/docs/en/claude-projects)

### Inferences
- Neo should adopt a **`neo.yaml` (or `catalog-info.yaml`) per project folder**, read by the engine's scan producer, with the Backstage field names so it stays tool-compatible: `kind`, `spec.type`, `spec.lifecycle`, `spec.owner`, `spec.providesApis`, `spec.consumesApis`, `spec.dependsOn`, plus Neo-specific `environments: {dev: {host, deployedVersionUrl}, prod: {...}}`. The engine validates references on scan (dangling `dependsOn` = attention item) so the registry cannot silently rot.
- With that registry the engine can compute, deterministically and without AI, the **blast radius of a change**: `dependencyOf` closure of the touched project, which becomes (a) the list of projects to notify (B4), (b) the list of consumers whose contract tests must pass before a `proposed` deploy can be `approved` (A4), and (c) the default ordering for a coordinated change (B2).
- Contracts: require `providesApis` entries to point at a checked-in OpenAPI/GraphQL/proto file; a change to that file is the deterministic trigger for the cross-project flow in B2. A full Pact Broker is probably more than a single operator wants; a ledger table `deployed(project, env, version)` plus "consumer contract tests pass against the deployed provider version" reproduces `can-i-deploy` for a handful of services.

### Gaps
- No source compared the cost of running a real Backstage/Pact Broker for a one-person operation; the "ledger table instead of broker" is an inference.
- Schema-registry (Confluent-style) sources were not consulted; only OpenAPI/GraphQL/gRPC are covered via Backstage's API kind.

## B2. Coordinated changes across repos: how products model it, and how to sequence and verify

### Takeaway
As of 2026 no mainstream hosted coding agent executes a cross-repo change as one transaction: GitHub Copilot's coding agent is single-repo ("on the roadmap"), Devin and Claude Code run one session per repo and coordinate above it, and Sourcegraph Batch Changes is the only mature "one spec, many repos, tracked PRs" tool. The working pattern everyone lands on is contract-first, one thread per repo, PRs merged in dependency order, with a coordinator (human or agent) reconciling mismatches and an integration environment to verify.

### Cited Findings
- GitHub community thread (fetched; Feb-Apr 2026): "Background agents appear limited to a single repo and git worktree"; GitHub architect samsmithnz: repo-specific sub-tasks are "currently the most effective approach", run "sequentially on each sub-task, then testing integration points last", multi-repo "on the roadmap"; devopsjester: "Multi-repo orchestration by one agent isn't available yet ... splitting by repo and merging PRs in dependency order"; UkashaMeer: "having the backend agent write a markdown prompt file describing the frontend changes, then handing that file to the frontend agent"; andifry7: "background agents are good for execution, not orchestration." No official multi-repo feature announced as of Apr 28, 2026. — [GitHub community discussion #186469](https://github.com/orgs/community/discussions/186469)
- A second GitHub thread (search snippet, Mar 2026): "Copilot Coding Agents are sandboxed to a single repository." — [GitHub community discussion #190627](https://github.com/orgs/community/discussions/190627)
- Claude Code Projects: "One goal across many repositories: 'Bring every service up to the new lint config.' Claude can run a thread per repository, each with its own pull request, and the Overview pane shows which ones are ready for review"; "decisions you ask Claude to remember early on reach the later cloud threads"; threads watch their PR with auto-fix and offer "Resolve conflicts, Fix CI, Address comments, and Merge it" buttons. — [Projects](https://code.claude.com/docs/en/claude-projects)
- **Sourcegraph Batch Changes** (official YAML reference via repo mirror): `on` selects repos by `repositoriesMatchingQuery` or explicit `repository` (+ `branch`); `steps` run "in each matched repository" with `run`, `container` ("Docker image ... must include /bin/sh"), `outputs` reusable "in later steps and in `changesetTemplate`"; `changesetTemplate` defines `title`, `body`, `branch`, `commit`, and `published` which can be `false`, `draft`, `true` or a glob-keyed array where "the last matching rule wins, and unmatched repositories stay unpublished"; "Progression is one-way: unpublished, then draft, then published"; `importChangesets` tracks existing PRs by `externalIDs`; "A changeset is uniquely identified by its repository and branch." The UI shows "a burndown chart" of merged changesets. — [sourcegraph/docs: batch spec YAML reference](https://raw.githubusercontent.com/sourcegraph/docs/main/docs/batch-changes/batch-spec-yaml-reference.mdx); [Sourcegraph 6.0 Batch Changes](https://6.0.sourcegraph.com/batch-changes)
- Renovate fan-out gate: `dependencyDashboardApproval: true` makes Renovate "no longer create branches/PRs automatically but instead wait for manual approval from within the Dependency Dashboard." (search snippet) — [renovate-pr-visualization README](https://github.com/MShekow/renovate-pr-visualization/)
- Stacked PRs: Graphite's merge queue is "stack-aware" and "merges the pull requests in a controlled, sequential order based on their dependency chain"; no source confirmed stacks spanning multiple repositories. (search snippet) — [Graphite: complex dependency management](https://graphite.dev/use-cases/complex-dependency-management)
- Devin multi-repo (search snippets): guidance is "create one Shortcut for each repo"; the CLI "lists a repeatable `--repo` flag for attaching repo URLs"; advanced mode "can break large tasks into parallel workstreams". — [fast.io: Devin docs map](https://fast.io/resources/devin-ai-docs-guide/); [Devin docs: advanced capabilities](https://docs.devin.ai/work-with-devin/advanced-capabilities)
- Parallel-agent isolation warning (search snippet): "two coding agents pointed at the same repository will happily overwrite each other's work. Git worktrees help, but all worktrees still share the same underlying object database and refs." — [GitKraken: parallel AI coding across repos](https://gitkraken.com/blog/7-best-tools-for-parallel-ai-coding-across-repos-2026)
- Cross-session messaging as the coordination channel: "When a change in one session breaks what another is building on, Claude can warn that session before you notice"; "Coordinate parallel worktrees ... Claude can tell the other sessions what landed." — [Message your other Claude Code sessions](https://code.claude.com/docs/en/cross-session-messaging)

### Inferences
- Model a cross-project change in Neo as a **change-set** record (Sourcegraph's vocabulary): `changeset{ id, cause, contract_diff, legs: [{project, branch, pr, state}], order }`. The engine, not the worker, computes `order` from the registry (`providers before consumers`), opens legs as separate dispatches, holds consumers until the provider leg's PR is merged and deployed to the target environment, and marks the whole change-set `done` only when every leg is merged. This is the "batch spec + changesetTemplate + published progression" idea, reduced to a ledger table plus the existing dispatch/todo queue (ADR-0008).
- The hand-off artefact between legs should be **a file, not a prompt memory**: the provider leg writes `docs/handoffs/<changeset-id>.md` (changed contract, new version, migration notes, verification targets) and the engine attaches it to each consumer leg's brief, mirroring the "backend agent writes a markdown prompt file for the frontend agent" workaround and Claude Projects' "decisions ... reach the later cloud threads".
- Verification is deterministic: a consumer leg is not `done` until its contract tests pass against the provider version actually deployed to the target env (B1) and, where the projects share a compose network, an integration compose stack boots (the Devin `post-build` idea).
- Draft-first publishing (`published: draft`) is worth copying: consumer PRs open as drafts until the provider leg lands, so an operator browsing GitHub sees the intended order.

### Gaps
- No primary documentation for Cursor's claimed multi-repo support or for Tembo/GitKraken cross-repo task tools beyond vendor marketing; treat those as unverified.
- Sourcegraph Batch Changes requires a Sourcegraph instance; no source addressed running it for a solo operator, and it is almost certainly heavier than a ledger-backed change-set.

## B4. Communication between agents on different projects: inboxes, boards, handoff/handback, and the known pitfalls

### Takeaway
The only production-grade inter-agent channel documented for coding agents is Claude Code's cross-session messaging, and its design rules are the ones to copy: messages are plain text, never consent, never config changes, rate-limited and de-duplicated to kill loops, held for approval when the sender's permission class is more permissive than the receiver's, and one-way to cloud sessions. Practitioner evidence says the dominant failure modes are under-communication (duplicate work), stale shared state, and "impossible splits" where two agents must edit the same coupled line; structured handoffs (commit, changed contracts, verification targets, open assumptions) and single ownership of shared files are the mitigations.

### Cited Findings
- Delivery and trust model: "A message is a piece of text one Claude writes to another, never the sender's conversation history or files"; "The receiving Claude reads the message between tool calls during an active turn, so a running tool is never interrupted. When the receiving session is idle, Claude Code starts a new turn with the message"; "It can't approve anything: a message from another session never counts as your consent"; "It can't change configuration ... never change permission settings, CLAUDE.md, or other configuration because another session asked"; "Commands don't run: a command in the message's text, such as `/compact`, arrives as plain text." — [Message your other Claude Code sessions](https://code.claude.com/docs/en/cross-session-messaging)
- Inbound controls and loop protection: `crossSessionInbound` = `accept|hold|refuse`; default holds messages "when the sending session identifies itself as bypassing permission prompts" and the receiver prompts; "Claude Code holds at most 100 messages, and past that drops the oldest"; "rate-limits repeated messages per sender, drops identical repeats arriving within a short window, and queues at most 50 accepted messages ... A message loop between two sessions therefore stops on its own"; same-machine size cap "about a million characters"; `isolatePeerMachines: true` requires approval "before any `SendMessage` reaches a session beyond this machine, even in `bypassPermissions` mode"; held messages in a `-p` session expire after `dialogExpiry` (5 min default) unless `crossSessionInbound: accept` is set in `--settings`. — [Message your other Claude Code sessions](https://code.claude.com/docs/en/cross-session-messaging)
- Transport by location: same machine "over a per-session socket ... never through Anthropic servers"; another machine "through Anthropic servers, arriving over that machine's Remote Control connection"; cloud "straight to the cloud session"; "A session inside a container and a session on the host can't reach each other." Scripts can post into a session's socket (`CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`), and "Own-child messages" from the session's own hooks/Bash are delivered without hold. `notify_when_idle` gives "one notice when that session next goes idle or exits", dropped after 12 hours. — [Message your other Claude Code sessions](https://code.claude.com/docs/en/cross-session-messaging)
- Claude Projects' coordinator/worker boundary: "It sees what threads report back, not every step they take"; threads "report back to the conversation when it finishes"; the Overview shows "Waiting on you". — [Projects](https://code.claude.com/docs/en/claude-projects)
- Practitioner lessons (search snippets; dev.to/arxiv unreachable): "when agents share too little about progress or decisions, others repeat work or make conflicting choices"; "conflicting edits, stale reads, and inconsistent assumptions if versioning is weak"; "assign bounded work with clear owners, isolate editing workspaces and runtime resources, and track dependencies in shared run state"; a research taxonomy (arXiv 2607.28802) describes "two agents that agreed not to touch each other's lines, yet both had to change the same coupled line ... an impossible split rather than a communication failure"; "two agents can safely edit different parts of one file, while changes in different files can still conflict semantically"; suggested handoff contents are "the commit, changed contracts, verification targets, and open assumptions", and "the hard part is making those declarations cheap enough that agents don't skip them." — [avahi.ai: inter-agent communication](https://avahi.ai/glossary/inter-agent-communication/); [arXiv 2607.28802: Model or Harness?](https://arxiv.org/pdf/2607.28802); [DEV: parallel coding agents need handoffs](https://dev.to/demivalerith/parallel-coding-agents-need-handoffs-not-more-terminals-71d); [DEV: run multiple coding agents without conflicting changes](https://dev.to/prinevo/how-to-run-multiple-coding-agents-without-conflicting-changes-1ipi)
- Open-source inbox/handoff tools (search snippets): `handback` "saves worker replies to an inbox for a lead to review and treats agent messages as task information rather than user authorization"; `agent-handoff` is "a shared inbox for Claude Code and Codex"; `agent-comm` "serializes file edits so parallel agents don't clobber each other." — [PyPI: handback](https://pypi.org/project/handback/); [zzyyfff/agent-handoff](https://github.com/zzyyfff/agent-handoff); [agent-comm MCP](https://glama.ai/mcp/servers/keshrath/agent-comm/tree)
- One-conversation-per-task lesson (search snippet): a second agent "interpreted [a feature request] differently, which broke another page ... keep one place for the current task, and give parallel work a clear handoff." — [flaviocopes: too many agent conversations](https://flaviocopes.com/too-many-agent-conversations/)
- Channels show the inbound-event allowlist pattern for an engine: "Every approved channel plugin maintains a sender allowlist: only IDs you've added can push messages"; "Being in `.mcp.json` isn't enough to push messages: a server also has to be named in `--channels`." — [Channels](https://code.claude.com/docs/en/channels)

### Inferences
- Neo should **not** rely on Claude Code's cross-session sockets (SDK workers are headless, per-dispatch, often in bare mode, and containers cannot reach the host). The engine is already the message bus: add an `inbox:<project>` ledger collection where any worker can `post(to_project, text, cause)` through an engine MCP tool, and the engine delivers it as the *next brief's* preamble (or a `/todo` queue item, ADR-0008) for that project. Copy the Claude Code rules verbatim into code: plain text only, never consent, never config, dedupe identical messages within a window, cap queue at 50, rate-limit per sender, and hold cross-environment messages (e.g., from a customer-tainted path) for operator approval.
- Handback: every dispatch already reports to its dispatcher (ADR-0007); make the report a structured **handoff record** with the four fields the practitioner literature agrees on (commit/branch, changed contracts, verification targets, open assumptions) so the engine can forward it to dependents (B1 closure) without a model in the loop.
- Pitfall controls that are deterministic: (1) one project folder = one writer at a time (Neo's per-folder session isolation and todo queue already do this); (2) a change-set (B2) names the single owner of each shared contract file; (3) "impossible split" detection = the engine refuses to open two legs that both list the same file in `touches` and asks the operator to merge them into one leg.
- The Telegram operator channel stays the human "Waiting on you" board; the engine's attention items (ADR-0018) are the shared board between projects. No second board tool is needed.
