# Multi-project orchestration and governance of coding-agent work (single operator, self-hosted, chat-steered)

Research date: 2026-11-02. Scope: how agent products/frameworks and ops practice handle work queues, parallelism, orchestrator/worker patterns, scheduling, budgets, observability, permissions and failure recovery when one operator runs headless coding-agent workers across many repos on one server.

Method note: primary documentation was fetched in full for Claude Code / Agent SDK (code.claude.com) and the Claude Platform rate-limit page. The following hosts were **not reachable from this session's network allowlist** and could only be covered through search-result snippets (lower confidence, marked "snippet" below): developers.openai.com, learn.chatgpt.com, docs.devin.ai, docs.github.com, arxiv.org, addyosmani.com, augmentcode.com, opentelemetry.io.

## 1. Work model: per-project queues vs global board; goals → tasks → verifier; priorities; dependencies

### Takeaway
Shipping products converge on a *goal-first, task-list-second, verifier-third* shape: a shared task list with pending/in-progress/completed states and explicit dependencies (blocked until deps complete), tasks claimed under a lock, and a separate model-based evaluator (not the worker) deciding whether the goal is met. Issue trackers (Linear, GitHub) act as the global board; the coding agent is an *additional contributor* on a human-owned ticket, never the owner.

### Cited Findings
- Claude Code agent teams coordinate through "a shared task list" where "Tasks have three states: pending, in progress, and completed. A task can also depend on other tasks and shows as blocked in the task list until they're completed. Teammates don't self-claim a blocked task, but you or the lead can still assign it." — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- "Task claiming uses file locking to prevent race conditions when multiple teammates try to claim the same task simultaneously." Dependencies unblock automatically: "when a teammate completes a task that other tasks depend on, it unblocks the dependent tasks without any action from you." — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Task list storage is a plain directory `~/.claude/tasks/{team-name}/` that "stays on disk after the session ends"; team config `~/.claude/teams/{team-name}/config.json` is deleted at session end. — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Known failure of the board: "Task status can lag: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks. If a task appears stuck, check whether the work is actually done and update the task status manually." — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Sizing guidance: "Start with 3-5 teammates for most workflows... If you have 15 independent tasks, 3 teammates is a good starting point"; "Having 5-6 tasks per teammate keeps everyone productive and lets the lead reassign work if someone gets stuck." — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Goal/verifier separation: `/goal` "adds a separate evaluator that checks your condition after every turn, so completion is decided by a fresh model rather than the one doing the work." The evaluator "doesn't run commands or read files independently, so write the condition as something Claude's own output can demonstrate." Verdicts: "Not yet met / Met / Impossible". Use case listed: "Working through a labeled issue backlog until the queue is empty." — [Claude Code: /goal](https://code.claude.com/docs/en/goal)
- Goal anti-stall: "If Claude keeps answering the evaluator without making progress (no tool use for several turns in a row), Claude Code stops the loop, prints a warning, and returns control to you." Bounding: "include a turn or time clause in the condition, such as `or stop after 20 turns`." — [Claude Code: /goal](https://code.claude.com/docs/en/goal)
- Linear as the board: "the assignee stays accountable. The agent is added as an additional contributor working on your behalf"; delegation via the Assignee field or pressing `A`; "Rules can also delegate issues to an agent as part of the same flow... during triage" (triage routing is Enterprise). — [Linear docs: AI agents](https://linear.app/docs/agents-in-linear); [Linear: Assign and delegate issues](https://linear.app/docs/assigning-issues)
- Linear's built-in coding session "runs through Claude Code or Codex, then drafts a PR and adds a diff to the issue for you to check before requesting review." — [Linear: Coding sessions](https://linear.app/enablement/guide/coding-sessions)
- GitHub Copilot coding agent (snippet, secondary): assigning an issue makes Copilot "create a `copilot/*` branch from your default branch, push commits as it works, and open a draft PR"; it "has read-only access to the repository and can only push to branches starting with copilot/"; draft PRs "require human approval before any Actions workflows run." — [DEV: Assign to Copilot explained](https://dev.to/thelogicwarlock/assign-to-copilot-explained-what-githubs-coding-agent-actually-does-59g9); [morphllm: Copilot coding agent 2026](https://www.morphllm.com/copilot-coding-agent)
- Devin (snippet, docs summary): "Devin can split a large task into pieces and hand them to a group of managed sessions, each in its own isolated VM"; example: "find the under-coverage modules, then start one session per module using a test-writing playbook, opening a PR for each"; you "can wait for all of them to finish in a single call instead of polling individually." Playbooks are reusable prompts; "automation macros can be attached to playbooks for trigger-based workflows." — [Devin docs: Advanced capabilities](https://docs.devin.ai/work-with-devin/advanced-capabilities); [Devin docs: Creating playbooks](https://docs.devin.ai/product-guides/creating-playbooks)
- Codex cloud (snippet): "start work in parallel and return as each task reaches a reviewable result"; "comparing several attempts" is a listed use case; third-party guides describe `codex cloud exec --env ENV_ID --attempts 3` with attempts 1-4, each in its own container. — [Codex cloud docs](https://learn.chatgpt.com/docs/cloud); [Daniel Vaughan: Codex best-of-N](https://codex.danielvaughan.com/2026/04/01/codex-cloud-exec-best-of-n-attempts/)
- Anthropic's orchestrator research: "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; without them "agents duplicate work, leave gaps, or fail to find necessary information." Effort budgets are encoded in the brief: "Simple fact-finding requires just 1 agent with 3-10 tool calls"; complex work "might use more than 10 subagents with clearly divided responsibilities." — [Anthropic: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- Per-project queues and a global board are not alternatives: products keep the *board* in the tracker (global, human-owned) and materialise a *per-run task list* (local, file-backed, lock-claimed) for the workers. An engine like Neo should treat its per-project todo queue as the worker-facing list and expose a cross-project "board view" purely as a read model.
- The verifier should be a distinct, cheaper model call that reads only what the worker surfaced (transcript evidence), plus deterministic checks (tests/exit codes) via hooks — exactly the `/goal` + Stop-hook split.
- Expect task-status lag as a steady-state bug; the engine needs a reconciliation sweep ("is the work actually done?") rather than trusting worker-reported completion.

### Gaps
- No primary documentation on Devin's queue semantics (priorities, dependencies) was reachable; only playbook/parallel-session summaries.
- No source documents priority levels inside Claude Code's task list; "priority" appears only in Linear/issue-tracker fields.

## 2. Parallelism and isolation: worktrees, branch naming, containers/VMs, merge conflicts, merge queues, measured limits

### Takeaway
Git worktrees per task/session are the de-facto isolation primitive (Claude Code, Dagger Container Use, GitHub Copilot desktop, Conductor); cloud products use a VM/container per task plus a dedicated branch prefix (`claude/`, `copilot/`, Cursor "fresh branch from main"). Worktrees isolate files but not runtime (ports, DBs, shared `.git`), and practical ceilings reported are 3-5 agents per reviewer/laptop; one paper reports 12 concurrent sessions on a 48 GB Mac with no conflict reaching main. Integration is the bottleneck, which is where merge queues (speculative batching) come in.

### Cited Findings
- Claude Code `--worktree <name>` creates `.claude/worktrees/<name>/` "on a new branch named `worktree-<name>`"; default base is "the repository's default branch on the remote" (`worktree.baseRef: "fresh"`) or `"head"` for in-progress work. `.worktreeinclude` copies gitignored files such as `.env` into every new worktree. — [Claude Code: Worktrees](https://code.claude.com/docs/en/worktrees)
- Isolation enforcement is in code, not prompts: Claude Code "blocks an `Edit`, `Write`, or `NotebookEdit` that targets a path in the main checkout", blocks commands whose cwd resolves to the main checkout, blocks git redirects (`git -C`, `GIT_DIR`, `GIT_WORK_TREE`, `cd`), and blocks commands whose shape it cannot verify ("You can't turn this check off"). Caveat: "None of them tracks which files a shell command writes, so a command that writes into the main checkout without running git there, such as `cp` or a shell redirect, isn't refused." — [Claude Code: Worktrees](https://code.claude.com/docs/en/worktrees)
- Subagents can run in their own worktree via `isolation: worktree` frontmatter; "Each subagent gets a temporary worktree that Claude Code removes automatically when the subagent finishes without changes." Running agents hold a `git worktree lock`; a periodic sweep removes stale worktrees older than `cleanupPeriodDays` but keeps any with "changed or untracked files, or unpushed commits." Non-interactive `-p` runs "have no exit prompt, so Claude doesn't clean up their worktrees." — [Claude Code: Worktrees](https://code.claude.com/docs/en/worktrees)
- Background sessions: "Before editing files, Claude moves the session into an isolated git worktree under `.claude/worktrees/`, so parallel sessions can read the same checkout but each writes to its own." Outside git, "sessions write to the working directory directly and aren't isolated from each other." — [Claude Code: Agent view](https://code.claude.com/docs/en/agent-view)
- What worktrees share: the `.git` directory (sandbox allows those writes), project plugins, and permission approvals ("don't ask again" rules saved to the main checkout's `.claude/settings.local.json` apply in every worktree). — [Claude Code: Worktrees](https://code.claude.com/docs/en/worktrees)
- Agent-teams guidance on same-repo conflicts: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files." — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Cloud scheduled tasks (routines): "Each repository you add is cloned on every run. Claude starts from the repository's default branch unless your prompt specifies otherwise"; "Claude pushes its work to a branch prefixed with `claude/` unless your prompt directs it to push to another branch. To control which branches a run can push to, use branch protection rules or rulesets on GitHub." — [Claude Code: Scheduled tasks (cloud)](https://code.claude.com/docs/en/routines)
- Cursor cloud agents (snippet): "run in isolated VMs in the cloud rather than on a local machine... (cloned repos, dependencies, secrets, and network access)"; "It cuts a fresh branch from main, works there, and you decide whether to merge." Workers can now be "a Cursor cloud machine, a self-hosted pool your org runs, or one of your own machines." — [Cursor docs index](https://docsearch.algolia.com/mcp/docs/website/cursor.com); [crystl: Cursor background agents](https://crystl.dev/blog/cursor-background-agents-vs-crystl/)
- Dagger Container Use: gives "each AI coding agent its own containerized sandbox and Git worktree. Developers can run several agents on one codebase without them interfering"; an "open-source MCP server" configurable with Claude Code, Cursor, etc. — [container-use.com](https://container-use.com); [InfoQ: Container Use](https://www.infoq.com/news/2025/08/container-use)
- GitHub Copilot desktop (snippet): "each session runs in its own git worktree"; June 2026 public preview of "cloud sandboxes... a fully isolated, ephemeral Linux environment hosted by GitHub" and "local sandboxes... built on Microsoft's MXC isolation layer." — [IT Brief: Copilot desktop app](https://itbrief.co.uk/story/github-launches-copilot-desktop-app-for-agentic-work)
- Measured/reported limits: "3-4 parallel agents when a single reviewer integrates the results" — [Augment Code guide](https://www.augmentcode.com/guides/how-to-run-a-multi-agent-coding-workspace); "4-5 worktrees is a practical ceiling on a modern laptop... each worktree with an AI agent running a build can consume roughly 2-4GB of RAM" — [developersdigest: Worktrees + Claude Code](https://www.developersdigest.tech/blog/git-worktrees-claude-code-parallel-agents-guide); "Worktrees isolate code but not runtime. Parallel agents still share ports, databases, and external services"; advise to "serialize commit, fetch, and pull operations across worktrees." — [Upsun: worktrees for parallel agents](https://developer.upsun.com/posts/ai/git-worktrees-for-parallel-ai-coding-agents)
- Glite ARF paper (snippet, arXiv): "up to twelve agent sessions running simultaneously on a single 48 GB Mac, with no merge conflict reaching main", using a verifier-driven loop. — [arXiv 2606.27416](https://arxiv.org/pdf/2606.27416)
- Merge queues: GitHub's native queue lets you "Select the minimum and maximum number of pull requests to merge into the base branch at the same time (between 1 and 100), and a timeout after which the queue should stop waiting for more entries." — [GitHub Docs (GHES): Managing a merge queue](https://docs.github.com/en/enterprise-server@3.17/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue); a practitioner post reports defaults of min group 1, 5-minute wait, max batch 5 (secondary). — [humanwhocodes: GitHub merge queue](https://humanwhocodes.com/blog/2026/04/improving-developer-velocity-github-merge-queue)
- Speculative checks "test multiple PRs in parallel by assuming earlier PRs will pass"; batching failures use a bisection "search to isolate the culprit"; "if your hit rate drops below 80%, dial depth down." Bors "has no speculative checks." — [Mergify: speculative merging](https://mergify.com/learn/merge-queue/speculative-merging); [Nirvana: cut PR merge time by 92%](https://nirvanatech.com/blog/we-cut-pr-merge-time-by-92-heres-the-system-we-built-to-do-it)
- Agent-teams docs also note hidden cost of in-process parallelism: "An in-process teammate's requests fall outside the main conversation's cache TTL bucket, so its cache holds for five minutes by default." — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)

### Inferences
- For a single-server engine: one worktree per task under a fixed prefix, branch named by `<prefix>-<task-id>`, `.worktreeinclude`-style env propagation, and a *serialized git mutex per repo* (fetch/commit/push) are the minimum. Runtime collisions (ports/DB) need per-task env (e.g. `PORT` offsets or Docker compose project names), which worktrees alone do not solve.
- Conflict avoidance is mostly *partitioning by file ownership at brief time*; conflict resolution is a merge-queue/rebase step owned by the engine, not the worker.
- The reported 3-5 agent ceiling is a human-review ceiling, not a machine ceiling; with a verifier and merge queue the machine ceiling is ~10+ (paper evidence), but reviewing throughput still bounds it.

### Gaps
- No controlled benchmark found that measures merge-conflict rate vs number of parallel agents on one repo; only anecdotal ceilings and one paper abstract.
- Could not fetch GitHub's current (github.com) merge-queue defaults; only GHES docs and a blog.

## 3. Orchestrator/worker patterns: lead-writes-briefs vs deterministic router; handoff/handback; fan-out; known pitfalls

### Takeaway
Two documented patterns coexist: (a) an LLM lead that decomposes and writes briefs (Claude agent teams, Anthropic research system) and (b) deterministic dispatch where only the worker is an LLM (Claude routines/GitHub triggers, Linear delegation). The lead pattern is expensive (~7-15x tokens) and has well-documented failure modes: duplicated work from vague briefs, over-spawning, premature "done", lost context in handoffs, and results that never get recorded. Handback in Claude's stack is explicit: subagents return a result to the caller; teammates send an idle notification with their final answer; nothing is delivered unless the mailbox write succeeds.

### Cited Findings
- Subagents vs teams: "Subagents report results back to the main agent. In agent teams, teammates share a task list, claim work, and communicate directly"; token cost "Lower: results summarized back" vs "Higher: each teammate is a separate Claude instance." Teams require an interactive session: "In non-interactive mode with the `-p` flag, including Agent SDK sessions, Claude doesn't spawn teammates." — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Handback mechanics: "when a teammate finishes and stops, it automatically notifies the lead and includes its final answer in the notification. A teammate whose turn ends on an API error notifies the lead that it failed and includes the error text." Mailboxes are JSON files `~/.claude/teams/{team}/inboxes/{agent}.json`; "Claude Code reports a message as sent only when the write to the recipient's mailbox file succeeds." — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Lead pitfalls documented: "Sometimes the lead starts implementing tasks itself instead of waiting for teammates"; "The lead can stop early too, deciding the team is finished before all tasks are actually complete"; "Teammates may stop after encountering errors instead of recovering." Also "No nested teams" and "Lead is fixed." — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Hooks as deterministic gates on the lead/worker loop: `TeammateIdle` (exit 2 "keeps the teammate working"), `TaskCreated` (exit 2 "Rolls back the task creation"), `TaskCompleted` (exit 2 "Prevents the task from being marked as completed"), `SubagentStop` (exit 2 "Prevents the subagent from stopping"). — [Claude Code: Hooks](https://code.claude.com/docs/en/hooks)
- Anthropic's lead-agent lessons: "multi-agent systems use about 15× more tokens than chats"; early versions "spawned 50 subagents for simple queries", "scoured the web endlessly for nonexistent sources", and with vague instructions "one subagent explored the 2021 automotive chip crisis while 2 others duplicated work." Mitigation: filesystem artifacts to prevent "information loss during multi-stage processing"; "deterministic safeguards like retry logic and regular checkpoints"; "resume from where the agent was when the errors occurred." — [Anthropic: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Agent-team cost figure: "Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode." — [Claude Code: Costs](https://code.claude.com/docs/en/costs)
- Fowler's "Orchestrator's Tax": duplication is "agents rebuilding the same mental model of the codebase, which happens when work is split by task rather than by area"; with four subagents "results were arriving out of order" and the session was "harder to reason about than the code." — [martinfowler.com: The Orchestrator's Tax](https://martinfowler.com/articles/orchestrator-tax.html)
- Practitioner pitfalls: "both diffs looked reasonable, but together, they were incompatible"; "context drift... an agent assumes an older API." — [Indie Hackers: give agents structure](https://www.indiehackers.com/post/stop-adding-more-agents-start-giving-them-structure-08ccb25d42); Codex issue: a parent "can prematurely fall back and redo a task that is still being processed successfully by a child agent, wasting tokens and bloating the parent's context." — [Codex issue #16900](https://upd.dev/openai/codex/issues/16900)
- Deterministic trigger→session pattern: GitHub-event routines "doesn't reuse sessions across events, so two PR updates produce two independent sessions." — [Claude Code: Scheduled tasks (cloud)](https://code.claude.com/docs/en/routines)
- Message trust between agents: "Claude Code tells the receiving agent the message came from another Claude session, not from you. A teammate can't approve a permission prompt or supply consent on your behalf, and a teammate that was denied an action can't relay it to another teammate to bypass the check." In auto mode the classifier "treats an approval claim relayed from another agent as untrusted input." — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Cross-session handoff is text-only and bounded: "A message is a piece of text one Claude writes to another, never the sender's conversation history or files"; same-machine messages refused above "about a million characters"; "queues at most 50 accepted messages"; identical repeats in a short window are dropped so "a message loop between two sessions therefore stops on its own." — [Claude Code: Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- SDK handback alternative: "Don't rely on session resume. Capture the results you need (analysis output, decisions, file diffs) as application state and pass them into a fresh session's prompt. This is often more robust than shipping transcript files around." — [Agent SDK: Sessions](https://code.claude.com/docs/en/agent-sdk/sessions)

### Inferences
- A deterministic router (Neo's design) avoids the lead's documented failure modes (over-spawning, early stop, invented scope) at the cost of needing well-structured briefs authored by the operator or a template; where decomposition is genuinely needed, run a *bounded* lead with hooks (`TaskCreated`/`TaskCompleted` gates) and a hard cap on spawn count.
- Handback must be an engine-recorded artifact (result stored on successful write, plus error text on failure), mirroring the mailbox "sent only when written" rule and Anthropic's filesystem-artifact pattern; never rely on the worker's chat summary alone.
- Split work by *area/file ownership* rather than by task to avoid the orchestrator tax.

### Gaps
- No source quantified "lost results" incidents in a coding orchestrator; only the attribution/handoff-context losses above.
- Codex subagent semantics could not be verified from primary docs (host blocked).

## 4. Scheduling and triggers: cron/interval loops, event triggers, trigger→action→goal, observe/dry-run, loop budgets, kill switches

### Takeaway
Claude Code now exposes three tiers — session-scoped `/loop`/CronCreate (ephemeral, jittered, 7-day expiry, 50-task cap), cloud scheduled tasks (schedule + API + GitHub-event triggers, fresh clone per run, auto-mode, hourly caps, on/off switch), and `/goal` (condition-driven, verifier-stopped). Event push into a live session comes via Channels (CI/webhooks/Telegram). Every tier has explicit bounding (expiry, caps, "no catch-up for missed fires") and a kill switch env var.

### Cited Findings
- Session scheduler: "The scheduler checks every second for due tasks and enqueues them at low priority. A scheduled prompt fires between your turns, not while Claude is mid-response"; "A session can hold up to 50 scheduled tasks at once"; "Recurring tasks automatically expire 7 days after creation"; "No catch-up for missed fires... it fires once when Claude becomes idle, not once per missed interval." — [Claude Code: Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)
- Jitter to avoid thundering herd: "a recurring task starts each run late by up to half the gap to the next run, and by at most 30 minutes"; every-5-minutes tasks start "15 seconds sooner" to stay inside the 5-minute prompt cache. — [Claude Code: Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)
- Self-paced loop: Claude "picks a delay between one minute and one hour based on what it observed"; can stop itself via `ScheduleWakeup` with `stop: true`; "If an iteration ends without either rescheduling or stopping, Claude Code schedules one fallback wakeup about 20 minutes later and ends the loop when that iteration doesn't reschedule either." — [Claude Code: Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)
- Built-in maintenance loop scope: "tend to the current branch's pull request: review comments, failed CI runs, merge conflicts... Claude does not start new initiatives outside that scope, and irreversible actions such as pushing or deleting only proceed when they continue something the transcript already authorized." Custom default via `.claude/loop.md` (truncated beyond 25,000 bytes). — [Claude Code: Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)
- Kill switch: "Set `CLAUDE_CODE_DISABLE_CRON=1`... The cron tools and `/loop` become unavailable, and any already-scheduled tasks stop firing." — [Claude Code: Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)
- Tier comparison table: cloud min interval 1 hour, desktop "1 minute when Claude sets it, 1 hour in the forms", `/loop` 1 minute; cloud "Access to local files: No (fresh clone)"; cloud permission prompts "Auto mode by default." — [Claude Code: Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)
- Cloud scheduled tasks triggers: "Schedule... API: trigger on demand by sending an HTTP POST to the task's own endpoint with a bearer token... GitHub: run automatically in response to repository events"; "GitHub webhook events are subject to per-task and per-account hourly caps. Events beyond the limit are dropped until the window resets"; on/off switch: "Paused tasks keep their configuration but don't run"; "Runs on the hour... can start several minutes late... pick a few minutes past the hour, for example 9:07." Example loops: PR review on `pull_request.opened`, library port on `pull_request.closed` filtered to merged, nightly backlog triage. — [Claude Code: Scheduled tasks (cloud)](https://code.claude.com/docs/en/routines)
- Event push into a live session: "A channel is an MCP server that pushes events into your running Claude Code session"; "Webhook receiver: a webhook from CI, your error tracker, a deploy pipeline... arrives where Claude already has your files open"; "Events only arrive while the session is open, so for an always-on setup you run Claude in a background process." Sender allowlist gates everything, and "Anyone who can reply through the channel can approve or deny tool use in your session." In `-p` mode "tools that need terminal input... are disabled so the session never stalls." — [Claude Code: Channels](https://code.claude.com/docs/en/channels)
- Goal check-ins while background work runs: first after 30 minutes, then doubling "up to four times the first interval"; "at most three idle check-ins per goal between your prompts"; configurable via `CLAUDE_CODE_GOAL_CHECKIN_MINUTES` (0 disables). — [Claude Code: /goal](https://code.claude.com/docs/en/goal)
- Background session supervisor: "stops finished or waiting sessions that have been unattached for about an hour. The conversation stays on disk and resumes on the next attach or reply." — [Claude Code: Agent view](https://code.claude.com/docs/en/agent-view)
- Devin automations: playbooks can have "automation macros... for trigger-based workflows" (snippet). — [Devin docs: Advanced capabilities](https://docs.devin.ai/work-with-devin/advanced-capabilities)
- Durable-execution engines for loops: Temporal "re-runs your workflow code and matches it against recorded event history, which is why that code must be deterministic"; Inngest "best if you already think in events, background jobs, webhooks, crons." — [ZenML: Inngest vs Temporal](https://www.zenml.io/blog/inngest-vs-temporal); [noqta: durable execution for agents 2026](https://www.noqta.tn/blog/durable-execution-ai-agents-inngest-trigger-temporal-2026)

### Inferences
- The trigger→action→goal shape Neo already uses matches the industry split: *trigger* (cron/API/GitHub event/channel), *action* (fresh session per event, never reused), *goal* (external evaluator). Copy the bounding rules: expiry on every recurring loop, hourly event caps with drop-not-queue semantics, jitter off the hour, one-fallback-then-stop for self-paced loops, and a single env-var kill switch.
- "Observe/dry-run" is not a first-class mode in any fetched doc; the closest primitives are plan mode (read-only until plan approved) and `dontAsk` (auto-deny prompts). A dry-run loop = plan-mode worker + verifier that only reports.

### Gaps
- Exact numbers for the cloud scheduled-task "hourly cap" and per-account limits were not stated on the page I could read.
- No documentation found for Codex scheduled/automation triggers (host blocked).

## 5. Budget and rate limits: subscription vs API quotas, interactive headroom, backoff, per-task/per-loop accounting

### Takeaway
Subscription plans meter on rolling 5-hour and weekly windows shared across all background work ("Each session uses your subscription quota independently" counts against the same pool), while the API meters per-organization RPM/ITPM/OTPM with token-bucket replenishment and `retry-after` on 429 (not on spend-cap 429s). Claude Code exposes per-loop and per-subagent attribution (`/usage`, OTel `query_source`) and a `--max-budget-usd` cutoff; cache reads are free for ITPM, so keeping workers inside the cache TTL is the biggest throughput lever.

### Cited Findings
- Subscription windows: "each member's Claude Code usage draws from a per-seat allowance that resets on a rolling five-hour window and a weekly window"; limit messages "You've hit your session limit" / "weekly limit" are "shared across all models, so the developer can't restore access by switching models." Claude Code v2.1.234+ can "wait and continue the interrupted task automatically after the reset" (`autoContinueAtUsageLimit`). — [Claude Code: Costs](https://code.claude.com/docs/en/costs)

### Inferences
- On a subscription there is no per-workspace API throttle to reserve interactive headroom, so the engine must implement it itself: track the 5-hour/weekly bars (as `/usage` does from local history), stop dispatching background work above a configured percentage, and treat "usage limit" errors as *pause-until-reset* (not retry), while 529/connection errors get bounded exponential backoff (3 tries then pause).
- Keep loops cheap by (a) firing inside the cache TTL window when a follow-up is imminent, (b) using the small model for verifiers, (c) attributing tokens per loop/task from the `result` message so per-project and per-loop daily caps are enforceable.

## 7. Permissions and safety: allow/ask/deny rules, path fences, pre-tool hooks, sandboxing, secrets, approval scopes, audit trails

### Takeaway
The mature model layers (1) declarative rules (`allow`/`ask`/`deny`, deny always wins, path-scoped `Edit(...)`/`Read(...)`, prefix Bash rules with shell-operator awareness), (2) hooks that can deny/ask/defer before a tool runs (exit 2 blocks; silence never approves), (3) an OS sandbox (bubblewrap/Seatbelt, network namespace + domain-allowlist proxy, protected config paths), and (4) a non-overridable floor ("actions no mode auto-approves") plus agent-to-agent messages that can never carry consent. Approval scopes are once / session / permanent-per-repo, and `tool_decision` events record who decided.

### Cited Findings
- Rule precedence: "A broad deny rule like `Bash(aws *)` blocks every matching call, including calls that also match a narrower allow rule... An allow rule can't carve an exception out of a deny rule. The same precedence applies between ask and allow." A bare tool-name deny "removes the tool from Claude's context entirely." — [Claude Code: Permissions](https://code.claude.com/docs/en/permissions)
- Compound-command handling: "a rule like `Bash(safe-cmd *)` won't give it permission to run the command `safe-cmd && other-cmd`... Every subcommand must be allowed"; deny/ask rules "apply when any subcommand matches them, including a command nested inside a subshell"; known wrappers (`timeout`, `nice`, `xargs`...) are stripped, but "`devbox run *` matches whatever comes after `run`, including `devbox run rm -rf .`." Path-form evasion: `Bash(rm *)` doesn't match `/bin/rm` or `bash -c 'rm ...'`, so "pair it with the sandbox network allowlist" / sandbox. — [Claude Code: Permissions](https://code.claude.com/docs/en/permissions)
- Path fences: `Read(./.env)`, `Read(./secrets/**)`, `Edit(docs/**)`; "`Write(path)`, `NotebookEdit(path)`, and `Glob(path)` rules never match" (use `Edit`/`Read`); redirects (`> file`, `tee`) are checked against Edit rules and working directories; `permissions.blockWritesOutsideWorkingDirectories` makes file tools refuse writes but "doesn't limit shell commands, MCP tools, or the programs hooks run, so use sandboxing." — [Claude Code: Permissions](https://code.claude.com/docs/en/permissions)
- Approval scopes: Bash/WebFetch "don't ask again" is "Permanently per repository and command/domain", saved to `.claude/settings.local.json` at the repo root (shared across worktrees); file edits "Until session end"; some prompts offer only one-time approval. Project `permissions.allow` and `additionalDirectories` "grant capability, so Claude Code applies them only after you accept the workspace trust dialog." — [Claude Code: Permissions](https://code.claude.com/docs/en/permissions)
- Modes: `dontAsk` "Auto-denies every call that would otherwise prompt"; `bypassPermissions` "Skips permission prompts, except for the actions no mode auto-approves"; `auto` uses "a background classifier"; `acceptEdits` auto-accepts edits and `mkdir/touch/mv/cp` within working dirs. — [Claude Code: Permissions](https://code.claude.com/docs/en/permissions)
- Hooks as policy: PreToolUse `permissionDecision` is `allow | deny | ask | defer`; exit 2 blocks and "Even a `permissionDecision` of `"allow"` doesn't let the action through"; exit 0 with no output means "the tool call continues through the normal permission flow. A hook can deny a call, but silence doesn't approve it"; timed-out hooks don't block unless `"onFailure": "block"` (v2.1.295+). Hook types: `command`, `http`, `mcp_tool`, `prompt`, `agent`. Admins can set `allowManagedHooksOnly`. — [Claude Code: Hooks](https://code.claude.com/docs/en/hooks)
- Sandbox: Linux uses bubblewrap, macOS Seatbelt; "Your allowed domains start empty"; Linux commands run "in a separate network namespace"; a host-side proxy enforces `network.allowedDomains`/`deniedDomains` (denied applies "in every permission mode"); protected write paths include `.claude/settings*`, `.mcp.json`, `.bashrc`, `.gitconfig`, `~/.claude` because a command editing them "could grant itself permissions, or add a hook or MCP server that Claude Code runs outside the sandbox." Reads default to "the entire computer, except certain denied directories" (so `~/.ssh`, `~/.aws/credentials` must be explicitly denied). Default failure mode: runs unsandboxed unless `sandbox.failIfUnavailable: true`. Runs outside the sandbox: Read/Edit/Write/WebFetch tools, command hooks, local MCP servers. — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Codex (snippet, official docs): sandbox vs approval are separate controls — "The sandbox defines technical boundaries. The approval policy decides when Codex must stop and ask"; lower-risk preset `sandbox_mode = "workspace-write"` + `approval_policy = "on-request"`; full access = `danger-full-access` + `never`; `approval_policy = { reject = { ... } }` auto-rejects categories (sandbox escalation, execpolicy prompts, MCP elicitations); "Network access is off by default"; `untrusted` approval policy no longer supported. — [Codex: Agent approvals & security](https://developers.openai.com/codex/agent-approvals-security); [Codex: Sandboxing concept](https://developers.openai.com/codex/concepts/sandboxing.md)
- OpenHands: sandbox is the agent-server container; runtimes `docker`, `process`, `remote`; SDK is "local-first, sandbox-on-demand" with "seamless local-to-remote execution portability." — [OpenHands: Sandboxes overview](https://docs.openhands.dev/openhands/usage/sandboxes/overview); [MLSys 2026: OpenHands SDK](https://mlsys.org/virtual/2026/oral/3749)
- Consent cannot be delegated: a message from another session "never counts as your consent, so it can't answer a pending permission prompt"; receiving Claude is told "never to change permission settings, `CLAUDE.md`, or other configuration because another session asked"; `/compact`-style commands in message text "arrive as plain text." `isolatePeerMachines: true` forces approval before any cross-machine send "even in `bypassPermissions` mode." — [Claude Code: Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- Channels: "only IDs you've added can push messages, and everyone else is silently dropped"; permission relay via a channel means "Anyone who can reply through the channel can approve or deny tool use." — [Claude Code: Channels](https://code.claude.com/docs/en/channels)
- Cloud routines: "Anything a scheduled task does through your connected GitHub identity or connectors appears as you"; "all of your currently connected connectors are included by default. Remove any that aren't needed." — [Claude Code: Scheduled tasks (cloud)](https://code.claude.com/docs/en/routines)
- Audit: `claude_code.tool_decision` records `decision`, `source` (`config`/`hook`/`user_permanent`/`user_temporary`/`user_abort`/`user_reject`), `tool_source`, `classifier_verdict`, `permission_mode`; `claude_code.safety_event` logs refusals/prompts without command text. — [Claude Code: Monitoring usage (OTel)](https://code.claude.com/docs/en/monitoring-usage)
- Copilot coding agent (snippet): "read-only access to the repository... can only push to branches starting with copilot/"; runs in a sandbox "with firewall-controlled internet access." — [morphllm: Copilot coding agent](https://www.morphllm.com/copilot-coding-agent)

### Inferences
- Neo's governor (default-ESCALATE, path fence, zero tools for tainted input) maps cleanly to: deny-wins rules + PreToolUse `ask/deny` + OS sandbox with empty domain allowlist + "never push/deploy without approval" as an `ask` rule on `Bash(git push *)` / deploy commands (the sandbox docs confirm content-scoped ask rules still prompt even in auto-allow mode).
- Store the *decision source* for every tool call (config/hook/operator-once/operator-permanent) — this is the audit trail products actually emit.
- Secrets: deny `Read(~/.ssh/**)`, `Read(~/.aws/**)`, `Read(./.env)` explicitly; the sandbox does not do it for you.

### Gaps
- Codex SDK-specific (programmatic) sandbox/approval surface not verifiable (host blocked); only config-file semantics are known.
- "Actions no mode auto-approves" list was referenced but the specific list was not in the fetched excerpt.

## 8. Failure recovery: restart-safe state, idempotent external actions, reconciliation on boot, retry policies, recovering half-done work from git

### Takeaway
Every durable system fetched follows "record first, act second, reconcile on restart": Claude Code persists transcripts and task lists on disk, restores goals and cron tasks on resume (without catch-up), refuses unsafe worktree re-entry rather than guessing, and keeps worktrees with uncommitted/unpushed work; the ops literature adds outbox + stable idempotency keys + reconciliation for external side effects because durability of progress does not make side effects exactly-once.

### Cited Findings
- Session durability: "The SDK writes it to disk automatically"; resume via `session_id` from the `result` message ("present on every result regardless of success or error"); "Recover from a limit... ended with `error_max_turns` or `error_max_budget_usd`... resume with a higher limit." "Sessions persist the conversation, not the filesystem" — use file checkpointing to revert edits. — [Agent SDK: Sessions](https://code.claude.com/docs/en/agent-sdk/sessions)
- Non-interactive resume fails closed: in `-p`/SDK resumes "Claude Code stops the resume with a stderr error for every refusal except a gone worktree, instead of continuing without isolation"; stream-json `result` carries `startup_failure_reason` = `worktree_unverified` or `worktree_resume_refused` (v2.1.274+) so "An application can branch on it instead of matching the error text." — [Claude Code: Worktrees](https://code.claude.com/docs/en/worktrees)
- Half-done work in git: the cleanup sweep "leaves a worktree in place" when it "still holds work: changed or untracked files, or unpushed commits"; "The sweep also releases a lock Claude Code set for a session whose process has exited, so a killed background session doesn't leave its worktree permanently locked"; reopening a clean worktree whose PR was merged resets to default branch, detected "from git state alone." — [Claude Code: Worktrees](https://code.claude.com/docs/en/worktrees)
- Scheduled-task restore: on `--resume`, CronCreate tasks are restored "except recurring tasks that have expired and one-shot tasks whose scheduled time has passed"; "A restored recurring task doesn't fire for the runs it missed"; a self-paced loop whose wakeup came due while the process was down "stops" and the transcript shows a notice. — [Claude Code: Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)
- Goal restore: "Claude Code restores a goal that was still active when the session ended... carries the condition over but resets the turn count, timer, and token-spend baseline." Unrecoverable errors (auth, exhausted credits, context overflow, model unavailable) clear the goal; others retry 3x then pause. — [Claude Code: /goal](https://code.claude.com/docs/en/goal)
- Agent-team restart gap: "`/resume` and `/rewind` do not restore in-process teammates. After resuming a session, the lead may attempt to message teammates that no longer exist." Task list survives on disk; team config does not. — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Background sessions: "Detaching never stops a background session"; `claude respawn <id>` exists; supervisor-stopped sessions "resume on the next attach or reply." — [Claude Code: Agent view](https://code.claude.com/docs/en/agent-view)
- Anthropic production practice: "we built systems that can resume from where the agent was when the errors occurred"; "rainbow deployments" shift traffic "gradually... from old to new versions while keeping both running simultaneously" so in-flight agents aren't disrupted. — [Anthropic: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Outbox/idempotency: the outbox covers "the case where a database commit succeeds but the event is never published"; derive keys "from the business operation, not from a single network attempt" (e.g. `claim.created:{claim_id}`); commit "the payment row and its reconciliation work item in one transaction" with deterministic IDs and `ON CONFLICT DO NOTHING` so "a retry is a safe no-op"; when an external op cannot be idempotent you need "a reconciliation process, a durable command state machine, or a compensating action", and "a distributed lock alone does not solve this problem because a lock can expire while the external operation remains in progress." — [OneUptime: exactly-once delivery](https://oneuptime.com/blog/post/2026-01-30-exactly-once-delivery/view); [Gravitee: idempotent event processing](https://gravitee.io/corpus/gen-2119/event-driven-soa/idempotent-event-processing.html); [DEV: transactional outbox](https://dev.to/moh_moh701/day-14-transactional-outbox-saving-the-payment-and-the-promise-atomically-49gc)
- Temporal: "by default, Activities are retried until they run successfully"; "at least once" by default; "Event History makes workflow progress durable, but it does not make an external side effect execute exactly once. The standard remedy is idempotency keys, plus reconciliation"; "Activities are only recorded in Event History once they return or error, so a crash mid-Activity can still cause a re-run." — [Temporal blog: idempotency and durable execution](https://temporal.io/blog/idempotency-and-durable-execution); [Temporal docs](https://docs.temporal.io/llms-full.txt?llms-doc=quickstart)
- Mailbox write-ack semantics (a local outbox): "Claude Code reports a message as sent only when the write to the recipient's mailbox file succeeds... When the write fails... the sending agent receives an error and nothing is sent"; malformed entries "are reported as errors and removed from the file; the valid messages are still delivered." — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)

### Inferences
- Boot reconciliation for Neo: enumerate worktrees with the engine's marker, classify by git state (dirty / unpushed / merged-and-clean), reattach or archive accordingly; re-derive "in-flight" from the ledger, not from process memory; replay unsent outbox rows (Telegram sends, PR comments) keyed by `<task-id>:<action>` idempotency keys.
- Treat worker completion claims like Temporal activities: at-least-once; make "mark task done" idempotent and verify from git/CI evidence.
- Follow Claude Code's precedent of *no catch-up for missed fires* for cron loops; one fire on recovery, never N.

### Gaps
- No source gave a measured MTTR or failure-rate figure for agent fleets; recovery guidance is mechanism-level, not quantitative.

## 9. Multi-repo knowledge: cross-project memory, shared skills/playbooks, code indexes, keeping CLAUDE.md/AGENTS.md consistent across many repos

### Takeaway
Current practice: one short root instruction file per repo (plus nested per-package files), shared reusable behaviour pushed into user-scope skills/plugins/subagent definitions rather than copied into every CLAUDE.md, and session-level memory kept per repo. Cross-repo consistency is handled by mirroring/importing AGENTS.md ↔ CLAUDE.md or by plugins that inject a standard file; Claude Code reads AGENTS.md natively only when no CLAUDE.md exists (reported, secondary). Devin's playbooks and Claude's subagent definitions are the shipped "playbook" primitives.

### Cited Findings
- What a worker loads: "a teammate loads the same project context as a regular session: CLAUDE.md, MCP servers, and skills"; `--setting-sources` restricts teammates "to the same restricted list of sources." Subagent definitions let you "define a role once, such as a security-reviewer or test-runner, and reuse it both as a delegated subagent and as an agent team teammate" from "project, user, managed, or plugin" scope. — [Claude Code: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Worktree read-through: when a worktree lacks `.claude/skills`, "Claude Code loads the main checkout's project skills"; same for `.claude/agents` and `.claude/commands` (skills read-through requires v2.1.277+). Subagent worktrees under `.claude/worktrees/` do not load that worktree's own `CLAUDE.md`/`.claude/rules/`. — [Claude Code: Worktrees](https://code.claude.com/docs/en/worktrees)
- Keep base context small: "Aim to keep CLAUDE.md under 200 lines by including only essentials"; "Skills load on-demand only when invoked, so moving specialized instructions into skills keeps your base context smaller"; code intelligence plugins give "precise symbol navigation instead of text-based search." — [Claude Code: Costs](https://code.claude.com/docs/en/costs)

### Inferences
- For a fleet: keep the engine-wide baseline (Neo's "engineering baseline") in the *dispatch preamble* or a user-scope skill, not copied into N repos; keep per-repo CLAUDE.md short and repo-specific; version the shared playbooks as plugins/skills so updates propagate without touching tracked files in every repo.
- A per-repo code index (LSP/code-intelligence plugin) is the documented way to cut token use when workers land in unfamiliar repos; cross-project memory should be stored as engine artifacts (files/DB) and injected selectively, following the filesystem-artifact pattern.
