# Bug finding and root-cause diagnosis by autonomous coding agents (and the engines that run them)

Scope: how a self-hosted engine running headless Claude Agent SDK workers across many repos (web, mobile, Go/TS services, Docker on dev + prod hosts) can make "find the bug" reliable. Each finding is tagged with how an engine can act on it:
**[ENGINE:tool]** = provide a tool/MCP/index deterministically · **[ENGINE:loop]** = run as a scheduled loop · **[ENGINE:gate]** = enforce as a done-gate/governor rule · **[PROMPT]** = can only be asked for in the brief.

Research caveat: in this sandbox arxiv.org, alphaxiv.org, huggingface.co, docs.sentry.io, blog.sentry.io, sre.google, traversal.com and docs.devin.ai did not resolve, so several papers/docs below are cited from search-result summaries and secondary pages rather than full text. Where that is the case, the finding is marked *(summary-level)*.

## Observability as the foundation: what "diagnosable from logs alone" looks like, and how to make it queryable by an agent

### Takeaway
The evidence is consistent that agents root-cause well only when telemetry is (a) structured, (b) correlated across services by trace/request id, and (c) reachable through a narrow query tool. The 2026 MCP ecosystem (Grafana/Loki/Tempo, Sentry, SigNoz, Tempo's native `/api/mcp`) makes this an engine-provided capability, not a prompt wish; Grafana's server even ships query guardrails and enforced label matchers so a worker cannot query outside its project.

### Cited Findings
- OpenTelemetry SDKs inject `trace_id` and `span_id` into every log emitted inside an active span; correlation is only possible if logs carry those fields, and a common failure is logs emitted outside any span having neither — [SigNoz: correlate traces and logs](https://signoz.io/docs/traces-management/guides/correlate-traces-and-logs/); [OneUptime: log correlation in OpenTelemetry](https://oneuptime.com/blog/post/2026-01-25-log-correlation-opentelemetry/view) **[ENGINE:gate — lint that every log line carries trace_id]**
- Guidance from the same sources: emit JSON with one consistent schema across services; make trace-context injection automatic via middleware/logging filters rather than optional; in Go the bridge reads context from `ctx`, so every log call must pass the active span's ctx — [OneUptime](https://oneuptime.com/blog/post/2026-01-25-log-correlation-opentelemetry/view); [OneUptime .NET](https://oneuptime.com/blog/post/2026-02-06-fix-dotnet-otel-logs-not-correlating-traces-ilogger/view) **[ENGINE:gate]**
- "Wide events"/canonical log lines (Stripe's long-standing pattern, re-branded "Observability 2.0"): emit one context-rich event per completed unit of work with high-cardinality fields (user id, request id, feature flags, ~20+ fields), emitted in a `finally` block, with consistent field names across services, so you can answer questions you did not anticipate — [Arvato Systems: Wide Events](https://us.arvato-systems.com/blog/wide-events); [boristane logging-best-practices skill](https://playbooks.com/skills/boristane/agent-skills/logging-best-practices); .NET implementation with OTel integration, adaptive sampling and PII masking: [WideEvents](https://github.com/Ermerson/WideEvents) (opinion/practitioner convention, not measured) **[ENGINE:gate + PROMPT]**
- SRE-book framing (secondary summaries): the four golden signals (latency, traffic, errors, saturation) are symptom-based; "page on symptoms, debug with causes" — [SRE book notes: Monitoring Distributed Systems](https://dev.to/bitmaybewise/sre-book-notes-monitoring-distributed-systems-5fai); [InfoQ golden signals](https://www.infoq.com/articles/monitoring-SRE-golden-signals) **[ENGINE:loop — error-sweep triggers on symptom metrics]**
- Grafana's official MCP server (`grafana/mcp-grafana`) exposes: Loki (`query_loki_logs`, `query_loki_patterns`, `query_loki_stats`, `analyze_loki_labels`, label listing), Prometheus query/metadata tools, Tempo (`search_tempo_traces`, `get_tempo_trace`, `diff_tempo_traces`, `query_tempo_metrics`, `get_tempo_traceql_docs`), Pyroscope, incidents, alerting, dashboards, OnCall — [grafana/mcp-grafana README](https://github.com/grafana/mcp-grafana) **[ENGINE:tool]**
- Same README: `--disable-write` strips all mutating tools (dashboards, incidents, alert rules, raw SQL); `--disable-query` strips log-content tools while keeping count-only tools (`query_loki_stats`, `analyze_loki_labels`); Loki/Prometheus **cost guardrails** run in `shadow` (log only) or `enforce` (block) mode checking selector/range/bytes (Loki) and range/points (Prometheus); `--loki-enforced-matchers` ANDs fixed label matchers into every Loki query so a caller can only narrow, fails closed on unparseable queries, and the docs warn to also disable API/rendering/assistant/snapshot paths that would bypass enforcement; recommends a narrowly scoped service account and streamable-http so each caller carries its own credentials — [grafana/mcp-grafana README](https://github.com/grafana/mcp-grafana) **[ENGINE:tool + gate]**
- Grafana Tempo ships a native MCP endpoint at `/api/mcp` (streamable-http, same auth and multi-tenancy as the rest of Tempo) letting agents search traces with TraceQL, fetch by id, compute span metrics and discover attributes; it serves TraceQL syntax docs as MCP resources; docs warn the endpoint returns trace data to the agent, which may forward it to an LLM provider — [Tempo and AI](https://grafana.com/docs/tempo/latest/introduction/tempo-and-ai/) **[ENGINE:tool]**
- No official Loki-only MCP server was found; community Go/Python servers exist (`loki_query` with LogQL, time ranges, limits, multi-tenant) and one listing says "review the source code before connecting it to your agent" — [grafana-loki-mcp listing](https://vibeindex.ai/mcp/tumf/grafana-loki-mcp) **[ENGINE:tool, with caution]**
- SigNoz (ClickHouse-backed OTel stack) released an official MCP server in May 2026 for searching logs, querying metrics and inspecting traces; self-hosted users run it locally via binary/Docker/source; SigNoz also publishes Agent Skills for ClickHouse query patterns — [SigNoz changelog 2026-05-01](https://signoz.io/changelog/2026-05-01-introducing-the-signoz-mcp-server-r5iwnkpxtsz88akwt6abqddn/); [SigNoz AI tools docs](https://signoz.io/docs/ai/overview/) **[ENGINE:tool]**
- Sentry's official MCP server (`getsentry/sentry-mcp`) groups tools into skills `inspect`, `triage`, `seer`, `project-management` (toggle with `--skills`/`--disable-skills`); the natural-language `search_errors/search_traces/search_logs/search_issues` tools need an LLM provider key; self-hosted works via `SENTRY_HOST`, but the `seer` skill is excluded by default off sentry.io; suggested token scopes include write scopes and there is no documented read-only mode; the server is "primarily designed for human-in-the-loop coding agents" — [getsentry/sentry-mcp](https://github.com/getsentry/sentry-mcp) **[ENGINE:tool — scope the token yourself]**
- Seer is not part of self-hosted Sentry — [eSEOspace Sentry MCP profile](https://eseospace.com/blog/sentry-mcp-server/) (secondary). GlitchTip is a self-hostable Sentry-SDK-compatible error tracker (Django + Celery + Postgres + Redis, no event cap) — [OpenAlternative: GlitchTip](https://openalternative.co/glitchtip) (secondary listing) **[ENGINE:tool]**
- Error dedupe is a solved primitive in trackers: every Sentry event gets a fingerprint; same fingerprint → same issue; built-in algorithms use stack trace, exception type and message; server-side fingerprint rules and SDK fingerprints override; an AI-similarity layer merges semantically similar errors but never splits fingerprint groups — [Sentry: Issue Grouping](https://docs.sentry.io/concepts/data-management/event-grouping/); [Sentry: grouping and fingerprints](https://docs.sentry.io/product/issues/grouping-and-fingerprints/) **[ENGINE:tool/index]**

### Inferences
- A "diagnosable from logs alone" standard the engine can check mechanically: every log line is JSON; carries `service`, `env`, `level`, `trace_id`, `span_id`, `request_id`, `release/commit`, `deploy_id`; every request emits one terminal wide event with outcome + duration + flags; every cross-service hop propagates W3C trace context; symbol/source maps are uploaded per release (see mobile section). Each of these is a lint or a CI gate, not a prompt.
- The engine should hand each worker **one narrow observability tool** (Grafana/SigNoz/Sentry MCP) pre-scoped by `--loki-enforced-matchers {project="X", env="prod"}` and `--disable-write`, plus a count-first discipline (`query_loki_stats` before `query_loki_logs`) to keep context small. Grafana's enforce-mode guardrails make per-project fencing deterministic, mirroring Neo's path fence for file writes.
- For Neo's own stack the cheapest self-hosted spine is OTel SDK → Vector/Alloy → Loki+Tempo (or SigNoz/ClickHouse) + GlitchTip/self-hosted Sentry for crash grouping; all three now have MCP servers that a worker can be given per-dispatch.

### Gaps
- Could not open OpenTelemetry's own logging spec or the SRE book chapter text (hosts blocked); field names are from vendor docs.
- No source compared agent RCA accuracy with vs. without trace-id correlation specifically; the only measured RCA inputs effect is ORCA-bench's "removing source code degrades every metric" (next section).
- Vector and ClickHouse-direct MCP tooling were not researched beyond SigNoz.

## Agent debugging workflow: what makes agents fix the right bug rather than the symptom

### Takeaway
Measured failure analyses converge on the same picture: agents usually *find* the right file but edit at the wrong level (symptom vs. upstream cause), persist with a flawed plan, or stop at the first plausible cause. Product teams that report improvements (Datadog, Cursor) moved to hypothesis-driven, targeted evidence gathering with recursive decomposition rather than bulk telemetry summarisation; the engine can enforce "reproduce first, failing test first, verify after" as gates.

### Cited Findings
- *(summary-level)* "Beyond Resolution Rates: Behavioral Drivers of Coding Agent Success and Failure" (arXiv 2604.02547, 2026): in the failing tasks examined the agent found the gold-patch file in 12/12 and edited it in 10/12, yet in 10 of 12 it patched a downstream symptom or misjudged fix scope while the reference fixed the upstream cause; example: a four-file matplotlib backend change where the accepted fix was a three-line serialization change; the agent's own tests passed but the benchmark validates at the root-cause level — [arXiv 2604.02547](https://arxiv.org/pdf/2604.02547)
- *(summary-level)* "An Empirical Study on Failures in Automated Issue Solving" (arXiv 2509.13941, 2025, SWE-Bench-Verified): the most common failure cause is fundamental flaws in the agent's reasoning that make it persist with a flawed plan — [arXiv 2509.13941](https://arxiv.org/html/2509.13941v1)
- ORCA-bench (Cornell Tech / Traversal / Columbia, arXiv 2607.28545, 2026): 1,079 RCA tasks (884 incidents + 195 control tasks where the right answer is "nothing is wrong"); best of five frontier agents (Opus 4.7, Sonnet 4.6, GPT-5.5, GLM-5, DeepSeek-V4-Pro) reached 25.3% RCA accuracy on Medium (realistic-input) tasks and 10.0% on Hard; agents named an implausible root cause in 7% (DeepSeek-V4-Pro) to 40% (GLM-5) of reports; removing source-code access degrades every metric; authors call the numbers a lower bound; qualitative: agents often find one true cause, explain it well, then stop looking — [Traversal: ORCA-bench](https://www.traversal.com/blog/orca-bench-how-ready-are-language-model-agents-for-oncall); [developersdigest summary](https://www.developersdigest.tech/blog/orca-bench-oncall-rca-agents-not-ready)
- FaultLoc (ICML 2026): 900 real vulnerabilities with verified PoCs; frontier agents "fail to recover the developer-identified root-cause region in most cases, achieving only 40% overlap with ground-truth buggy lines" — [FaultLoc, ICML 2026](https://icml.cc/virtual/2026/67968)
- LinuxFLBench (arXiv 2505.19489): fault-localisation benchmark from real Linux kernel bugs — [arXiv 2505.19489](https://arxiv.org/abs/2505.19489v1). AgentDebug/AgentErrorBench (arXiv 2509.25370): taxonomy of agent failures across memory/reflection/planning/action; AgentDebug reports +24% all-correct and +17% step accuracy over the strongest baseline — [alphaxiv 2509.25370](https://www.alphaxiv.org/abs/2509.25370v1)
- Datadog Bits AI SRE engineering post: early versions made many broad tool calls across logs/traces/metrics and summarised everything in one prompt; a Kafka-lag incident made 12 tool calls, one returned the correct cause, but suspicious upstream errors in other responses led the summariser to pick the wrong root cause; the redesign ties each query to a specific hypothesis, decomposes hypotheses into sub-hypotheses, drops unsupported branches and recurses "until the search space is exhausted" (a CrashLoopBackOff case went from stopping at OOM kills to tracing them to abnormally large payloads); evaluation is on labelled real internal incidents scored by an LLM judge calibrated to humans; no accuracy figure disclosed; product page claims "up to 95%" faster resolution (vendor) — [Datadog: Building Bits AI SRE](https://www.datadoghq.com/blog/building-bits-ai-sre/); [Bits AI SRE product](https://www.datadoghq.com/product/bits-ai-sre) **[PROMPT for the method; ENGINE:tool for hypothesis-scoped queries]**
- Cursor Debug Mode: agent explores files, generates multiple root-cause hypotheses, inserts log statements that post to a local debug server, asks the human to reproduce, confirms/rejects hypotheses from the captured output, proposes a fix, asks for one more reproduction with the fix, then removes all instrumentation — [Cursor docs: Debug Mode](https://cursor.com/docs/agent/debug-mode); [Cursor blog](https://cursor.com/blog/debug-mode). A tool-portable open-source version (NDJSON logs, works with Claude Code/Codex) exists — [millionco/debug-mode-skill](https://github.com/millionco/debug-mode-skill) **[ENGINE:tool — a debug-log sink the worker can write to and read back]**
- JetBrains IntelliJ 2026.2 reworked logpoints so agents inspect runtime state without editing source, cannot touch developer-created logpoints, and are ~30x faster — [JetBrains blog](https://blog.jetbrains.com/idea/2026/08/println-debugging-done-right/) (vendor)
- Anthropic's "Fix software bugs faster with Claude" (Oct 2025) frames debugging as structured problem-solving and cites Ramp's 80% reduction in incident triage time (vendor-reported) — [claude.com blog](https://claude.com/blog/fix-software-bugs-faster-with-claude). In May 2026 Anthropic published a postmortem tracing six weeks of Claude Code quality complaints to three overlapping product changes — [InfoQ](https://infoq.com/news/2026/05/anthropic-claude-code-postmortem) (example of "what changed" diagnosis)
- Codex CLI practitioner patterns: diagnose in read-only mode until one cause is named "as file, line and condition"; pipe the failing test output into `codex exec`; run the smallest failing test, not the suite; AGENTS.md rules "never weaken assertions or delete failing tests"; each fix starts with a test that fails for the diagnosed reason — [developertoolkit: Test and debug with Codex](https://developertoolkit.ai/en/codex/test/); [Codex CLI debugging patterns](https://codex.danielvaughan.com/2026/04/25/codex-cli-debugging-patterns-systematic-bug-hunting-gpt-5-5/) (community, not OpenAI docs) **[ENGINE:gate — read-only diagnosis phase; PROMPT for the rest]**
- Community "systematic debugging" skills share one sequence: reproduce → isolate/minimise → trace back to the first wrong state → fix root cause not symptom → verify; canonical example: duplicate rows fixed by a bad JOIN in the API, not de-dupe in the UI — [playbooks systematic-debugging](https://playbooks.com/skills/vadimcomanescu/codex-skills/systematic-debugging) **[PROMPT]**
- Reproduction tooling: Playwright MCP lets the agent open a browser it controls, click through steps and report; "if it can reproduce, you now have a script you can harden into a test"; it exposes console output and recent network requests; Chrome DevTools MCP is stronger for network waterfall, performance and live page state — [Steve Kinney: runtime tools compared](https://stevekinney.com/courses/self-testing-ai-agents/runtime-tools-compared); [TestDino Playwright MCP](https://testdino.com/blog/playwright-mcp-setup); [Chrome DevTools MCP write-up](https://www.buildmvpfast.com/blog/chrome-devtools-mcp-ai-agent-2026) **[ENGINE:tool]**
- Practitioner opinion: tests tell an agent *that* something is wrong, not *where* or *why*; a debugger/runtime inspection closes that gap — [LinkedIn post via search](https://de.linkedin.com/in/rieckpil) (opinion)

### Inferences
- The measured gap is not localisation but **level-of-fix**. An engine can counter this with a mandatory "cause statement" artifact: before any edit, the worker must write `cause: file:line + condition`, `first wrong state`, `why upstream not downstream`, and the engine refuses Edit/Write until that record exists (a governor rule, like Neo's plan registry). This is deterministic and cheap.
- ORCA-bench's control tasks (195 "nothing is wrong") imply an engine should include negative controls in any RCA eval and should let a worker return "no defect found" without penalty, to suppress hallucinated causes (7–40%).
- Datadog's lesson maps directly to engine design: give workers hypothesis-scoped query tools and budget per hypothesis, instead of dumping whole log windows into context; enforce a recursion budget rather than a single pass.
- "Reproduce first" is enforceable: the engine can require a failing test (or a Playwright script) in the diff that fails on the base commit and passes after — a two-run check the engine performs itself.

### Gaps
- Full text of the three arXiv failure studies was not accessible; percentages per failure category in 2509.13941 are not captured.
- No Anthropic or OpenAI *engineering* post dedicated to agent debugging methodology was found; only product blogs and community skills.
- No controlled study comparing hypothesis-driven vs. summarise-everything agents was found beyond Datadog's internal anecdotes.

## Cross-project / cross-service bugs: tracing, contracts, "what changed since it last worked"

### Takeaway
Cross-service diagnosis rests on three engine-providable primitives: trace propagation (so one id walks the whole request), contract/spec diff gates (so breaking changes are caught at PR time, not in prod), and automated bisect (so "what changed" is a mechanical search). The deploy-history/dependency-diff side is thinly documented but easy for an engine that already keeps a ledger.

### Cited Findings
- Cross-service debugging requires propagating trace context between services, then filtering every service's logs by one trace id; without it logs are "disconnected islands" — [OneUptime log correlation](https://oneuptime.com/blog/post/2026-01-25-log-correlation-opentelemetry/view) **[ENGINE:gate]**
- Tempo MCP `diff_tempo_traces` compares two traces (good vs. bad request) — [grafana/mcp-grafana README](https://github.com/grafana/mcp-grafana) **[ENGINE:tool]**
- oasdiff as a CI gate: run on every PR touching the OpenAPI spec, fetch the previous spec from git history, compare, exit non-zero on breaking changes unless a version bump accompanies them — [OneUptime: consumer-driven contract breaking changes](https://oneuptime.com/blog/post/2026-08-24-consumer-driven-contract-breaking-changes/markdown) **[ENGINE:gate]**
- Pact provider verification replays consumer interactions so a change that breaks a real consumer fails the build even when the spec diff looks small; consumers should assert only fields they use to avoid false positives on additive changes; recommended release check is `can-i-deploy` — [same OneUptime guide](https://oneuptime.com/blog/post/2026-08-24-consumer-driven-contract-breaking-changes/markdown); an agent skill combines Pact + OpenAPI (Prism/dredd) + oasdiff in CI — [harness-engineering api-contract-testing skill](https://openskillindex.com/skills/intense-visions-harness-engineering-api-contract-testing-4c4d5e) **[ENGINE:gate]**
- PactWatch keeps a service→consumer graph and classifies each change BREAKING/RISKY/SAFE per consumer (maturity unclear) — [pactwatch on PyPI](https://pypi.org/project/pactwatch/)
- Automated bisect with an agent as oracle: `codex exec` paired with `git bisect run`, where the model judges whether each commit shows the bug described in natural language and then explains the offending diff — [Codex CLI automated git bisect](https://codex.danielvaughan.com/2026/04/25/codex-cli-automated-git-bisect-regression-hunting-root-cause-analysis/); a bisect skill stresses deterministic test scripts, timeouts, exit-code conventions and handling untestable commits (`git bisect skip`) — [bisect-aware-instrumentation skill](https://tessl.io/registry/skills/github/ArabelaTso/Skills-4-SE/bisect-aware-instrumentation); [Automated Git Bisect skill](https://mcpmarket.com/tools/skills/automated-git-bisect) **[ENGINE:tool/loop]**
- A CI-triggered pipeline (bisect → RCA write-up → tracker issue) claims 4h→12min debugging time (vendor-style, unverified) — [dailyaiworld workflow](https://dailyaiworld.com/workflow/build-autonomous-git-bisect-agent-workflow-claude-code)
- Reproducing prod locally: record relevant commit + masked config + synthetic data + representative request in an isolated env with default-deny network; limitation: synthetic data can lose causal behaviour — [stackcendra wiki: Production to Local Reproduction](https://github.com/keshav-019/stackcendra/wiki/Phase-11-Production-to-Local-Reproduction); diagnostics should record active feature flags, connectivity and cache generation so the bug report carries the context that shaped behaviour — [DZone: replayable production diagnostics](https://dzone.com/articles/replayable-production-diagnostics); AREX records prod requests plus dependency responses via a Java agent and replays in test — [AREX on dev.to](https://dev.to/arex_test/reproduce-production-bugs-locally-with-arex-2daa); replays drift when third-party responses change (open issue) — [Product Hunt thread](https://www.producthunt.com/products/replay-production-api-failures-locally) **[ENGINE:tool for flag/config capture; PROMPT for repro design]**
- Anthropic's own May 2026 incident was diagnosed as three overlapping product changes over six weeks — a "what changed" diagnosis — [InfoQ](https://infoq.com/news/2026/05/anthropic-claude-code-postmortem)

### Inferences
- An engine with a ledger already knows deploy times per project; it can expose a deterministic `what_changed(project, since)` tool returning commits, lockfile/dependency diffs, config/env diffs, migrations and flag flips across *all* repos in the window — the missing piece the search found no product for. Combined with `git bisect run` using a worker-written oracle script, "last known good" becomes a loop, not a prompt.
- Contract gates (oasdiff + Pact) belong in the engine's definition-of-done for any PR touching an API surface; they are exit-code tools and need no AI.
- Cross-repo bugs need a cross-repo index: store each service's OpenAPI/proto/schema in a registry the worker can grep, plus a service dependency graph (PactWatch-style) so the worker knows who consumes what.

### Gaps
- No source on schema registries (Avro/Protobuf/Buf) for agent use was retrieved.
- No source correlating bisect with deploy history or dependency diffs; the mechanism above is an inference.
- Feature-flag tooling (LaunchDarkly/Unleash) for prod-bug reproduction was not found in results.

## Error-sweep loops: scheduled agents that scan trackers, cluster, ticket, and propose fixes

### Takeaway
Shipping products (Sentry Seer, Devin scheduled remediation, GitHub agentic autofix, Datadog Bits) all converge on the same loop shape: tracker/scanner emits grouped findings → agent root-causes with code + telemetry → opens a PR containing cause, fix and a regression test → human reviews. Vendor accuracy claims exist only for Sentry (94.5% RCA, vendor-measured); independent benchmarks (ORCA-bench 25.3%) are far lower, so budget and dedupe matter more than throughput.

### Cited Findings
- Sentry Seer GA: "since beta, Seer has helped fix 38,000+ issues, identified root causes with 94.5% accuracy" (vendor-measured); Anthropic's customer page cites 95% RCA accuracy and "merge-ready code fixes nearly half the time"; an older beta page said 90% — [Sentry blog: Seer GA](https://blog.sentry.io/seer-sentrys-ai-debugger-is-generally-available/); [Anthropic: Sentry customer story](https://www.anthropic.com/customers/sentry). No independent audit found.
- Seer's MCP flow: the MCP server triggers a root-cause analysis per issue; Seer checks stack traces, tracing data, logs, profiles and the connected codebase; connect the GitHub repo before relying on it — [Sentry cookbook: Cursor](https://sentry.io/cookbook/fix-issues-sentry-mcp-cursor); [Sentry cookbook: Warp](https://sentry.io/cookbook/debug-with-sentry-mcp-warp/); an automated "self-healing" workflow cookbook exists — [Sentry cookbook: self-healing workflow](https://sentry.io/cookbook/self-healing-workflow-seer/); issue-fix docs — [Sentry: Seer issue fix](https://docs.sentry.io/product/ai-in-sentry/seer/issue-fix) *(not fetched; blocked)*
- Devin "Scheduled Sentry remediation": a daily automation works through overnight Sentry errors and opens one targeted PR per error; each PR must include the Sentry issue link, root-cause description, the fix, and "a test that would have caught the original error"; guidance is to narrow scope to specific Sentry projects and review results after about a week — [Devin docs](https://docs.devin.ai/use-cases/gallery/scheduled-sentry-remediation); Devin code scans can run on a schedule, scanning only commits since the last run, with each finding assignable to a PR-opening session — [Devin code scans](https://docs.devin.ai/zh/work-with-devin/code-scans) **[ENGINE:loop — template]**
- GitHub agentic autofix for code-scanning alerts: public preview July 2026, GA October 2026; the Copilot coding agent investigates the vulnerability, validates the fix by re-running CodeQL, iterates, and opens a draft PR; fix generation "typically takes 2–4 minutes"; consumes AI credits — [GitHub changelog 2026-07-10](https://github.blog/changelog/2026-07-10-agentic-autofix-for-code-scanning-alerts-in-public-preview/); [Visual Studio Magazine on GA](https://visualstudiomagazine.com/articles/2026/10/23/github-makes-agentic-autofix-generally-available-for-code-scanning-alerts.aspx). 2024 beta: median 28 min to commit a fix vs 1.5 h manual (speed, not correctness) — [ITmedia](https://atmarkit.itmedia.co.jp/ait/spv/2408/19/news045.html). A March 2026 third-party post says no merge-rate or adoption stats have been published — [Pixee](https://www.pixee.ai/blog/github-security-automation-beyond-dependabot)
- Datadog Bits: evaluated on labelled real incidents from hundreds of internal teams with an LLM judge calibrated to humans; users correct wrong conclusions by supplying the actual root cause with telemetry links so the agent "learns from each investigation" — [Datadog: Building Bits](https://www.datadoghq.com/blog/building-bits-ai-sre/); [Datadog docs: Help Bits learn](https://docs.datadoghq.com/fr/bits_ai/bits_ai_sre/help_bits_learn)
- Dedupe primitive: fingerprint-based issue grouping with server-side rules and AI similarity merge — [Sentry: Issue Grouping](https://docs.sentry.io/concepts/data-management/event-grouping/) **[ENGINE:index]**
- mcp-grafana Sift tools (`find_error_pattern_logs`, slow-request finders, investigations) exist per catalogs, and `query_loki_patterns` extracts log patterns — [mcp-grafana on LobeHub](https://lobehub.com/mcp/grafana-mcp-grafana); [README](https://github.com/grafana/mcp-grafana) **[ENGINE:tool for clustering]**
- A production-grade debugging agent built on Claude + GitHub Actions is described by Provectus — [Provectus blog](https://provectus.com/blog/building-a-production-grade-ai-debugging-agent-with-claude-and-github-actions) (not fetched; title-level only)
- ORCA-bench hallucination rates (7–40% implausible causes) are the best available counterweight to vendor accuracy claims — [Traversal: ORCA-bench](https://www.traversal.com/blog/orca-bench-how-ready-are-language-model-agents-for-oncall)

### Inferences
- Engine-level error-sweep spec (deterministic parts): trigger = cron or new-fingerprint webhook; selection = top-N by (events × users affected × recency) for issues with no open ticket; dedupe = tracker fingerprint + a ledger table `incident(fingerprint, project, status, pr, last_seen)`; budget = max sessions/day per project and per-issue token cap; output contract = PR with cause statement, fix, regression test, link to issue; stop = issue resolved in tracker for N days. Everything except the diagnosis itself is engine code.
- Given independent accuracy is low, the loop should prefer **"open a ticket with reproduction + hypothesis"** over "open a PR" for anything cross-service or without a reproducible test; PRs only when a failing-then-passing test exists.
- Treat tracker "regressed" events (issue reopened after a fix PR merged) as a scored signal: it is the cheapest ground truth for the loop's own accuracy, analogous to Datadog's correction feedback.

### Gaps
- No published accuracy/merge-rate for Devin remediation or GitHub agentic autofix; Sentry's 94.5% is unaudited.
- Google Jules: no source found describing a scheduled error-sweep or accuracy report.
- Seer automation knobs (actionability score thresholds, auto-run settings) could not be read (docs blocked).

## Testing that finds bugs before users do, and what an agent can be made to run as part of "done"

### Takeaway
The strongest measured result in this area is that weak tests inflate agent success: strengthening SWE-bench Verified suites drops top agents by 4–17 points. Property-based tests kill ~50x more mutants than unit tests, and mutation testing is already used as an agent merge gate. Flaky-test handling is governance (quarantine with expiry), which an engine can run as a loop.

### Cited Findings
- STING (arXiv 2604.01518, 2026): 77% of SWE-bench Verified instances admit at least one surviving mutant of the gold patch; four weakness patterns: insufficient input-space exploration, partial patch-path coverage, weak assertions, missing environmental context; adding 1,014 validated tests across 211 instances lowers top-10 agents' resolved rates by 4.2–9.0% — [arXiv 2604.01518](https://arxiv.org/abs/2604.01518)
- SWE-ABS (ICML 2026, arXiv 2603.00520): strengthens 50.2% of SWE-bench Verified instances, rejects 2,184 (19.78%) of previously accepted patches; the top agent drops 16.6 points (78.80% → 62.20%), first to fifth place — [arXiv 2603.00520](https://arxiv.org/abs/2603.00520v1); [ICML poster](https://icml.cc/virtual/2026/poster/62669)
- OOPSLA 2025 study of 40 Python projects: each property-based test finds on average ~50x as many mutants as the average unit test — [SPLASH/OOPSLA 2025](https://2025.splashcon.org/details/OOPSLA/102). "Property-Based Mutation Testing" defines a property mutation score — [arXiv 2301.13615](https://arxiv.org/pdf/2301.13615). Earlier study on whether LLMs write good PBTs — [arXiv 2307.04346](https://arxiv.org/pdf/2307.04346)
- Agent skill using mutation testing as a pre-PR gate: 100% kill rate required, failing blocks merge; requires a `MUTATION_RESULT` evidence packet (tool, scope, survivors) — [jwilger mutation-testing skill](https://skills.sh/jwilger/agent-skills/mutation-testing); feeding survivors back as a constraint ("write tests that kill these") — [CallMissed AI testing frameworks 2026](https://www.callmissed.com/blog/ai-testing-frameworks-2026) (blog) **[ENGINE:gate]**
- Practitioner write-up: "The test passed and the value was wrong" — AI-written tests are "too polite" — [pete.lostsource.net](https://pete.lostsource.net/posts/2026-07-28-the-test-passed-and-the-value-was-wrong.html); [viblo summary](https://viblo.asia/p/your-ai-written-tests-are-too-polite-mutation-testing-and-property-based-testing-to-catch-slop-AoJe8jjZ41j) (opinion)
- Flaky tests: flag when fail-then-pass on retry or when the same commit yields different results; track per-test history; GitHub Actions has no native flaky detection as of 2026; keep retries narrow (network/infra boundaries); Playwright `--fail-on-flaky-tests` can make retry-recovered tests fail a stable gate; quarantined tests still run but don't affect status; quarantine should be time-limited (e.g. 14 days) and owned, with auto-promotion after consistent passes; "quarantining a real defect hides a bug" — [OneUptime: quarantine flaky tests](https://oneuptime.com/blog/post/2026-07-28-quarantine-flaky-tests/view); [TestDino flaky tests GitHub Actions](https://testdino.com/blog/flaky-test-github-actions) (vendor blogs; thresholds are opinion) **[ENGINE:loop + index]**
- Codex guidance: `AGENTS.md` rules "never weaken assertions or delete failing tests" — [Codex CLI debugging patterns](https://codex.danielvaughan.com/2026/04/25/codex-cli-debugging-patterns-systematic-bug-hunting-gpt-5-5/) **[ENGINE:gate — diff lint on deleted/weakened asserts]**
- Playwright MCP reproduction can be "hardened into a test" — [Steve Kinney](https://stevekinney.com/courses/self-testing-ai-agents/runtime-tools-compared) **[ENGINE:tool]**

### Inferences
- A deterministic "done" gate for bug fixes: (1) a new test fails on base commit and passes on head (engine runs both); (2) mutation score on changed files does not drop (Stryker/go-mutesting/mutmut run by engine, survivors returned to the worker); (3) no assertion removals or test deletions in the diff without an explicit operator approval; (4) contract gates pass. These are all exit-code checks.
- Because weak tests inflate agent self-reports, the engine should never accept "tests pass" from the worker's own run; it reruns in a clean container (matches the Docker baseline rule).
- Flaky-test quarantine is a natural Neo loop: nightly job computes per-test pass history from CI artifacts, quarantines with a 14-day TTL, opens a todo, and un-quarantines after N green runs.

### Gaps
- The "Dan Luu 42%" and "OutSight 2026" statistics circulating in blogs have no primary source and were excluded.
- No measured data on snapshot/visual testing or fuzzing with agents was found in this pass.

## Production-safe diagnosis: letting an agent reason about prod without touching it

### Takeaway
The consistent recipe is: read-only by default enforced at the *data layer* (DB role with SELECT only, replica itself read-only, MCP server started with write tools disabled), redaction of returned data and telemetry before it reaches the model, query cost/time guardrails, an action allowlist, a kill switch, and human approval for any mutation. Grafana's MCP server implements most of this as flags.

### Cited Findings
- Read-only should be the default for AI SRE agents because triage is investigation; model = agent investigates and recommends, human approves; "the first and most important guardrail is read-only access" — [DZone: AI SRE agents guardrails](https://dzone.com/articles/ai-sre-agents-guardrails) (opinion)
- 30-day prod-access experiment: a "read-only replica" enforced only in application code was still writable; fix = dedicated DB role with SELECT only and writes explicitly revoked, plus an action allowlist and a kill switch — [LevelUp: we gave an AI agent production access for 30 days](https://levelup.gitconnected.com/we-gave-an-ai-agent-production-access-for-30-days-0b0c07e3da87) (practitioner)
- "Scoping controls where the agent can query; redaction controls what comes back" — mask regulated fields in returned data — [hoop.dev PII/PHI redaction for agents](https://hoop.dev/blog/pii-phi-redaction-for-ai-agents-on-snowflake/) (vendor); pre-model guardrails (PII redaction, sensitive-data blocking) run before context reaches the model; monitor detection-rate spikes — [Arthur: redact PII before external LLM provider](https://www.arthur.ai/column/redact-pii-before-external-llm-provider) (vendor); add PII redaction to the telemetry pipeline plus audit logging — [Strands Agents: secure for production](https://strandsagents.com/docs/user-guide/sdk/safety-security/)
- Redaction failure modes: fail-closed (block), fail-open (allow + alert) or degraded (deterministic-only redaction) when the detector is down — [Gravitee corpus page](https://gravitee.io/corpus/gen-1405/pedagogical-agent/piiredactionpipelines.html) (low-authority, generated-looking reference)
- mcp-grafana: `--disable-write`, `--disable-query` (keeps count-only tools), enforce-mode cost guardrails on Loki/Prometheus (selector/range/bytes; range/points), `--loki-enforced-matchers` that fail closed, and the warning that API/rendering/assistant/snapshot paths must also be disabled to make enforcement meaningful; narrow service-account RBAC; per-caller credentials over streamable-http — [grafana/mcp-grafana README](https://github.com/grafana/mcp-grafana) **[ENGINE:tool/gate]**
- Tempo MCP returns trace data to the agent which may forward it to an LLM provider; consider data content and policy before connecting — [Tempo and AI](https://grafana.com/docs/tempo/latest/introduction/tempo-and-ai/)
- Sentry MCP suggested scopes include `project:write`, `event:write`; no documented read-only mode — [getsentry/sentry-mcp](https://github.com/getsentry/sentry-mcp)

### Inferences
- For Neo this is the same compliance-firewall pattern as the governor: prod access is a *tool profile* (read-only DB role on a replica, MCP with write disabled, enforced label matchers for the project, time-boxed query limits) assigned by dispatch; "never debug by editing prod" is enforced by not mounting prod folders and by the governor's path fence, not by prompt.
- Redaction belongs in the log pipeline (Vector/Alloy transform) so prod logs are already PII-clean before any MCP returns them; that also protects the subscription path from customer PII (relevant to Neo's own-work vs customer-work split).
- Time-boxing: enforce query range/bytes limits at the MCP guardrail and a per-session wall-clock budget in the engine; the worker never gets an unbounded `SELECT *`.

### Gaps
- No authoritative standard (NIST/OWASP-style) for agent prod access was found; sources are vendor and practitioner.
- No data on how often read-only agents leak PII into transcripts.

## Knowledge capture: regression tests, postmortems and a searchable incident record

### Takeaway
Google's SRE material supplies the postmortem structure and the warning that untracked action items are forgotten and cause repeat outages; agent products (Devin) make "a test that would have caught it" a PR requirement; Datadog closes the loop by letting humans correct the agent's conclusion with telemetry links. The engine can make all three mandatory artifacts and index them.

### Cited Findings
- SRE Book ch. 15: a blameless postmortem "must focus on identifying the contributing causes of the incident without indicting any individual or team"; culture practices include postmortem reading clubs and "postmortem of the month" — [SRE Book: Postmortem Culture](https://sre.google/sre-book/postmortem-culture/); SRE Workbook ch. 10 case study: only one action item got a tracking bug; "without a formal tracking process, action items from postmortems are often forgotten, resulting in outages" — [SRE Workbook: Postmortem Culture](https://sre.google/workbook/postmortem-culture/) **[ENGINE:index + loop]**
- Third-party postmortem template includes an action item: "a unit test that should fail against the bug, pass after the fix" — [tessl post-mortem-author](https://tessl.io/registry/testland/post-mortem-author) (template, not Google guidance)
- Devin remediation PRs must contain the issue link, root-cause description, fix and a test that would have caught the original error — [Devin docs](https://docs.devin.ai/use-cases/gallery/scheduled-sentry-remediation) **[ENGINE:gate]**
- Datadog Bits learns from corrections: users supply the actual root cause with supporting telemetry links — [Datadog docs: Help Bits learn](https://docs.datadoghq.com/fr/bits_ai/bits_ai_sre/help_bits_learn)
- Sentry grouping lets you link fixes to fingerprints and marks regressions when a resolved fingerprint recurs — [Sentry grouping and fingerprints](https://docs.sentry.io/product/issues/grouping-and-fingerprints/) **[ENGINE:index key]**
- incident.io practitioner guidance on postmortem templates/process — [incident.io SRE postmortem best practices](https://incident.io/blog/sre-incident-postmortem-best-practices) (vendor)

### Inferences
- Minimum incident record the engine should write per fixed bug (deterministic fields, worker fills prose): `fingerprint`, `project`, `services touched`, `trace_id of a failing example`, `cause statement (file:line:condition)`, `trigger`, `detection source`, `fix commit`, `regression test path`, `what_changed window`, `time to detect/fix`. Store in the ledger with FTS (Neo already has FTS recall for memory) so the next worker's first tool call is `search_incidents(error_message | fingerprint | file)`.
- Make the regression test the *index key*: a bug without a test that fails-then-passes is "open," not "fixed"; the error-sweep loop reopens it when the fingerprint recurs.
- A nightly "postmortem action-item sweep" loop (SRE Workbook's lesson) checks every incident record's action items for a linked todo and nags the operator; this is pure ledger code.

### Gaps
- No source describing an organisation that indexes incidents specifically for agent retrieval or measuring precedent-hit rates.
- Google's chapters could not be read directly (host blocked); quotes are via search summaries.

## Mobile / web specifics: crash reporting, symbolication, device logs, real-browser/device reproduction

### Takeaway
Agent-readable mobile crash data depends on two engine-side guarantees: symbols/source maps uploaded per release in CI (otherwise frames are `<redacted>` or wrong-lined) and an MCP into the crash tracker (Firebase's official Crashlytics MCP tools, Sentry MCP). Browser reproduction is mature (Playwright MCP, Chrome DevTools MCP); physical-device reproduction by agents was not found in sources.

### Cited Findings
- Firebase ships official Crashlytics MCP tools/prompts (via `npx -y firebase-tools@latest mcp`) for Claude Code, Gemini CLI and Cursor; use cases include stack-trace analysis and root-cause analysis; a `crashlytics:connect` step needs Firebase CLI login; `crashlytics_get_top_issues` compares Android/iOS — [Firebase: AI assistance for Crashlytics via MCP](https://firebase.google.com/docs/crashlytics/ai-assistance-mcp); [Firebender Crashlytics MCP](https://docs.firebender.com/context/mcp/crashlytics); [Classmethod write-up](https://dev.classmethod.jp/articles/firebasemcp-crashlytics/) **[ENGINE:tool]**
- Community Crashlytics MCP over BigQuery export (fatal crashes, ANRs; needs export enabled; no non-fatals, read-only) — [tjdam007/mcp-crashlytics-server](https://glama.ai/mcp/servers/tjdam007/mcp-crashlytics-server)
- Symbolication: with ProGuard/R8 `minifyEnabled` you must upload mapping files to see complete stack traces; iOS requires dSYM upload; Sentry Gradle plugin auto-uploads mappings and native symbols; JS/RN source maps via `sentry-cli ... upload-sourcemaps`; `<redacted>` frames = missing dSYM; wrong line numbers = release/dist mismatch; symbol upload cannot restore debug info never preserved, so keep the original CI artifacts — [Sentry Flutter: upload debug symbols](https://docs.sentry.io/platforms/flutter/upload-debug/); [OneUptime: Sentry missing native debug symbols](https://oneuptime.com/blog/post/2026-09-14-sentry-missing-native-debug-symbols/view); [fastlane-plugin-sentry](https://www.rubydoc.info/gems/fastlane-plugin-sentry/2.6.3) **[ENGINE:gate — release pipeline step]**

### Inferences

- Give web workers Chrome DevTools MCP (or Playwright MCP) in the dev environment only; prod reproduction stays read-only via tracker data (breadcrumbs, session replay) rather than driving a live prod browser.
