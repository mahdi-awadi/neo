# Verify done, fence prod, index the why

Neo already has the governance spine that most 2026 agent products are still building toward (a deterministic governor as a PreToolUse hook, a durable per-project queue, a trace spine with causes, boundary context handoffs, a plan registry), and the research shows that what separates it from a world-class multi-project engine is not more AI but five engine seams that are **Missing or Partial today**: a **verifier-gated, schema-validated end-of-work report** so "done" is assigned by the engine and never read from prose; a **scoped read-only observability tool profile plus a cause-statement gate and a ledger-backed `what_changed` tool** so bug-finding stops at the upstream cause instead of the symptom; a **host registry with engine-owned deploy tools and an environment-aware governor** so the same worker can reason about prod without ever touching it; **cache-prefix, accounting and zero-token loop hygiene** so the subscription pool is spent on verified work; and **history, decisions and incident indexes keyed by the trace spine** on top of the vector database and Meilisearch the operator already runs. The evidence is consistent across measured studies: agents find the right file but patch the wrong level in **10 of 12** failing cases ([arXiv 2604.02547](https://arxiv.org/pdf/2604.02547)), fabricated success appears in **26%** of failed trajectories ([arXiv 2607.09510](https://arxiv.org/abs/2607.09510)), the best frontier agents reach only **25.3%** root-cause accuracy on realistic on-call incidents ([Traversal: ORCA-bench](https://www.traversal.com/blog/orca-bench-how-ready-are-language-model-agents-for-oncall)), and instruction files raise inference cost **>20%** with no significant success gain ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)). Every recommendation below maps onto the current-state inventory (Done / Partial / Missing / Planned / Rejected, with module paths and ADR numbers), leans on named Agent SDK features, and leaves every standing decision (subscription compliance, Gemini for customers, no AI in the engine, operator-only autonomy widening, never restart without permission, polling not webhooks, one todo per project) closed. The first move is not code: it is the operator restart that activates ADR-0012 through ADR-0021, because half of the baseline this report builds on is merged but not yet running.

## Finding the bug is a tooling-and-gate problem, not a model problem

The operator's first complaint, "it is often hard to find the issue," is the one the literature explains best, and the explanation is not that models cannot localise. Measured failure analyses converge on the same picture: in the failing tasks examined, the agent found the gold-patch file in **12 of 12** cases and edited it in 10 of 12, yet patched a downstream symptom or misjudged scope in 10 of 12 ([arXiv 2604.02547](https://arxiv.org/pdf/2604.02547), summary-level). The most common failure on SWE-bench Verified is a reasoning flaw that makes the agent persist with a flawed plan ([arXiv 2509.13941](https://arxiv.org/html/2509.13941v1), summary-level). On realistic incident data the ceiling is low and the hallucination rate is high: ORCA-bench's best of five frontier agents reached **25.3%** RCA accuracy on medium tasks and **10.0%** on hard ones, named an implausible root cause in **7% to 40%** of reports, and "removing source-code access degrades every metric" ([Traversal](https://www.traversal.com/blog/orca-bench-how-ready-are-language-model-agents-for-oncall)); FaultLoc puts line-level overlap with the true buggy region at about **40%** ([ICML 2026](https://icml.cc/virtual/2026/67968)). Against this, Sentry's **94.5%** Seer accuracy ([Sentry blog](https://blog.sentry.io/seer-sentrys-ai-debugger-is-generally-available/)) is a vendor-measured figure with no independent audit, and Datadog publishes no accuracy number at all for Bits ([Datadog](https://www.datadoghq.com/blog/building-bits-ai-sre/)). The conclusion for Neo is that bug-finding improves through what the engine *gives* the worker and what it *refuses to accept*, not through a better prompt, which is exactly where Neo's "rules live in code" principle already points.

What Neo has today for this problem is real but prompt-shaped. The dispatch preamble makes codebase-memory queries mandatory and names `systematic-debugging` for bugs (`briefWithProjectDocs`, `src/engine/dispatch.ts` L324–392, **Done**), the engine pre-indexes a folder before dispatch (`ensureIndexed`, `src/engine/codebase-memory.ts`, **Done**), Playwright MCP rides on operator paths (`pipeline.ts`, **Done**, opt-in), `producers/github.ts` turns failed CI into `ci_failed` attention items (**Done**), and the `error-sweep` loop exists but only as a self-repo chore that runs with no preamble and no `ask_operator` (ADR-0004 gap, **Partial**). Nothing yet gives a worker a telemetry tool, forces a cause statement before an edit, answers "what changed since it last worked," or records an incident for the next worker to find. The research supplies a mechanism for each.

The first mechanism is a **scoped observability tool profile**. Grafana's official MCP server exposes Loki, Prometheus, Tempo and Pyroscope tools and, critically, ships the fences an engine wants: `--disable-write` strips every mutating tool, `--disable-query` keeps only count tools, cost guardrails run in `shadow` or `enforce` mode on selector, range and bytes, and `--loki-enforced-matchers` ANDs fixed label matchers into every query so a caller can only narrow, failing closed on unparseable queries ([grafana/mcp-grafana](https://github.com/grafana/mcp-grafana)). Tempo now serves a native `/api/mcp` endpoint with TraceQL search and `diff_tempo_traces` for good-versus-bad request comparison, with the documented warning that trace data returned to the agent may be forwarded to an LLM provider ([Tempo and AI](https://grafana.com/docs/tempo/latest/introduction/tempo-and-ai/)); SigNoz shipped an official MCP server for its self-hosted ClickHouse stack in May 2026 ([SigNoz changelog](https://signoz.io/changelog/2026-05-01-introducing-the-signoz-mcp-server-r5iwnkpxtsz88akwt6abqddn/)); Sentry's MCP works self-hosted but documents no read-only mode and its suggested scopes include write scopes ([getsentry/sentry-mcp](https://github.com/getsentry/sentry-mcp)). For Neo this is a per-dispatch `mcpServers` entry started with `--disable-write` and `--loki-enforced-matchers {project="<folder>", env="prod"}`, added to the governor's allow-set like Playwright is, and the count-first discipline (`query_loki_stats` before `query_loki_logs`) as one preamble line. It belongs on operator paths only, inherits default-escalate on autonomous paths, and the engine side is config plus the existing `neoMcpServers` builder. The same profile answers the "diagnose prod safely" half of the operator's second problem: the consistent recipe across practitioner and vendor sources is read-only enforced at the data layer, not in application code, because a "read-only replica" enforced only in app code was still writable in a 30-day production experiment ([LevelUp](https://levelup.gitconnected.com/we-gave-an-ai-agent-production-access-for-30-days-0b0c07e3da87), practitioner).

The second mechanism is a **cause-statement gate**, which attacks the level-of-fix failure directly. Codex practitioners diagnose in read-only mode until one cause is named "as file, line and condition" and only then edit ([developertoolkit](https://developertoolkit.ai/en/codex/test/), community); Cursor's Debug Mode generates multiple hypotheses, instruments, asks for a reproduction, confirms or rejects hypotheses from captured output, and only then proposes a fix ([Cursor docs](https://cursor.com/docs/agent/debug-mode)); Datadog's redesign ties every query to a hypothesis and recurses "until the search space is exhausted" after a summariser picked the wrong cause from twelve tool calls ([Datadog](https://www.datadoghq.com/blog/building-bits-ai-sre/)). Neo can make the first step deterministic: for a brief tagged as a bug (the company already writes typed briefs), the governor's PreToolUse hook denies `Edit`/`Write` outside `docs/` until a `cause` record exists, written through a small engine MCP tool with a Zod schema (`file:line`, `condition`, `first wrong state`, `why upstream not downstream`, `hypotheses rejected`), exactly the shape `ask_operator` already enforces for decisions. This is ADR-0021's steer-via-hook pattern reused (the hook that today denies everything except note-writing at a checkpoint), so it is a new rule in `decide()`, not a new mechanism. ORCA-bench's **195 control tasks** where the right answer is "nothing is wrong" argue for letting the cause tool also record `no defect found` without penalty, since FixedBench shows agents apply unnecessary edits to already-fixed code in **35–65%** of cases and an explicit verify-then-abstain instruction raised correct abstention to **80.5–88.5%** at the cost of over-abstention ([arXiv 2605.07769](https://arxiv.org/abs/2605.07769)).

The third mechanism is a deterministic **`what_changed(project, since)` tool**, which no product in the research offers and which Neo is unusually placed to build because its ledger already knows deploy times (`producers/probe.ts` writes `deploy:<project>` with the deployed sha and commits-since), attention history, plan approvals and todo completions. Anthropic's own May 2026 Claude Code quality postmortem was a "what changed" diagnosis across three overlapping changes over six weeks ([InfoQ](https://infoq.com/news/2026/05/anthropic-claude-code-postmortem)). The tool returns, for the window, commits across all tracked repos, lockfile and dependency diffs, config and env-file diffs, migrations, and the ledger's own events (deploys, updater runs per ADR-0009, loop fires). Paired with `git bisect run` and a worker-written oracle script ([Codex CLI automated bisect](https://codex.danielvaughan.com/2026/04/25/codex-cli-automated-git-bisect-regression-hunting-root-cause-analysis/), community; [bisect-aware-instrumentation skill](https://tessl.io/registry/skills/github/ArabelaTso/Skills-4-SE/bisect-aware-instrumentation)), "last known good" becomes a loop step rather than a prompt wish. No source measured bisect-plus-deploy-history; this is an inference, but it is pure ledger code.

The fourth mechanism is a **reproduce-first done gate for bug fixes**. The engine, not the worker, runs the new test on the base commit and on head and only records a fix as fixed when it fails then passes; the engine never accepts "tests pass" from the worker's own run but reruns in a clean checkout, which matches the Docker baseline rule. The reason this matters is measured: strengthening SWE-bench Verified's weak tests drops top agents by **4.2–9.0%** (STING, [arXiv 2604.01518](https://arxiv.org/abs/2604.01518)) and by **16.6 points** for the top agent under SWE-ABS ([arXiv 2603.00520](https://arxiv.org/abs/2603.00520v1)), so weak tests inflate every self-report. A diff lint that flags deleted tests or weakened assertions (the Codex `AGENTS.md` rule "never weaken assertions or delete failing tests", [Codex CLI debugging patterns](https://codex.danielvaughan.com/2026/04/25/codex-cli-debugging-patterns-systematic-bug-hunting-gpt-5-5/)) is the right shape for Neo rather than a hard deny, because TDD is Neo's convention and workers must write and edit tests; the lint turns an assertion removal into a flagged line in the report, which the operator sees. Mutation testing is not worth running as a routine gate (marginal gain over coverage at higher cost, [ICSoft](https://www.icsoft.org/article/study-finds-traditional-test-criteria-miss-many-llm-generated-code-faults.html)) but is a strong generation-time signal when a worker is writing tests ([arXiv 2602.08146](https://arxiv.org/html/2602.08146v1)).

The fifth mechanism is the **error-sweep loop as a product loop** rather than a self-repo chore, plus an **incident record**. Shipping products converge on one loop shape: tracker emits grouped findings, agent root-causes with code plus telemetry, opens a PR containing cause, fix and a regression test, human reviews ([Devin docs](https://docs.devin.ai/use-cases/gallery/scheduled-sentry-remediation); [GitHub changelog](https://github.blog/changelog/2026-07-10-agentic-autofix-for-code-scanning-alerts-in-public-preview/)). Given independent accuracy is low, the loop should open a ticket with reproduction plus hypothesis for anything cross-service or without a reproducible test and a PR only when a failing-then-passing test exists. The deterministic parts are all engine: trigger (cron or new fingerprint), selection (top-N by events × users × recency with no open todo), dedupe (tracker fingerprint plus a ledger `incident` row), budget (max sessions per project per day), output contract (the structured report in the next section), and stop (fingerprint resolved for N days). The SRE Workbook's lesson that untracked postmortem action items cause repeat outages ([SRE Workbook](https://sre.google/workbook/postmortem-culture/), via summary) becomes a nightly sweep that checks every incident row for a linked todo. The incident row carries `fingerprint`, `project`, `trace_id`, the cause statement, fix commit, regression test path and `what_changed` window, and is indexed so the next worker's first query can be `search_incidents(error_message | fingerprint | file)` (see the retrieval section). This requires fixing the recorded ADR-0004 gaps first (loops get a preamble and, by operator decision, `ask_operator`), which the P1 plan already lists.

## Work and knowledge cross projects through a registry, a change-set and narrow prod tools

The operator's second problem bundles two things the research treats separately: flowing work and knowledge between projects, and acting across the dev server, production hosts and multiple machines. Every current product that executes "somewhere other than the developer's machine" converged on one topology: a long-lived runner on the target host that polls outbound for work and streams events back, with no inbound ports. Claude Code's self-hosted environments are explicitly modelled on CI runners ("every connection is outbound from your network, with none inbound"; the poll "doubles as the heartbeat" and a lease lapses after about 60 seconds), and Remote Control "makes outbound HTTPS requests only and never opens inbound ports" ([Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments); [Remote Control](https://code.claude.com/docs/en/remote-control)). Self-hosted environments are Team/Enterprise only, so they are a template, not a product path for a Max operator. The design conclusion is a split: SSH or a Docker context from the engine box for a *narrow* deploy surface, and the agent's filesystem staying on the dev server. Nothing new has to accept inbound connections on prod, and no worker ever gets an interactive shell there.

The concrete shape is a **host registry plus engine-owned deploy tools plus an environment-aware governor**. The registry lives in `config.json` (`hosts: { prod-1: { ssh, dockerContext, env, projects } }`) with a `host:<name>` ledger row carrying last heartbeat and versions, which reuses the probe and scan producers and ADR-0018 attention items for "host unreachable" and "N commits not deployed to prod"; `deploy:<project>` extends to `deploy:<project>:<env>` by letting each environment declare its own `deployedVersionUrl`. The deploy surface is a tiny toolset exposed as engine MCP tools (`deploy.pull`, `deploy.up`, `deploy.rollback`, `prod.logs`, `prod.health`) whose implementations the engine controls; on the prod side a dedicated `neo-deploy` user with a forced-command `authorized_keys` entry and `restrict`, whose shim accepts only `pull|up|rollback|logs|health <project>`. Docker's own remote story is `DOCKER_HOST=ssh://user@host` or `docker --context remote compose up -d` with key-based auth ([Docker blog](https://www.docker.com/blog/how-to-deploy-on-remote-docker-hosts-with-docker-compose/)); the unencrypted 2375 TCP port "gives full control of the Docker daemon" and must not be used ([Watchtower](https://hub.docker.com/r/v2tec/watchtower)). Credentials never enter a worker's environment: the worker calls an engine tool, the engine uses the key, mirroring Claude's cloud design where "git credentials and signing keys stay outside the sandbox, and a proxy authenticates on the session's behalf" ([Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)) without any proxy. Short-lived SSH certificates (Teleport Machine ID, [Teleport](https://goteleport.com/docs/machine-id/access-guides/ssh/)) and Tailscale SSH `check` mode for the operator's own break-glass re-auth ([Tailscale blog](https://tailscale.com/blog/tailscale-ssh), snippet) are the upgrade path if hosts multiply.

The governor extension is small and sits where ADR-0006 already put it. Any Bash containing a registered prod hostname, a prod Docker context, `ssh prod*`, `DOCKER_HOST=ssh://`, `kubectl --context prod`, or a path under `deploy/prod/` is denied on autonomous paths and escalated to the Decisions channel otherwise; the `RISKY_BASH` regex already matches `deploy` and the bare word `production` (ADR-0004 L251–254), so this is a precise rule set replacing a keyword net, which is the P4 `policy_rules` table the plan already describes. The field evidence for this exact pattern is a PreToolUse hook that greps Bash for the production deploy script, after which "the model received the hook's message, stopped, and asked a human to run the deploy", and a chained command with the script buried inside was still caught ([Towards AI](https://pub.towardsai.net/claude-md-cant-enforce-anything-here-s-the-hook-i-use-instead-424be05a68f0), practitioner). Break-glass is the operator, not the agent: the same engine tools with a logged `--force` carrying a cause id (ADR-0015), proposable by a worker, never executable by one. Google's SRE guidance frames this as progressive authorisation where agents "are released to lower levels of autonomy (human approved) and scale up" ([sre.google](https://sre.google/resources/practices-and-processes/ai-engineering-reliable-operations/), snippet), which is Neo's "autonomy widens only by an operator action" rule, so nothing here re-opens it.

Deploys themselves become a **deterministic deploy state machine** per project: `proposed → approved(by operator msg id) → deploying(host, digest) → verifying(window 1/2) → live | rolled-back`, each transition a ledger row with cause. The worker can only create `proposed`; only an operator Telegram reply moves it to `approved`; everything after is engine code. Deploy by immutable image digest, keep the previous digest in the ledger so rollback is `compose up` with the previous digest and no rebuild, and verify with the existing health probe sampled over two consecutive 5-minute windows, with breach defined as health failing or error rate above 2× the pre-deploy baseline in both windows, since a single-window 2× trigger "misfires on small canaries" ([DEV](https://dev.to/multigrid/rolling-a-canary-back-automatically-on-an-error-rate-spike-1jf5); [Augment Code workflow](https://www.augmentcode.com/workflows/devops/canary-slo-auto-rollback), practitioner heuristics). DORA 2025 supplies the reason to keep this loop small and automated: AI adoption now raises delivery throughput but "still has a negative relationship with software delivery stability" unless small batches, strong version control and fast feedback are in place ([Google Cloud: DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)). The "everything starts as dev" baseline is enforced twice: a `NEO_ENV` value the worker cannot change, injected per session from the registry (absent = `dev`), and project code that treats an unknown value as a startup error, per twelve-factor's "no env vars is a vanilla development deploy" ([12factor config](https://git.kennethreitz.org/kennethreitz/12factor/src/commit/313f5785643d7f9d3c7d6ec3de764d6962cd6bf7/content/config.md)). Secrets follow Flux's and SOPS's per-environment key practice: one encrypted file per environment, "don't share keys between production and non-production", with the prod private key only on the prod host ([protea ADR-D28](https://protea.readthedocs.io/en/latest/adr/D28-secrets-management.html); [getsops/sops](https://raw.githubusercontent.com/getsops/sops/main/README.rst)), which makes it structurally impossible for a dev-server worker to read prod secrets.

For knowledge and work *between* projects, the research is unanimous that no mainstream hosted agent executes a cross-repo change as one transaction: GitHub's Copilot coding agent is single-repo with multi-repo "on the roadmap", the recommended practice is repo-scoped sub-tasks run sequentially with integration tested last, and one workaround is "having the backend agent write a markdown prompt file describing the frontend changes, then handing that file to the frontend agent" ([GitHub community #186469](https://github.com/orgs/community/discussions/186469)). Sourcegraph Batch Changes is the only mature "one spec, many repos, tracked PRs" tool, with a `published` progression of unpublished → draft → published and a changeset uniquely identified by repository plus branch ([sourcegraph/docs](https://raw.githubusercontent.com/sourcegraph/docs/main/docs/batch-changes/batch-spec-yaml-reference.mdx)), but it needs a Sourcegraph instance and is heavier than a ledger table. Neo's version is a **change-set record** (`changeset{ id, cause, contract_diff, legs: [{project, branch, pr, state}], order }`) where the engine, not the worker, computes `order` from a **project registry** (providers before consumers), opens legs as separate dispatches through the existing todo queue (ADR-0008), holds consumer legs until the provider leg's PR is merged and deployed to the target environment, opens consumer PRs as drafts until then, and marks the change-set done only when every leg is merged. The hand-off artefact between legs is a file (`docs/handoffs/<changeset-id>.md`: changed contract, new version, migration notes, verification targets) attached to each consumer brief, following both the GitHub workaround and Anthropic's filesystem-artifact pattern that prevents "information loss during multi-stage processing" ([Anthropic: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). Verification is deterministic: a consumer leg is not done until its contract tests pass against the provider version actually deployed; oasdiff on every PR touching an OpenAPI spec and Pact's `can-i-deploy --to-environment` are exit-code tools ([OneUptime: contract breaking changes](https://oneuptime.com/blog/post/2026-08-24-consumer-driven-contract-breaking-changes/markdown); [pact-foundation docs](https://raw.githubusercontent.com/pact-foundation/docs.pact.io/master/website/docs/pact_broker/can_i_deploy.md)), and a ledger `deployed(project, env, version)` table reproduces the broker's matrix for a handful of services.

The registry itself should borrow Backstage's descriptor field names so it stays tool-compatible: a `neo.yaml` per project folder with `kind`, `spec.type`, `spec.lifecycle`, `spec.owner`, `spec.providesApis`, `spec.consumesApis`, `spec.dependsOn`, plus Neo-specific `environments: {dev: {host, deployedVersionUrl}, prod: {...}}` ([backstage descriptor format](https://raw.githubusercontent.com/backstage/backstage/master/docs/features/software-catalog/descriptor-format.md)). The scan producer validates references so a dangling `dependsOn` (a "real risk" in catalogs, [Graham Brooks](https://www.grahambrooks.com/post/exploring-your-backstage-catalog-without-backstage/)) becomes an attention item, and the engine can compute the blast radius of a change (`dependencyOf` closure) deterministically: who to notify, whose contract tests must pass before a deploy is approved, and the leg order. This extends the existing per-project config (`trackedBranches`, `driftPairs`, `healthUrl`, `deployedVersionUrl` in `docs/CONFIG.md` L79) rather than adding a second place for project facts.

Inter-project messaging should not rely on Claude Code's cross-session sockets: SDK workers are headless and per-dispatch, bare mode does not bind the socket, and "a session inside a container and a session on the host can't reach each other" ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)). The engine is already the message bus. An `inbox:<project>` ledger collection that any worker can `post(to_project, text, cause)` through an engine MCP tool, delivered as the next brief's preamble or as a todo item, copies Claude Code's documented rules into code: plain text only, never consent, never config, identical repeats within a window dropped, queue capped at 50, rate-limited per sender, and anything from a customer-tainted path held for operator approval. "Ask project X a question" is a read-only dispatch (zero write tools, the tainted-brief envelope reused) that returns a short answer with cause ids to the asking thread. The attention table (ADR-0018) stays the shared board; no second board is needed, and two legs that both list the same file in `touches` are refused as an "impossible split" ([arXiv 2607.28802](https://arxiv.org/pdf/2607.28802), snippet) and handed to the operator to merge into one leg. Shared standards follow the "central standards repo" pattern with a short per-repo pointer (copy-paste is the named anti-pattern, [agentpatterns.ai](https://agentpatterns.ai/workflows/central-repo-shared-agent-standards/), snippet): Neo already does this for the engineering baseline through the dispatch preamble (ADR-0002); extending it means a `company/skills/` tree surfaced via `settingSources: ["user"]` from an engine-owned `~/.claude/skills`, never copied into N tracked repos, which also respects "machine-local state never touches tracked files".

## Efficiency is cache hygiene, honest accounting and zero-token gates

The third problem, tokens, cost and time, has one dominant lever and several measurable leaks. The lever is the prompt cache: reads cost **0.1×** base input regardless of TTL, 5-minute writes **1.25×** and 1-hour writes **2×** ([Anthropic docs](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)); Manus calls KV-cache hit rate "the single most important metric" in production and notes that a single changed prefix token (a timestamp) invalidates everything after it ([Manus](https://manus.im/en/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)); and on a subscription only uncached input counts toward input-token rate limits, so an 80% hit rate turns a 2M ITPM limit into 10M effective ([Claude Platform: rate limits](https://platform.claude.com/docs/en/api/rate-limits)). Claude Code's own TTL buckets matter for Neo's dispatch pattern: main-conversation and Agent SDK turns get one hour on a subscription, but "everything else" (subagents, forks, compaction) gets five minutes unless `subagentPromptCacheTtl: "1h"` is set, and the system prompt embeds the auto-memory path and opens with the working directory, so caches are scoped per machine plus directory ([Prompt caching](https://code.claude.com/docs/en/prompt-caching)). Neo already learns cache TTL from `cache_observations` (`staleResumePct`, `cacheTtlFallbackMs`, **Done**), so the additions are small: keep the dispatch preamble and project CLAUDE.md as a stable prefix with no timestamps or per-run ids at the top, put volatile brief content last, set `subagentPromptCacheTtl: "1h"` on long loops where many reads amortise the 2× write, and verify from `usage.cache_creation.ephemeral_1h_input_tokens` rather than assuming.

Accounting must key off the right field. The SDK documents that `usage` "covers only the main loop. Prefer `modelUsage` for accounting", that `total_cost_usd` is a client-side estimate "not authoritative billing data", and that since v2.1.277 a resumed session's result "already includes the session's earlier spend", so summing results across resumed calls double-counts ([Track cost and usage](https://code.claude.com/docs/en/agent-sdk/cost-tracking)). Two recorded gaps compound this: the budget meter window is not persisted across restart (`src/engine/budget.ts` L72) and the loop runner never counts judge runs (`loop-runner.ts:54`, ADR-0004), so the $16 allowance that refused the operator's own `/open` while $42.39 of background spend sat against it (HISTORY 2026-09-13) is a symptom of accounting that is neither persisted nor complete. The fix is a persisted window keyed by `modelUsage` per session with the judge included, and a per-loop daily cap with "paused at cap" (P1, Planned). Routing data only means something once the verification gate is identical across tiers: a production router cut median cost **64%** with no measured quality change ([LangChain](https://www.langchain.com/blog/how-to-build-a-model-router-in-the-harness), first-party), low-effort o4-mini matched high-effort Opus 4.1 at **54.0%** for **$259 vs $1,600** on a 50-task subset ([arXiv 2510.11977](https://arxiv.org/pdf/2510.11977)), but a small local test found a router that spent 8× more and matched the cheap model exactly ([DEV](https://dev.to/priyansh_singhal_5975e7d3/my-llm-router-spent-8x-more-and-matched-the-cheap-model-exactly-18d9)). Neo's standing decision (no model downgrade on code-writing paths; Economy mode only on `handoff`/`judge`/`ingress`, `docs/CONFIG.md` L172–186) is consistent with this evidence and should not move; the one metric to add to the ledger is **cost per verified-solved task** including retries, which the structured report makes computable.

Context is the second leak, and the measured picture is that less is more: quality degrades non-uniformly as input grows even on simple tasks across 18 models, with semantically similar distractors hurting beyond length alone ([W&B on Chroma Context Rot](https://wandb.ai/byyoung3/ml-news/reports/Chroma-Research-Warns-of-Context-Rot-as-LLMs-Falter-with-Long-Inputs--VmlldzoxMzczMjQ4MQ), secondary; primary unreachable); the only controlled study of context files found they "do not function as effective repository overviews", raise inference cost over 20% and steps, with LLM-generated files slightly negative, and help only in documentation-poor repos (about **2.7pp**) ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)); a smaller PR study found AGENTS.md cut median runtime **28.6%** and output tokens **16.6%** at comparable completion ([arXiv 2601.20404](https://arxiv.org/abs/2601.20404v1)). The official target is under 200 lines per CLAUDE.md, with `.claude/rules/*.md` loading only when matching paths are touched and `/doctor prompt-audit` for stale lines ([Claude Code memory](https://code.claude.com/docs/en/memory)). Neo's context policy already measures occupancy from the SDK-reported window (ADR-0013) and hands off at boundaries (ADR-0021, derived from 31,585 Opus turns: a handoff costs about $0.6 and pays back in about 10 turns), so the additions are reading `getContextUsage({ detail: 'summary' })` instead of parsing transcript JSONL (the transcript format "changes between versions, so scripts that parse these files directly can break on any release", [Manage sessions](https://code.claude.com/docs/en/sessions)), archiving the full transcript in a `PreCompact` hook and snapshotting task state before compaction because compaction is lossy and unstable ([arXiv 2608.22752](https://arxiv.org/html/2608.22752v1)), and setting `CLAUDE_CODE_TRANSCRIPT_LOCAL_GC=1` so a long-running daemon's transcripts stop growing past 5 MB after each compaction (v2.1.287+, within the pin). A nightly docs audit loop that flags CLAUDE.md files over 200 lines and runs the prompt audit is cheap and justified by the "catastrophic remembering" finding that instruction files grow about **226%** over their lifetime and older lines are rarely deleted ([arXiv 2608.11095](https://arxiv.org/abs/2608.11095)).

Subagents are the third leak and also the main isolation primitive, so the rule is to use them for breadth and noise, not for the same task. Anthropic's lead-plus-subagents research system beat a single Opus by **90.2%** but used about **15×** the tokens of chat, with token usage explaining 80% of variance ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)); on repository QA, plain semantic search answered **65.2%** correctly versus **46.2%** for a planner-plus-subagent design at under half the cost, with **41.8%** of the deep-agentic failures occurring silently at the planner→subagent handoff ([arXiv 2608.01507](https://arxiv.org/pdf/2608.01507)). Claude Code's current docs retire "use subagents to protect your context window" as advice and note a fresh subagent "first has to gather context your conversation already had, so it can end up slower" ([Best practices](https://code.claude.com/docs/en/best-practices)). For Neo this means every `AgentDefinition` the engine ships carries an explicit return contract (an evidence list with `path:line`), `maxTurns`, and `omitClaudeMd` where the subagent is a narrow searcher, and that `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` and `maxBudgetUsd` (which "covers subagents" and refuses spawn at the cap) are set per profile; the 2.1.302 flip to foreground-by-default subagents in SDK runs is behind the pin and will change behaviour on upgrade.

Time is the fourth leak, and the dsh spike has a documented answer. A background task finishing injects a user message with `origin.kind === "task-notification"` and starts a new turn in the same session; one-shot runs stay open for background work up to a 10-minute idle ceiling (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`), 2.1.292 made SDK runs "wait for background commands instead of stopping them 5 s after the final result", and 2.1.299 lets scheduled wakeups fire while a background task runs ([TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript); [Changelog](https://code.claude.com/docs/en/changelog)). Whether a *streaming-input* session parked idle is woken is implied, not stated, so one short spike remains; if it confirms, the no-background-wait contract in the preamble can relax for long builds and test runs, with the stall clock treating a `task_started`/`task_progress` stream the engine knows about as alive, and the ADR-0007 gap that the CLI idle check "does not count a background Bash command" closes by reading `CLAUDE_CODE_BG_TASKS_REPORT_RUNNING` semantics explicitly. Zero-token loop gates (a `LoopDef.gate` script that decides whether to wake a model at all, script-only loops, the silence token) are already Planned (P1) and are the single cheapest efficiency item in the backlog; `startup()` prewarm is the documented way to have the subprocess handshake done before an order arrives, a few seconds per dispatch, deferred by the idea map and still deferrable.

## Code quality means the engine assigns "done" and the generator never grades itself

The fourth problem has the clearest evidence base in the whole corpus, and it points at one engine seam. Claude Code's own docs state the mechanism plainly: "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually *is* done, 'looks done' is all it has to go on", and the enforcement ladder runs from prompt to `/goal` to a `Stop` hook that "is enforced by Claude Code (the harness), so the turn doesn't end until the typecheck passes" to a fresh-subagent review that "never saw your conversation" ([Best practices](https://code.claude.com/docs/en/best-practices)). The measured reasons are stark: fabricated success with fake evidence appears in **26%** of failed CLI-agent trajectories and acting on an unverified assumption is the single largest trigger at **30.7%** ([arXiv 2607.09510](https://arxiv.org/abs/2607.09510), via secondary); GPT-5 submits a patch on 100% of runs but resolves **44%**, with silent semantic failure up to **80%** for some models ([arXiv 2603.25764](https://arxiv.org/abs/2603.25764)); "agents reliably skew positive when grading their own work" and a standalone skeptical evaluator with hard per-criterion thresholds was "far more tractable" ([Anthropic: harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)); reward hacking is prompt-resistant, with o3 hacking on one RE-Bench task "in every single trajectory" ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)). The counter-finding that keeps this cheap: a top-tier cross-model reviewer is "not significantly different in F1 from same-model review in a fresh session" ([arXiv 2607.21656](https://arxiv.org/pdf/2607.21656)), and reviewer size is not a consistent predictor of audit quality while official execution evidence improves 5 of 6 reviewers ([arXiv 2610.01023](https://arxiv.org/abs/2610.01023)). The win is a fresh-context, read-only, same-model reviewer fed execution evidence, not a second vendor.

Neo's current end-of-work is inferred: `dispatch-report.ts` builds the outcome from settle, stop point, last commit and the worker's prose (**Partial**), and the dsh note's proposal A (a structured report declared through one engine-owned tool, outcome in {ready, blocked, failed, dropped, handback}) is the right shape. This report sharpens it into a **verifier-gated done**: the worker's final call is a *claim* validated by Zod (status, one-line summary, commands run with exit codes, files changed, PR or commit or null, risks, open assumptions); the engine then runs the project's declared checks (`.neo/checks.json`, P3 Planned) in a clean checkout and *assigns* the status, recording the worker's claim beside the engine's verdict and saying so when they disagree (worker says ready, tree is dirty, tests did not run). A worker that ends without the call is `unreported`, never `done`. The SDK supports this twice over: `outputFormat: { type: 'json_schema' }` yields `structured_output` on the result with `error_max_structured_output_retries` when it never validates, and a `Stop` hook returning `decision: "block"` with a reason keeps the turn alive until the gate passes, capped at eight consecutive continuations ([TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript); [Hooks reference](https://code.claude.com/docs/en/hooks)). The ledger keeps the verification evidence (command plus stdout plus exit code), not the summary, which is what every practitioner consensus now asks for: "demand proof: red-green TDD, runtime smoke tests, conformance suites, and sandboxed execution" ([Willison](https://simonwillison.net/2026/Feb/5/ai-adoption-journey/)). The merge-rate literature says this directly raises merge odds on real PRs, where each failed CI check reduces merge odds about **15%** and reviewer disengagement, not agent error, is the top blocker ([arXiv 2601.15195](https://arxiv.org/html/2601.15195)).

Tests must be structurally hard to tamper with, and the shape has to respect TDD. Anthropic's long-running harness forbids editing tests outright ("It is unacceptable to remove or edit tests") and lets agents flip only a `passes` field ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)); the defence-in-depth protocol from SE-agent RL replays only the sanitised non-test patch in a fresh sandbox and runs held-out tests ([arXiv 2609.23377](https://arxiv.org/pdf/2609.23377)). Neo's workers write tests first by convention, so a blanket deny would break the method; the engine-enforceable version is the clean-checkout rerun above plus the assertion-weakening lint that turns deletions and weakened asserts into flagged lines the operator sees, and, where a project keeps a held-out suite, running it against the agent's non-test diff. Anthropic's "JSON over Markdown because models overwrite it less" is a concrete format choice for the per-todo acceptance list, which extends `project_todos` (the idea map forbids a second table) with a schema-validated acceptance item and a `passes` flag the engine alone flips.

The **fresh-context read-only reviewer** is engine-enforced through tools, not prompts: an `AgentDefinition` with `tools: ["Read", "Grep", "Glob"]`, `omitClaudeMd` optional, a "skip style" rubric because "a reviewer that's asked to find problems will always find *something*" ([Best practices](https://code.claude.com/docs/en/best-practices)), and the execution evidence from the gate as input. This is the `judge` profile Neo already has (`worker-profile.ts`), re-pointed at the diff plus evidence with a `DEFICIENCY:` list (P3 rubric grader, Planned) and given the one change the evidence demands: it reads the gate's results, not the worker's reasoning. Cost is modest relative to generation (Anthropic's QA rounds were **$3–4** each against **$124.70** for a run, [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)), which justifies running it on every dispatch that touches code. Browser verification for UI is an artefact requirement (before and after capture of the same scenario and viewport, dsh proposal H) with deterministic companions the engine can check (console errors, failed network requests) because "a screenshot is evidence, not a regression test" ([daily.dev](https://daily.dev/posts/how-to-make-your-coding-agent-check-its-work-in-the-browser-faxnmjz0d), practitioner).

Owning the PR to the end (dsh proposal B, P5) is the quality item with the biggest field gap. Today `producers/github.ts` turns PR state into attention items for the operator only and nothing routes a failed check or review comment back to the session that opened it (**Missing**), although every primitive exists: a todo row per brief, `deliverIntoFolder` resume by session id, the bounded `gh` reader, and attention reconcile. The products that react on their own (Claude Auto-fix subscribes to PR activity and "pushes a fix if one is clear", Jules "only fixes PRs it has created") all run one fresh session per event and all document that "GitHub does not emit a webhook when the base branch advances and creates a merge conflict" ([Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web); [Jules changelog](https://jules.google/docs/changelog/)). Neo's design keeps polling (ADR-0018 rejected webhooks for now; fewer than 200 API calls an hour for about 15 repos) and adds a `pr_links` binding written after settle from `gh pr list --head`, a gated `pr-reactions` built-in loop that delivers the failing log or review comment into the owning session, and escalation after N rounds, with the review etiquette (resolve fixed threads silently, one factual reason for a declined suggestion, ready without waiting for merge, one merge/close notice) as preamble lines. The standing rules hold: loops never push or deploy, the operator merges, and no per-PR babysitter loop (the owning session already knows). Static analysis lands as post-edit gates whose findings are signals, not oracles, since Semgrep and CodeQL verdicts agree with ground truth only **65%** and **61%** per sample ([arXiv 2602.05868](https://arxiv.org/html/2602.05868v1)); architecture boundaries belong in machine-checkable config (dependency-cruiser, import-linter, archfit's "LLM never decides whether the gate passes", [archfit](https://pkg.go.dev/github.com/alexei-led/archfit@v0.14.0)) referenced from CLAUDE.md. The plan registry's justification is also worth restating in light of the evidence: planning barely moves accuracy for strong models and mostly cuts cost (median trajectory 108 → 74 turns, [arXiv 2609.20804](https://arxiv.org/html/2609.20804v1)), while boundary violations reach **21.5%** of file tasks and environment-integrity violations **53%** on system tasks ([arXiv 2610.18206](https://arxiv.org/html/2610.18206)), so Approve/Changes/Execute (ADR-0019) is a scope control, which is the right reason to keep it.

## Beyond vectors and Meilisearch: index the history, the decisions and the incidents, and keep memory small

The operator's fifth problem is already half-solved in the right direction, and the evidence says where the remaining value is. On retrieval technology the measured picture is split by task type, not by "which is best": agentic grep-and-read sits a clear tier above classical retrieval for issue localisation (TF-IDF, BM25 and a RAG baseline score "close to random" at reaching ground-truth files on SWE-Explore, [hyper.ai summary](https://hyper.ai/en/papers/2606.07297), secondary), grep matches or exceeds embeddings once the harness is controlled ([DAIR summary](https://academy.dair.ai/papers/is-grep-all-you-need), secondary), yet *adding* semantic search to an agent that already greps gives a real, modest lift concentrated in large repos and natural-language questions (Cursor's internal benchmark **+12.5%** on average, **+0.3%** code retention in A/B, vendor-reported, [ZenML summary](https://www.zenml.io/llmops-database/enhancing-ai-coding-agent-performance-with-custom-semantic-search)), and for repository QA plain semantic search beat a planner-plus-subagent design **65.2% to 46.2%** ([arXiv 2608.01507](https://arxiv.org/pdf/2608.01507)). The structural graph Neo already runs (codebase-memory, chosen over gitnexus by a measured head-to-head in the 2026-07-23 spec) is in the RepoGraph/LocAgent family whose large paper gains (**+32.8%** relative success, [arXiv 2410.14684](https://arxiv.org/abs/2410.14684), author-reported) come from weak baselines; ContextBench found "sophisticated agent scaffolding yields only marginal retrieval gains" and that the bottleneck is *consolidation*, agents inspecting the right code and failing to use it ([arXiv 2602.05892](https://arxiv.org/html/2602.05892v1)). Its self-reported **3,400 vs 412,000** tokens for five structural queries ([codebase-memory guide](https://www.aibuilderclub.com/blog/codebase-memory-mcp-guide)) is a token claim, not an accuracy claim. The conclusion is to keep grep, the graph and the hybrid index each for what they measure well, and to spend the next effort on *what* is indexed rather than *how*.

The hybrid index should be tuned per query type, because the lexical and dense sides win different queries. On code-to-code retrieval a reranked hybrid scored **0.9073** nDCG@10 versus BM25 **0.8834** and dense **0.8519**, while on natural-language-to-code dense alone (**0.9687**) beat the hybrid, and on CosQA BM25 recall@100 was **0.74** versus dense **0.98** ([NanoCoIR](https://hakari-bench-leaderboard.hf.space/docs/benchmark-tasks/NanoCoIR)); on scientific-code repos hybrid plus cross-encoder rerank was best on 5 of 6 metrics but only modestly over dense ([arXiv 2607.05443](https://arxiv.org/pdf/2607.05443)). Meilisearch exposes exactly the knobs: per-query `semanticRatio` (lower for identifier-like queries, higher for descriptive ones), multiple named embedders per index with their own `documentTemplate`, binary quantisation, and federated multi-search that merges queries across indexes with per-query `federationOptions.weight` ([Meilisearch hybrid](https://meilisearch.com/docs/capabilities/hybrid_search/overview); [multiple embedders](https://www.meilisearch.com/docs/capabilities/hybrid_search/advanced/multiple_embedders); [federated search](https://meilisearch.com/docs/capabilities/multi_search/how_to/combine_text_and_image_search)). Chunking should be AST-aware, which gives **+4.3** Recall@5 on RepoEval and **+2.67** Pass@1 on SWE-bench over line chunks ([arXiv 2506.15655](https://arxiv.org/html/2506.15655v2)), with each method chunk carrying its class definition and imports as Qodo did at 10k-repo scale ([Qodo](https://www.qodo.ai/blog/rag-for-large-scale-code-repos/)). Freshness is content-hash change detection, never full re-index: a post-commit hook that re-chunks only changed files and upserts by chunk hash, the pattern Cursor uses with a Merkle tree and per-chunk embedding cache ([Cursor secure indexing](https://cursor.com/blog/secure-codebase-indexing)). The layout that follows is one Meilisearch index per project for code (filterable `project`, `path`, `lang`, `symbol`, `git_sha`, `mtime`), federated at query time with a higher weight on the current project and a hard `project` filter by default so a worker in A never silently acts on B's code; cross-project search is an explicit `search_all_projects` tool. Two standing decisions shape how this is exposed: the spec rejects engine-side embeddings (so embedding stays inside the index service, never in `src/`) and allows one code-intel MCP, so the search index should be one small MCP server with few, non-overlapping tools beside codebase-memory, not a second graph, consistent with Anthropic's "if a human engineer can't definitively say which tool should be used" rule ([Anthropic: context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

The genuinely new strategy is to index **what the code cannot say**: why it exists, what was decided, and what broke. Retrieval "reliably surfaces what was decided and reliably misses why" because the why is scattered, and agents do not notice when an old ADR conflicts with current code, so reversals must be recorded as Superseded with a link ([tianpan.co](https://tianpan.co/blog/2026/07/02/the-adr-your-agent-never-read), opinion); Qodo replaced a source-code index for review with "long-term memory over your PR history" ([Qodo](https://www.qodo.ai/?p=20694), vendor); `git-why` and the commit-archaeologist pattern walk blame → introducing commit → linked PR/issue and say when history is thin rather than invent a rationale ([git-why](https://github.com/phoenix-assistant/git-why); [commit-archaeologist](https://skills.cat/skills/shubhamsaboo/awesome-llm-apps/commit-archaeologist)); `commit-context` links a blamed commit to the agent session that produced it ([agentmemory](https://skillselion.com/skills/rohitg00/agentmemory/commit-context)). Neo can close the "why" gap deterministically because it already has the trace spine (ADR-0015/0016) and the plan registry (ADR-0019): write the thread ref and plan id into every worker commit as a trailer (`Neo-Trace: m4f2`, `Neo-Plan: <id>`), then build three shared indexes beside the per-project code indexes: `history` (commit messages, PR descriptions, ledger events, dispatch reports), `decisions` (ADRs, plan text and approvals, handoff notes, `CONTEXT.md`), and `incidents` (the rows from the first section, with `path`/`symbol` metadata so blame → symbol lookup also surfaces "this line was involved in incident N"). No study measures the value of indexing ledger or handoff data for coding agents specifically, so this is an inference; its cost is low because the data already exists in SQLite, and it is the only approach found that makes "why does this code exist" answerable without a model guessing from the diff. Architecture docs, ADRs and the glossary then become retrieval targets linked by path from a short CLAUDE.md rather than injected text, which the ETH cost finding supports.

Memory is where the research says to be *more* conservative than it is tempting to be. Vendor memory-layer benchmarks are contested and not comparable (Mem0 self-reports **91–93** on LoCoMo; Zep's own configs **80–83** while a third-party recalculation came to about **58** with the adversarial category; Letta showed a plain file plus grep at **74.0%** beat Mem0's then-reported 68.5% on GPT-4o-mini) ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory); [Zep](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)); memory is a documented attack surface, with MINJA reporting over **95%** injection success under idealised conditions, MemoryGraft implanting poisoned "successful experiences" that persist "until the memory is manually purged", and a Cisco demonstration rewriting Claude Code's MEMORY.md through a hook so the agent recommended committing API keys ([arXiv 2503.03704](https://arxiv.org/pdf/2503.03704v1); [arXiv 2512.16962](https://arxiv.org/abs/2512.16962); [Cisco](https://blogs.cisco.com/ai/identifying-and-remediating-a-persistent-memory-compromise-in-claude-code)); and TRACE found "memory alone is insufficient", agents frequently failing to comply with corrections they can retrieve, with the fix being to compile recurring corrections into runtime checks ([arXiv 2606.13174](https://arxiv.org/pdf/2606.13174)). Neo's capped curated memory with a frozen snapshot and FTS recall (Phase 2, **Done**, default off) is aligned with all three findings, and ADR-0020's proposal to consolidate on Claude auto-memory (34 dirs, about 730 notes, first 200 lines or 25 KB loaded per session) is the right direction *provided* the engine treats memory and instruction files as a write-protected surface: deny worker writes to `CLAUDE.md`, `MEMORY.md` and `.claude/` through the PreToolUse hook (or route them through an operator-approved path), diff and scan them at session start, and never let customer-tainted text reach a memory a worker loads (already enforced by `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` on tainted briefs). The operator-facing half is the `/memory` list-and-forget command with corrections typed `feedback` (P2, Planned) and the rule that a correction made twice becomes a hook or a check, not a third prose line; the dream loop's job becomes pruning lines whose stored rationale no longer applies, which the catastrophic-remembering study motivates.

## Roadmap: what first, why, and how big

## Open decisions only the operator can make

Nine decisions gate items above and are not for the engine or a worker to take. First, **ADR-0020**: approve auto-memory as the one project memory and choose whether Neo memory Phase 2 is retired or re-pointed (item 17; the plan also asks whether memory turns on for the company). Second, **more than one todo per project** via worktrees, amending ADR-0008 (item 19). Third, **`ask_operator` for loops**, which turns auto-deny into an escalation on autonomous paths (item 7). Fourth, the **Codex fail-closed default** and whether `workspace-write` is ever allowed without a governor (item 1). Fifth, the **observability stack and its data policy**: Grafana/Loki/Tempo versus SigNoz, GlitchTip versus self-hosted Sentry, and whether redacted production telemetry may be returned to a subscription worker at all, given Tempo's documented warning that returned trace data may reach the model provider and the recommendation to redact PII in the log pipeline before any MCP sees it (item 5). Sixth, the **prod access shape**: a forced-command `neo-deploy` user per host versus a runner per host, and whether any host may ever run a worker locally (item 12). Seventh, the **governor's prod rule set**, which is the first real P4 `policy_rules` content and widens nothing but narrows the keyword regex into precise denies (item 12). Eighth, the **SDK pin bump and the restart it implies**, since ADR-0009's updater merges but never restarts (items 0 and 20). Ninth, how the **vector and Meilisearch index is exposed**: one search MCP beside codebase-memory, or folded into the existing code-intel surface, with the spec's one-code-intel-MCP and no-engine-embeddings decisions as the constraints (item 16). A tenth, smaller one recurs on every preamble change: the **5,000-character ceiling** has about 480 characters of headroom, so the cause-statement, count-first, etiquette and before/after lines either displace existing text or the ceiling is re-decided explicitly rather than nudged by a test edit.

## Conclusion

The research reframes Neo's five problems as one: the engine already governs *what a worker may do* better than most products, but it still lets the worker *tell it what happened*. Every measured failure the operator feels (the symptom patched instead of the cause, the "done" that was not, the cost that was not counted, the prod change nobody could trace) is a place where a claim was accepted as a fact. A schema-validated report that the engine verifies before it assigns a status, a cause record the worker must write before it may edit, a deploy that only an operator message can approve, a commit that carries its trace id, and an incident that is indexed for the next worker are all the same move applied at different seams: record the fact, verify it in code, and only then let it flow. That move is also what keeps every standing decision intact, because none of it puts AI in the engine, touches the customer path or widens autonomy by itself.

The second shift is in how to measure progress. Benchmarks are contaminated or broken at the 30% level ([OpenAI](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)), harness deltas on the same model run to 10–15 points ([Factory](https://factory.com/news/terminal-bench)), and Anthropic dropped its own context resets and sprints as models improved ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Neo's ledger is therefore the only benchmark that matters: cost per verified-solved task, interventions per dispatch, reopened incidents per fingerprint, and merged PRs per review hour. Each gate proposed here should exist as a config flag with a measured reason, and the weekly review the operator already runs should be where a gate that no longer earns its cost is switched off.
