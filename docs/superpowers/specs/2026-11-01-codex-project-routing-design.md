# Codex project routing design

## Goal and observed evidence

Selecting Claude or Codex in Neo's console must switch the whole platform's operator-owned AI work to that SDK, including a request to open and work in `/home/neo` through the default company assistant, background work, and assistant roles. The same rule applies in both directions. The selection should survive a daemon restart. The original user-visible failure has not yet been reproduced: capture its exact error and test both the console's direct open form and a natural-language request to the company.

Today `setWorkerSdk` changes only the in-memory provider, existing worker controls keep their original SDK, and `neoMcpServers` builds an Anthropic in-process MCP server which the Codex adapter drops. The company instructions depend on the `dispatch` tool. These are verified gaps, not proof of the specific reported failure.

## Behavior

- The selected operator provider is durable and shared by console and `/sdk`. Restore it at startup; absent a selection, preserve existing configured defaults. An explicit provider environment override, if one exists, has precedence and is shown as such. Do not write tracked files.
- A switch takes effect for newly launched own-work sessions immediately. Existing sessions finish their current turn and drain already accepted input on their original provider; thereafter they close gracefully and reopen under the selected provider on the next delivery. Show the selected provider and any sessions still switching. Never interrupt work silently or lose/duplicate accepted input. Rapid toggles converge on the latest selection. A session that cannot drain remains visibly pending with a recovery path; it is not falsely reported as switched.
- SDK session IDs are provider-specific. Never pass a known Claude ID to Codex or vice versa; on change start a fresh thread with the existing handoff/memory context. Do not erase old provider history. Existing unknown-ID recovery must still work.
- Codex receives the same engine-owned `neo` tool definitions and access scope that the corresponding Claude session receives, including company dispatch and project notes. Reuse the existing handlers and schemas; no second implementation. Preserve the narrower consult and ingress tool sets. Any optional external MCP server must be translated only when supported and safe; otherwise visibly report the missing capability, never silently claim parity.
- A per-run, loopback-only MCP bridge uses the existing MCP SDK and a cryptographically random capability. Bind its tool set and caller context to that run, authenticate every request including initialization, and terminate it when the run ends or startup fails. No public listener, unrestricted localhost endpoint, secret in argv/logs, cross-run capability reuse, or tool exposure to unrelated sessions. Preserve cancellation and propagation of tool errors. Confirm installed Codex SDK and MCP SDK transport support in a real local spike before choosing the exact bridge transport; if authenticated HTTP is not supported end-to-end, implement a local stdio proxy with a protected capability channel instead. Fail closed if the bridge cannot start.
- Customer-origin routing stays behind the existing firewall. Codex sandbox and approvals are not equivalent to Claude's per-tool governor; do not claim full governance parity. Keep read-only runs read-only, do not weaken external-action approval, and explicitly reject a path when equivalent controls cannot be enforced.
- The chosen SDK is the platform-wide authority for all operator-owned AI work, not merely project workers: audit company, project, dispatch, loops, consult, handoff, judge, secretary, background producers, retries, and any direct SDK/API calls or independently configured AI roles. Remove or adapt own-work provider overrides and boot-time captures so new work always uses the latest choice in both directions. If an operator-owned feature cannot work with the selected SDK, disable it with an actionable visible error; never silently fall back to the other SDK. Keep deterministic engine work provider-independent and preserve the customer-direct firewall and its separately configured customer provider.

## Verification and release

Automated tests cover provider persistence, switching races, context isolation, bridge authentication/lifecycle and tool scope, routing across worker paths, console display, and failures. A real Codex smoke test in a disposable repository must verify the company can dispatch a project and that the project can invoke an allowed Neo tool; use a fake side-effect-free tool for transport checks. The explicit `/open` path and the reported failure must also be reproduced. Run `bunx tsc --noEmit` and `bun test`. Record SDK/transport limits and the security decision in an ADR. A fix is not live until the running daemon contains the tested commit and the end-to-end smoke passes against that build; preserve active work during rollout.
